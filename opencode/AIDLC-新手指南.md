# 第一章 先搞清楚：你在学什么

## 1.1 从一个真实的痛点说起

假设你用 AI 编程助手（比如 opencode）做一个真实项目。第一天很爽：你说"帮我写个登录功能"，它唰唰唰就写完了。但做到第二周，问题开始出现了：

- **它不问就动手**。你随口说了句"用户可能要导出数据"，它直接把导出功能写了，而你只是想讨论一下要不要做。
- **它替你做了你没看见的决定**。它选了 PostgreSQL 而不是 MySQL，你三天后才发现，已经改不动了，而且没人记得当时为什么这么选。
- **它跳过了它觉得不重要的步骤**。没写测试、没做设计，直接堆代码。等出 bug 了，连你自己都说不清系统是怎么搭起来的。
- **它失忆**。对话窗口一关一开，它完全不记得昨天干到哪了，你们只能从头对一遍。
- **它的话没法追责**。上周它说"这个设计是评审过的"，但评审记录在哪？谁批的？找不到了。

这些问题的共同根源是：**AI 模型本质上是个"即兴发挥"的系统**——它每次回答都是现场生成的，没有内置的流程观念、没有持久的记忆、没有"这件事必须经过谁批准"的概念。

## 1.2 AI-DLC 的回答：把"流程"从 AI 手里拿出来

AI-DLC（AI-Driven Development Life Cycle，AI 驱动开发生命周期）是 AWS 提出的一套方法论。它的核心洞察用一句话说：

> **让 AI 做它擅长的（理解需求、写设计、写代码、回答问题），让确定性的程序做 AI 不擅长的（记住进度、决定流程顺序、记录决定、强制执行检查）。**

所以 AI-DLC 不是一个单纯的"提示词模板"，而是一个**双层系统**：

- **上层是一群 Markdown 文件**：告诉 AI"你现在是产品经理，去跟用户确认需求"——这部分靠 AI 的理解力工作；
- **下层是 50 多个 TypeScript 小程序**：管状态、管记账、管流程顺序、管质量检查——这部分完全不靠 AI 自觉，程序说了算。

两者配合的效果是：AI 还是那个聪明健谈的 AI，但它被装进了一条流水线里——**每一站该干什么、干完了谁签字、签完字记在哪，全部由程序控制**。

## 1.3 这个 `opencode/` 目录到底是什么

你现在看的这个目录，是 AI-DLC v2.0 在 **opencode**（一个开源的命令行 AI 编程工具）上的完整发行包。它不需要安装、不需要编译——把整个目录放进你的项目里，opencode 启动时就会自动发现它，然后你就多了一个 `/aidlc` 命令。

这个目录里的约 300 个文件分三类：

1. **给 opencode 看的**（`.opencode/` 和 `opencode.json`）：命令定义、角色定义、事件翻译器；
2. **流程引擎本体**（`.aidlc/`）：33 个步骤的定义、50 多个工具程序、17 个自动触发的脚本——**这部分和其他 AI 工具（Claude Code、Cursor 等）的版本逐字节相同**；
3. **工作数据**（`aidlc/`）：你用它做项目时产生的所有档案——需求文档、设计图、决定记录、进度状态。

## 1.4 开始之前你需要什么

- **opencode ≥ 1.17**：命令行输入 `opencode --version` 检查；
- **bun**：一个 JavaScript/TypeScript 运行时（类似 Node.js 但更快），插件的所有工具程序都靠它运行。安装：官网 bun.sh 一条命令；
- **一个模型服务**：opencode 自己配置的（比如 Anthropic、AWS Bedrock 等）。插件里 5 个角色默认指向 AWS Bedrock 上的 Claude 模型，如果你的服务商不同，可以在项目配置里改。

权限方面不用担心：插件默认**所有命令执行前都要问你**，只有框架自己的登记过的命令可以免询问直接跑（后面第十七章会详细讲它的安全设计）。

# 第二章 三分钟总览：这套系统长什么样

## 2.1 一个比喻：软件工厂

把 AI-DLC 想象成一家管理严格的软件工厂：

- **你是老板（甲方）**。工厂接你的订单，但每个关键节点都要你签字；
- **AI 会话是厂长（叫 conductor，指挥）**。他接待你、理解你的需求、协调各个部门；
- **14 个 AI 角色是各工种**：产品经理、架构师、设计师、开发、测试、运维……厂长按工序让他们轮流上；
- **流程卡片是 33 个 stage（步骤）**：从"确认意图"到"部署上线"，每一步干什么都写在卡片上；
- **车间调度系统是编排引擎（orchestrate 工具）**：一个程序，厂长每干完一步就问它"下一步是什么"，它查状态后给出唯一答案；
- **质检员是传感器（sensor）和评审员（reviewer）**：自动检查和人工挑刺两道关；
- **门卫是审批门（gate）**：每一步的产物出厂前必须你点头；
- **台账是审计日志（audit log）**：只增不删的账本，谁在什么时候做了什么、你批了什么，永久可查；
- **规章制度是五层规则文件**：厂规（org.md）→ 车间规定（team.md）→ 本项目 special 要求（project.md）……

## 2.2 一次完整使用的时间线

输入 `/aidlc 帮我做一个课程表小程序` 之后：

```
[初始化 0.x]  插件自动扫描项目 → 是空项目还是已有代码？→ 建立工作档案
     │        （全自动，不需要你做任何事）
     ▼
[构思 1.x]    AI 扮演产品经理：给谁用？解决什么？市面上有类似的吗？
     │        问题写在文件里，你逐条回答 → 产出《意图陈述》《范围文档》
     │        ── 审批门：你签字 ──
     ▼
[需求与设计 2.x] AI 扮演产品经理+架构师：详细需求（每条有编号）、
     │          系统拆成哪几个模块、模块怎么连接、先做哪个后做哪个
     │        ── 审批门：你签字 ──
     ▼
[开发 3.x]    按模块逐个来：先交施工方案 → 你批准方案 → AI 写代码
     │        → 自动构建和测试 → 测试不过有明确的处理流程
     │        ── 审批门：你签字 ──
     ▼
[上线 4.x]    部署流水线、环境检查、监控告警、应急预案
     │        ── 审批门：你签字 ──
     ▼
[完成]        全部档案留存在 aidlc/ 目录里，可以提交 git
```

**但不是每个项目都走全部 33 步**。修个小 bug 走精简版（9 步），做企业级系统才走全程。这叫 **scope（范围套餐）**，第五章细讲。

## 2.3 你会反复看到的三个动作

整个使用过程中，你作为用户其实只做三件事：

1. **回答问题**：每个阶段开始，AI 会把问题写在一个 `xxx-questions.md` 文件里，聊天里显示成编号选项（1/2/3），你回个数字或者说自己的想法；
2. **在审批门做决定**：每个阶段结束，AI 展示成果摘要，你选"批准 / 要求修改 / 其他"；
3. **中途随时插话**：改主意了、有新想法了、想跳过某步了，直接说，它有对应的处理流程。

# 第三章 术语体系（本指南最重要的一章）

后面的每一章都会用到这些词。建议完整读一遍，读完你就掌握了 AI-DLC 的"语言"。

## 3.1 关于"系统形态"的词

### harness（宿主外壳）
AI-DLC 是一套方法论，但它必须附着在某个具体的 AI 工具上才能跑。这个被附着的工具就叫 harness。同一个 AI-DLC 核心，装在 opencode 上就是 opencode 版，装在 Claude Code 上就是 Claude Code 版——目前官方支持 7 个 harness。**你这份的 harness 是 opencode**。

为什么要知道这个词？因为文档里经常出现"在某某 harness 上行为不同"——说的就是"换了个 AI 工具，这一步的实现方式会不一样"。

### skill（技能）
一个写给 AI 看的**操作手册**（Markdown 文件，带头部元信息）。opencode 启动时会发现它，之后你可以在聊天里用 `/技能名` 调用它，AI 就会严格按手册里写的流程执行。

这个插件有 41 个技能：1 个主手册（`/aidlc`）+ 30 个"单步执行"手册（`/aidlc-code-generation` 之类）+ 5 个"套餐快捷方式"（`/aidlc-bugfix` 之类）+ 几个辅助手册。

### agent（智能体 / 角色）
一份"人格设定文件"。AI 读到它就临时扮演那个角色：说话方式、关注重点、专业知识都会切换。比如 `aidlc-product-agent` 让 AI 变成产品经理，`aidlc-developer-agent` 让它变成资深开发。

**为什么要搞角色？** 因为"什么都懂一点"的 AI 不如"此刻专注当一个角色"的 AI。问需求时用产品经理的脑子，写代码时用开发的脑子，挑刺时用评审员的脑子——每个角色还有自己的知识库文件（比如架构师角色配了 DDD、架构模式的参考资料）。

### conductor（指挥）
就是运行 `/aidlc` 的那个主 AI 会话。它是唯一跟你对话的"人"，也是唯一能分派任务的"人"。14 个角色之间**不允许互相直接联系**——所有协作都经过指挥中转（这个专业上叫"总线模式"）。

为什么这样设计？如果角色之间可以自由对话，协作就会变成 AI 之间的黑箱，你看不到也控制不了。全部经过指挥，每一步协作你都能在对话里看到。

### hook（钩子）
挂在 opencode 事件上的小脚本，事件一到就自动执行。比如：AI 每次写文件 → 钩子自动记一笔账；AI 想执行绕过流程的命令 → 钩子拦下来报错。**钩子是"规矩不靠 AI 自觉"的关键实现**——它不是建议，是强制执行。共 17 个，第十三章逐个讲。

### tool（工具）
50 多个 TypeScript 小程序（用 bun 运行）。每一个负责一件"必须精确"的事：记录进度（state）、记账（audit）、决定下一步（orchestrate）、跑质量检查（sensor）……AI 通过命令行调用它们，比如 `bun .aidlc/tools/aidlc-orchestrate.ts next`。

**为什么要有工具？** 因为让 AI 自己记"做到第几步了"是不可靠的（它会记错、会编造），让程序记就永远不会错。这就是整个方法论最核心的工程决策：**凡是要精确的事，落成程序；凡是要判断的事，留给 AI 和你**。

### plugin（插件）
这个词在本文有两个含义，注意区分：
1. **opencode 插件**：`.opencode/plugin/` 下的 TypeScript 文件，opencode 进程内加载，本目录只有一个（适配器，见第十章）；
2. **AI-DLC 插件**：给 AI-DLC 框架本身增加新步骤/新角色的扩展包，有完整的开发工具链（第十九章）。

## 3.2 关于"流程"的词

### phase（大阶段）
软件生命周期的五个大块：**Initialization（初始化）→ Ideation（构思）→ Inception（需求与设计）→ Construction（开发）→ Operation（上线运维）**。用盖房子比喻：勘察场地 → 业主座谈会 → 出图纸 → 施工 → 交付入住。

### stage（步骤）
每个大阶段里的具体步骤，共 33 个。比如 Inception 里有"需求分析""用户故事""领域设计"等 9 步。每个步骤有一份自己的说明书文件（frontmatter 元信息 + 执行步骤），里面写死了：这步谁负责（lead agent）、谁协助（support agents）、产出哪些文件（produces）、需要哪些上游文件（consumes）、要不要评审员（reviewer）、跑哪些自动检查（sensors）。

### scope（范围套餐）
预设的"流程裁剪方案"，共 11 档。修 bug 用 `bugfix` 档（只走 9 步），做企业系统用 `enterprise` 档（全 33 步）。每个 scope 还附带**深度**（depth）：Minimal（少问少写）/ Standard / Comprehensive（多问多写）。

**为什么要有 scope？** 因为"给每个项目都上全套流程"和"给每个项目都裸奔"一样糟糕。流程的价值在于恰到好处——这是 AI-DLC 名字里 "Adaptive"（自适应）的含义。

### gate（审批门）
每个步骤结束时的**强制人工检查点**。AI 展示这步产出了什么，你选：批准 / 要求修改 / 其他。在你明确表态之前，流程完全停住。

审批门是整个方法论的**灵魂**。它保证：没有任何设计、任何代码、任何决定，能在你不知情的情况下流向下一步。而且"批准"这个动作本身会被记进审计日志——半年后你能查到"3 月 15 日你批准了架构设计"。

几个铁律：
- AI **永远不能**替你批准，也不能把"你没反对"当作批准；
- 你说"这步你看着办"，授权只对这个步骤这一次有效，下一步重新开始问；
- 初始化三步骤（0.1-0.3）除外——它们只是扫描建档，没有需要你决定的内容，自动通过。

### directive（指令）
编排引擎（orchestrate 工具）每次被问"下一步干嘛"时，返回的**唯一一条**指令。指令是 JSON 格式的，有个 `kind` 字段说明类型：运行某个步骤（run-stage）、问用户问题（ask）、打印信息（print）、出错了（error）、全部完成（done）、已暂停（parked）……

**为什么每次只给一条？** 这是防止 AI"一口气规划十步然后自由发挥"的机制。AI 拿到一条指令 → 执行 → 汇报结果 → 再问。每一步都重新读取最新状态，所以中途你改了任何东西，下一步的指令都会反映出来。

### forwarding loop（转发循环）
就是上面那个"问引擎 → 执行 → 汇报 → 再问"的循环，整个插件的心跳。AI 的主手册（SKILL.md）把它写成铁律：不许自己琢磨"接下来该干嘛"，永远问引擎。

### orchestrate / 引擎 / engine
`.aidlc/tools/aidlc-orchestrate.ts` 这个程序的俗称。它是整个系统的**调度中心**：知道全部 33 个步骤的依赖关系（一张有向无环图）、知道当前进度（状态文件）、知道当前套餐裁掉了哪些步骤，所以它能确定性地回答"下一步是什么"。

注意：引擎**不做任何 AI 式判断**——它是纯程序，给定同样的状态永远返回同样的答案。这是刻意的：流程顺序这种事，要的就是绝对可预测。

### intent（意图）与 record（档案）
你交代的一件完整工作（"做课程表小程序"）就是一个 intent。它的所有产出存在一个专属文件夹里（叫 record 目录），路径形如 `aidlc/spaces/default/intents/260907-course-app/`。里面按大阶段/步骤组织，放着所有文档、日记、账本。

### space（空间）
intent 的上级分组，给多团队共用一个大仓库时隔离用的。单人/单团队永远只有 `default` 一个空间，初学可以完全忽略这个概念。

### park（暂停）与 resume（恢复）
长流程不必一次做完。说"先停一下"或跑 `park` 命令，引擎会在一个"干净的步骤边界"把进度存好。下次（哪怕换了电脑、过了几天）输入 `/aidlc --resume`，它会从存档点继续。

## 3.3 关于"质量把关"的词

### sensor（传感器）
自动质量检查器，共 6 个。比如 `required-sections` 检查"文档必须包含规定的章节"，`traceability` 检查"每条需求都能追踪到下游"。有的在文件写入时触发（提醒性质），有的在审批门触发（**阻塞性质**——不通过就不给开门，除非你显式选择"覆盖"并留下审计记录）。

### reviewer（评审员）
两个"只挑刺不干活"的特殊角色：产品负责人（product-lead，审需求类文档）和架构评审人（architecture-reviewer，审设计类文档）。某步骤声明了评审员，产物就必须先过评审才能给你看。

评审分两档：**adversarial（对抗式）**——评审员假设"这东西肯定有毛病"，想尽办法找茬，找到为止（最多 2 轮）；**advisory（咨询式）**——评审员只审一遍，意见原样附上，最终判断留给你。

### learnings ritual（学习仪式）
每个步骤完成后、审批门之前，AI 会问你："这次有什么经验值得下次记住吗？"你说"以后接口文档要先出"，这条经验就会经过**冲突检查**（不能和组织级规矩矛盾）后被程序写进团队规则文件（team.md/project.md），从此永久生效。

这是 AI-DLC 的"自学习"机制：**团队越用，流程越贴合团队习惯**。

### traceability（可追溯性）
贯穿全程的一条暗线：需求有编号（FR1、NFR2）、用户故事有编号（US1.1）、验收标准有编号（AC1.1.1）、业务规则有编号（BR1.1）、工作单元有编号（U1）。每个步骤产出一个 `traceability.json`，记录"我的哪些产物对应上游的哪些编号"。到最后你能回答："FR3 这条需求，对应哪个故事、哪个模块、哪段代码、哪个测试？"

### question file（问题文件）
AI 提问不走闲聊，而是写在 `xxx-questions.md` 文件里：每个问题有 A-E 选项 + 一个"Other（自己说）"，你回答后答案写回文件的 `[Answer]:` 标签。**文件是事实源**——聊天记录可能丢，文件永远在。

## 3.4 关于"并行与规模"的词

### Unit（工作单元）
一个大功能拆出来的、可独立交付的块，比如"用户模块""报表模块"。有编号（U1、U2）、有类型（service/ui/library 等）、有复杂度评级（S/M/L/XL）、有依赖关系（谁依赖谁，构成一张图）。

### Bolt（构建冲刺）
一次构建行动：一个或多个 Unit 排在一起做。开发计划（delivery-planning 步骤）会决定 Bolt 的顺序——注意**顺序是经济决策不是技术决策**（"先做客户最想看的"可以压过"技术上的依赖顺序"，但偏离必须写明理由）。

### walking skeleton（行走骨架）
一种开发策略：第一个 Bolt 不做完整功能，而是做一个"从界面到数据库全打通但极薄"的骨架版本，先验证整条技术链路可行，再往上堆肉。你的团队可以在规则文件里设置"总是/从不/看情况"启用它。

### autonomous / gated（自治模式）
骨架交付后（或开发阶段开始时），AI 会问你一次："剩下的构建要怎么跑？"——**Continue autonomously**（自动跑完，出问题再停）还是 **Gate every Bolt**（每个 Bolt 都停下来等你批准）。这就是自治模式选择，选一次管整个开发阶段。

### swarm（蜂群）
自治模式下，多个 Unit 可以**并行**开工：每个 Unit 在独立的 git worktree（同一仓库的独立工作目录，互不干扰）里由独立的 AI 子会话开发，完成后由程序统一验收（跑检查、要评审记录）再逐个合并回主干。

### worktree
git 的功能：同一个仓库可以同时检出多个工作目录。蜂群用它隔离并行开发。你不需要手动操作，工具程序（aidlc-worktree.ts）全包了。

## 3.5 关于"记忆与知识"的词

### memory（规则层）
`aidlc/spaces/default/memory/` 下的规则文件，分五层：**org.md（组织默认）→ team.md（团队约定）→ project.md（项目特殊）→ phases/*.md（大阶段规则）→ 步骤级**。严格叠加：每一层只能加码不能松绑，下层和上层冲突的规则在学习仪式的冲突检查处就会被拒绝。

### CodeKB（代码知识库）
如果你的项目已有代码（brownfield，棕地项目），"逆向工程"步骤会分析整个代码库，产出架构、依赖、技术栈等 9 份文档，存在 `codekb/` 里。它是**跨任务累积**的：这次任务扫描过，下次任务可以直接复用（系统会先检查代码有没有变化）。

### DocumentKB（文档知识库）
把团队的 PDF/Word/Markdown 文档做成可检索目录，AI 各阶段可以引用。关键安全设计：**文档内容只被当作"数据"，永远不会被当作"指令"**——客户文档里就算写着"跳过所有测试"，AI 也不会照办。

### audit log（审计日志）
只增不删的账本，存在每个 intent 的 `audit/` 目录。91 种事件类型（阶段开始、门批准、问题回答、传感器结果……），每条带 ISO 时间戳。**AI 被明令禁止自己写账本**——所有记录由工具程序在状态变化时自动写入，这是"记录可信"的基础。

### runtime-graph
从账本和日记汇总出的统计报表（每步耗时、检查计数、经验条数……）。三个"回顾类"命令（`/aidlc-session-cost`、`/aidlc-replay`、`/aidlc-outcomes-pack`）的数字全部来自它。

# 第四章 完整上手：从零到第一个工作流

## 4.1 安装与自检

1. 把 `opencode/` 目录的内容放进你的项目根目录（`.opencode/`、`.aidlc/`、`aidlc/`、`opencode.json`、`AGENTS.md`、`.gitignore`）；
2. 确认 `bun` 在 PATH 上（或者装在 `~/.bun/bin/bun`——适配器会直接探测这个位置）；
3. 启动 opencode，输入 `/aidlc --doctor`——这是"体检"命令，会检查：钩子是否都能正常运行（每个钩子有心跳文件）、步骤图有没有损坏、工作区配置有没有漂移。全部绿色就可以开始了；
4. `/aidlc --version` 打印框架版本（应该是 2.7.1）。

## 4.2 第一个工作流：详细过程

输入 `/aidlc 帮我做一个命令行待办事项工具`。接下来发生的事：

**① 静默初始化（几秒，全自动）**
初始化三步骤（0.1 建目录 → 0.2 扫描项目 → 0.3 写状态文件）自动跑完，没有审批门。你会看到 AI 简短说了一句"Let me get started on …"，然后直接进入下一步——这是规矩：它**不许**跟你播报"我正在初始化"这种内部细节。

**② 套餐确认**
它会告诉你它判断的 scope（比如"这看起来是个标准特性，走 feature 流程"），你可以纠正。

**③ 需求问答**
AI 切换到产品经理人格，创建 `requirements-analysis-questions.md`，开始问你问题。聊天里长这样：

```
**Question** — 这个工具的主要使用者是谁？

1. **个人用户** — 自己管理自己的待办
2. **小团队** — 多人共享任务列表
3. **Other** — describe what you want instead

Reply with a number (or just tell me).
```

你回 "1"。它把答案写进问题文件，接着问下一个。问题数量取决于套餐深度：Minimal 档问 2-4 个，Standard 档 5-8 个，Comprehensive 档 8-12 个以上。

你也可以不逐条答：它支持三种模式——**guided**（它一条条问，默认）、**self-guided**（你自己打开问题文件编辑，改完说声"done"）、**chat**（自由聊天，它替你整理答案写回文件）。

**④ 生成前确认**
所有问题答完，它会把你的回答汇总成一份摘要，问一句特殊的确认："**以上理解都对吗？**"（Looks correct / Request changes）。这是一个强制停顿——**在它确认理解无误之前，不会生成任何正式文档**。你说"对"，它才写 `requirements.md`。

**⑤ 评审与经验**
文档写好后，如果这一步配了评审员（需求分析配了产品负责人），会先让评审员挑刺一遍，意见附在文档末尾的 `## Review` 章节给你看。然后它问学习仪式的问题："这次有什么值得下次记住的吗？"——可以答"Nothing to add"。

**⑥ 审批门**
最后展示成果摘要 + 批准问题：

```
**Approval** — Requirements Analysis complete. How would you like to proceed?

1. **Approve** — Continue to User Stories
2. **Request Changes** — Provide revision feedback
3. **Other** — describe what you want instead
```

你回 1，它记录"批准"、推进到下一步。**你说 2（要求修改），就进入修订循环**：说哪里不满意 → 它改 → 改了的话重新评审 → 再问。同一个步骤修了 3 轮你还不满意，它会多给一个选项 "Accept as-is"（就这样吧，先往前走）——防止无限返工。

**⑦ 之后每个步骤重复 ③-⑥ 的节奏**，直到整个工作流完成。

## 4.3 中途的各种情况

**想暂停**：直接说"先到这里"，或让它 park。下次 `/aidlc --resume` 继续。

**对话被压缩了/程序重启了**：不用担心。压缩前钩子会校验状态文件并写一个"恢复面包屑"；新会话打开 `/aidlc`，它会探测到有未完成的工作流，给你菜单：继续 / 重做当前步 / 跳转 / 重新开始。

**突然想改方向**：直接说。它会判断——你这是接着干（继续）、是件新事情（问你要不要另开一个 intent）、还是要裁剪剩余流程（触发 compose 重排，**也要你批准**）。

**想跳过某步**：说"跳过市场调研"。如果是明确的命令式请求，它会直接给你呈现一个"跳过这些步骤？"的批准门；批准后用 `recompose` 工具改流程。注意它**绝不会**自己决定跳过。

## 5.1 总图

```
opencode/

│
├── .opencode/           # 【翻译层】opencode 专属，别的 harness 没有
│   ├── command/aidlc.md
│   ├── agents/          # 14 个角色（opencode 格式）
│   └── plugin/aidlc-opencode-adapter.ts
│
├── .aidlc/              # 【引擎本体】跨 harness 共享
│   ├── skills/          # 41 个操作手册
│   ├── agents/          # 14 个角色（通用格式）
```

## 5.2 根目录三个文件

**`opencode.json`**：opencode 的项目配置。干了三件事：① 告诉 opencode 去 `.aidlc/skills/` 找技能；② 告诉它把 `aidlc/spaces/default/memory/` 下的规则文件**每次会话都读进上下文**（这样团队规则永远在场）；③ 设权限——默认所有 bash 命令要问你，只有框架登记过的工具/钩子命令可以直接跑。

**`AGENTS.md`**：写给 AI 的项目说明书。opencode 启动时自动注入。内容是 AI-DLC 的导览：怎么用、东西都在哪、opencode 版有什么差异。**同时也是给你的一份很好的快速参考**。

**`.gitignore`**：见第二十章（Git 协作）。

## 5.3 `.opencode/` —— 翻译层

为什么需要这一层？因为 AI-DLC 核心是为"通用的 AI 工具"写的，而每个工具接入的方式不同。opencode 的接入方式是：命令放 `.opencode/command/`、角色放 `.opencode/agents/`、事件处理放 `.opencode/plugin/`。

- **`command/aidlc.md`**：`/aidlc` 命令的定义，内容就一句话："立即调用 aidlc 技能并严格照做"。真正的逻辑在技能里。
- **`agents/`**：14 个角色文件的 opencode 格式版（和 `.aidlc/agents/` 里的通用版内容逐字节相同，只有头部的工具禁用声明写法不同）。
- **`plugin/aidlc-opencode-adapter.ts`**：**适配器**，整个目录里唯一真正为 opencode 编写的程序（774 行）。第十章专门讲它。

## 5.4 `.aidlc/` —— 引擎本体

- **`skills/`**：41 个操作手册。最重要的是 `aidlc/SKILL.md`（主手册，268 行，定义了指挥的一切行为准则）。其余是 30 个单步手册、5 个套餐快捷手册、和几个辅助手册（详见第十四章）。
- **`tools/`**：50 多个程序。最核心的是 `aidlc-orchestrate.ts`（调度引擎）、`aidlc-state.ts`（状态管理）、`aidlc-audit.ts`（记账）。`tools/data/` 里是静态数据：编译好的步骤依赖图（stage-graph.json）、套餐网格（scope-grid.json）、模型价格表等。第十三章有完整清单。
- **`hooks/`**：17 个自动脚本。第十三章逐个讲。
- **`aidlc-common/stages/`**：33 个步骤的说明书，按 5 个大阶段分目录。第六章、第七章全部在讲它们。
- **`aidlc-common/protocols/`**：8 份"工作规范"——主规范（怎么提问、怎么开门）、开发阶段规范、多角色协作规范、评审规范、恢复规范等。第八章讲。
- **`aidlc-common/conductor.md`**：指挥人格手册——"怎么把每个步骤干好"的技艺（提问的艺术、记日记的格式、处理矛盾的方法）。引擎会在工作流开始时把它注入给 AI。
- **`scopes/`**：11 个套餐的定义文件。第五章（后文第九章）讲。
- **`sensors/`**：6 个质量检查器的定义。第十一章讲。
- **`knowledge/`**：按角色分的方法学参考书（40 多篇）：架构师的有 ADR 模板和 DDD 模式，安全工程师的有 STRIDE 威胁建模指南，测试的有测试策略模式……AI 扮演角色时会先读对应的参考书。
- **`agents/`**：14 个角色的通用格式人格文件。框架以**这个目录**为准来判断"哪些角色可用"。

## 5.5 `aidlc/` —— 工作档案

刚拿到手时这里几乎是空的：只有 `spaces/default/memory/` 下的规则种子文件（org.md 等）。跑起来之后会逐渐生成：

- `intents/<日期>-<名字>/`：每个任务的完整档案（状态、账本、各步骤产物、日记）；
- `knowledge/`：团队知识库和文档知识库（DocumentKB）；
- `codekb/`：代码知识库（棕地项目扫描产物）。

**这个目录要提交 git**——它就是"项目的过程资产"：半年后新同事加入，看这里的审计日志和需求文档就能明白系统是怎么一步步长出来的。

# 第六章 核心机制：引擎和指挥怎么配合

这一章讲整个系统最精妙的设计：**AI 和程序的分工**。理解了这一章，你就理解了 AI-DLC 的灵魂。

## 6.1 为什么不能让 AI 自己管流程

假设没有引擎，只靠一份超长的提示词告诉 AI："先做需求，再做设计，再写代码，每步要批准……"会发生什么？

- 对话长了之后，AI 对"现在该哪一步"的记忆会模糊甚至记错；
- AI 可能"好心"合并步骤："设计和需求差不多，我一起做了吧"；
- AI 可能自己宣布"用户刚才的意思就是批准了"；
- 崩溃重启后，AI 只能靠猜来恢复进度。

这些不是某个模型的问题，是所有大语言模型的本质局限：**它们是概率生成器，不是状态机**。

## 6.2 解决方案：状态机外置

AI-DLC 把"状态机"从 AI 脑子里搬到了一个程序里。这个程序就是 `aidlc-orchestrate.ts`（引擎）。它手里有两样东西：

1. **步骤依赖图**（`stage-graph.json`）：33 个步骤谁依赖谁、谁是哪个大阶段的、谁是可选的——一张提前编译好的静态图；
2. **当前状态**（`aidlc-state.md`）：哪个步骤打勾了、哪个在进行中、当前套餐裁掉了哪些步——一个磁盘上的文件。

给定这两样，"下一步是什么"就是一个**纯计算问题**，不需要任何 AI 判断。

## 6.3 转发循环的运作细节

引擎只有 5 个命令，记住这 5 个你就懂了全部调度：

| 命令 | 干什么 | 谁来调 |
|---|---|---|
| `next` | 读状态 → 算下一步 → 返回一条指令（**只读，不改任何东西**） | 指挥反复调 |
| `report` | 指挥干完活了，汇报结果（"这步批准了"/"被拒了"/"不适用跳过"）→ **引擎这才改状态** | 每步完成后调 |
| `continue` | 内部传输用：规则文件太长时，引擎分段发给指挥，指挥用它取后续段 | 指挥自动调 |
| `park` | 在干净边界暂停工作流 | 你想停时 |
| `team-board` | 只读查询团队构建分工 | 多人协作时 |

于是整个工作流就是这个循环：

```
指挥: bun .aidlc/tools/aidlc-orchestrate.ts next
引擎: {"kind": "run-stage", "stage": "requirements-analysis", ...}   ← 一条指令
指挥: （扮演产品经理，提问、写需求文档、开门、等你批准）
指挥: bun .aidlc/tools/aidlc-orchestrate.ts report --stage requirements-analysis --result approved
引擎: （改状态：需求分析打勾，发审计事件）
指挥: bun .aidlc/tools/aidlc-orchestrate.ts next
引擎: {"kind": "run-stage", "stage": "user-stories", ...}
……循环直到引擎返回 {"kind": "done"}
```

注意这个设计的美妙之处：**`next` 永远只读**。所以即使 AI 多问了一次、问错了时机，也不会搞坏状态。所有修改都经过 `report`，而 `report` 有严格校验（比如没真的经过批准流程的"批准"会被拒绝）。

## 6.4 指令的 8 种类型（白话版）

引擎返回的指令有个 `kind` 字段，目前实际会发出 8 种：

| kind | 白话解释 | 你要做什么 |
|---|---|---|
| `run-stage` | "该干某一步了"，附带：这一步的说明书路径、需要读的上游文件、规则包、要不要开门 | 什么都不用做，AI 会执行 |
| `load-steering` | "先把这些规则读进来"，纯内部传输 | 无感 |
| `ask` | "这个问题得问人类"（比如：要不要为新事情开个新工作流） | 回答它 |
| `print` | "把这段信息给用户看"或"执行这条具体命令" | 看 |
| `invoke-swarm` | "这批模块可以并行开工了"（自治模式下） | 无感或等结果 |
| `error` | "出错了，这是给人看的错误信息" | 看错误 |
| `done` | "全部完成了" | 收获成果 |
| `parked` | "已暂停，进度存好了" | 下次 resume |

## 6.5 为什么 AI 说话那么"克制"

用一段时间你会注意到：这个 AI 不啰嗦。它不会播报"我正在调用工具""接下来我要做 X"——这是**刻意设计的语音契约**（voice contract）：

- 内部术语（引擎、指令、套餐网格……）永远不跟你说——你是在做项目，不是来学框架的；
- 工具调用之间保持沉默——专家在你身边干活不会念叨自己的每次敲键；
- 只有四类内容会到你眼前：引擎写好的说明文字、问题、审批门、成果摘要。

如果你见过别的 AI 工具刷屏式的"思考过程播报"，会发现 AI-DLC 的对话异常干净——原因就在这里。

## 6.6 新工作与流程重塑的判断

工作流进行中你又输入了一段话，指挥要先做一个判断（这是它少数被允许自主判断的事）：

1. **这是接着干**（默认）：比如你回答了它的问题、补充了细节——继续当前工作流；
2. **这是件新事情**：比如课程表项目做到一半你说"再帮我做个记账工具"——它会**问你**要不要另开一个 intent（不会自作主张开）；
3. **这是要改计划**：比如"市场调研跳过吧，这个市场我熟"——触发流程重塑（compose/recompose），**一定要你批准**才生效。

## 6.7 自适应规划器（composer）白话

不确定该用哪个套餐？输入 `/aidlc compose "你的任务描述"`，会启动一个特殊角色——**自适应规划器**。它会：

1. 只读扫描你的项目（不改任何东西）；
2. 从五个维度评估任务的"不确定性"（这套评分叫 **ARS**）：
   - **意图歧义**：你说清楚了没？
   - **结构不确定性**：代码库有多复杂难懂？
   - **验证熵**："做对了没有"好不好检查？
   - **风险**：搞砸了影响多大？
   - **未决假设**：有多少事是猜的？
3. 基于评分推荐一套裁剪后的步骤清单：哪步做、哪步跳过、**每个跳过都有理由**；
4. 呈现给你批准 / 修改 / 拒绝。

分数只是参考（文档原话："未校准先验，纯咨询性质"）——**决定权永远在你**。

# 第七章 33 个步骤逐个白话讲解

这是本文最长的一章。每个步骤讲四件事：**这步在干嘛（比喻）、AI 扮演谁、会问/会做什么、产出什么文件**。跳过逻辑也一并说明。

## 7.0 大阶段零：初始化（3 步，全自动，无审批门）

### 0.1 Workspace Scaffold（建脚手架）
纯事务性工作：把本次工作流需要的目录结构建好（哪些大阶段要跑就建哪些）。相当于工厂开工前把工位摆好。你无感。

### 0.2 Workspace Detection（项目检测）
扫描你的项目文件夹：有没有已有代码？什么语言、什么框架、有没有测试设施？结论分两类：**greenfield（绿地）**= 从零开始的新项目；**brownfield（棕地）**= 已有代码的项目。这个分类直接决定后面的路由（棕地项目会多走"逆向工程"步骤）。

### 0.3 State Init（状态初始化）
创建本次工作流的"总控文件" `aidlc-state.md`：项目描述、套餐配置、全部步骤的打勾清单。从这刻起，进度有了持久化载体。然后根据绿地/棕地定好第一站去哪。

## 7.1 大阶段一：Ideation 构思（7 步）

> 盖房子比喻：业主座谈会。先聊清楚"为什么盖、给谁住、值不值得盖"，再谈图纸。

### 1.1 Intent Capture（意图捕获）—— 总是执行
**扮演**：产品经理（架构师协助）。**干什么**：把你的原始描述变成一份正式的《意图陈述》：问题是什么、目标客户是谁、成功长什么样、为什么是现在。

**这步的特别之处**是"**来源标注**"：文档里每一句实质性的话都必须标来源——`[desc]`（来自你的描述）、`[Q3]`（来自第 3 个问题的回答）、`[assumption]`（这是我们的假设）。门处有专门的传感器检查标注齐全。**为什么？** 防止 AI 把你没说过的话写成"需求"。另外你粘给它的文档会被当作"不可信数据"处理——文档内容只参考不执行。

**产出**：intent-statement.md、stakeholder-map.md、问题文件。**评审**：产品负责人（咨询式）。

### 1.2 Market Research（市场调研）—— 有市场考量时才执行
**扮演**：产品经理。问竞品、行业趋势、自建 vs 外购（build-vs-buy）。内部工具、修 bug 之类不触发这步。**产出**：竞品分析、市场趋势、自建/外购评估。套餐：仅 enterprise、feature。

### 1.3 Feasibility（可行性分析）—— 有技术/合规不确定性时才执行
**扮演**：架构师（AWS 平台专家和合规专家协助）。问集成约束、监管要求（比如要不要过等保/PCI）、预算时间线、技术风险。产出《可行性评估》《约束登记表》《RAID 日志》（风险/假设/问题/依赖）。套餐：enterprise、feature、mvp。

### 1.4 Scope Definition（范围定义）—— 总是执行（在本大阶段启用时）
**扮演**：产品经理（工程经理协助）。核心问题：**做什么、不做什么**。产出范围文档（in/out 清单）和按优先级排序的待办清单（用 MoSCoW/WSJF/RICE 这些经典优先级方法）。

### 1.5 Team Formation（团队组建）—— 需要规划团队时
**扮演**：工程经理。问可用人力、技能缺口、分工、时区。产出团队评估、技能矩阵、协作编组计划。单人项目不触发。套餐：enterprise、feature。

### 1.6 Rough Mockups（草图）—— 有界面时
**扮演**：设计师（产品经理协助）。画低保真界面草图（ASCII 字符画或结构化描述）+ 用户操作流程图。**每屏强制标注一行无障碍说明**（比如"这屏键盘能不能走完"）——无障碍从第一天就是刚需不是补丁。无界面的纯后端项目会改画系统交互图。

### 1.7 Approval & Handoff（审批交接）—— 总是执行（在本大阶段启用时）
**扮演**：工程经理。**构思阶段的收尾**：把前面所有产出汇编成一份一页纸的《倡议简报》（意图、市场验证、风险、范围、团队、建议），跑第一次**大阶段边界验证**（检查构思阶段的承诺是否齐全），然后给你一个三选门：**批准进设计 / 要求修改 / 否决整个倡议（结束工作流）**。

## 7.2 大阶段二：Inception 需求与设计（9 步）

> 盖房子比喻：出图纸。需求细到"每面墙多高"，设计细到"哪根梁承重"。

### 2.1 Reverse Engineering（逆向工程）—— 仅棕地项目
**扮演**：开发者先扫描，架构师再综合（**流水线模式**：前者的产出直接交给后者加工）。分析已有代码库，产出 9 份文档：业务概览、架构、代码结构、API 文档、组件清单、技术栈、依赖、代码质量评估、扫描时间戳。

**特别之处**：这些文档存在 `codekb/` 里，**跨任务累积复用**。下次新任务时系统先检查代码有没有变：没变直接复用；变了问你——全量重扫还是只扫变化的部分？绿地项目整步跳过。

### 2.2 Practices Discovery（实践发现）—— 多数套餐执行
**扮演**：CI/CD 工程师主导，质量、开发、安全三个角色**各自独立**审查（互相看不到对方的意见，防止从众），最后由主导者汇总。

**干什么**：搞清楚"你们团队的开发习惯"——分支策略是什么、测试怎么写、怎么部署、代码风格如何。棕地项目从 git 历史和 CI 配置里推断；新项目给你看行业默认值让你确认。

**特别之处**：确认后的实践不会只存在本次任务里——你批准后，一个专门工具（`practices-promote`）会把它**提升写入团队规则文件**（team.md），从此对所有任务生效。而且规矩很硬：人类批准 + 工具提升**两个事实都齐全**，这步才算完成——防止"批了但没落实"。

### 2.3 Requirements Analysis（需求分析）—— 全部套餐都执行
**扮演**：产品经理。**这是整个流程最核心的步骤之一**。把你之前在构思阶段的回答和描述，变成正式需求文档：每条需求有永久编号（FR1、FR2 是功能需求；NFR1、NFR2 是非功能需求比如性能安全）。

**特别强调的机制**：
- **矛盾检测是强制的**：你的回答之间如果有冲突（比如"要极简"但"要支持 100 种自定义"），它必须指出来问你，不许自己悄悄选一个；
- **生成前确认是强制的**：所有问答结束后先给你一份汇总，你确认"理解无误"才生成正式文档；
- **绝不重问**：它会通读所有历史问题文件，问过的不问第二遍。

**产出**：requirements.md（全部套餐的骨架文档）。**评审**：产品负责人。

### 2.4 User Stories（用户故事）—— 有用户功能时
**扮演**：产品经理主导 + 设计师/开发/测试**圆桌会议**（mob 模式——唯一用这个模式的步骤）。产出标准格式的用户故事（"作为 <角色>，我希望 <功能>，以便 <价值>"），每个故事带验收标准（"Given 用户已登录，When 点导出，Then 5 分钟内收到文件"这种 Given/When/Then 格式）。

**圆桌的规矩**：三个协助角色互盲地各自提意见写在文件里；产品经理汇总；**有分歧时分两类处理**——"判断题"（比如这个功能要不要砍，双方都有道理）停下来问你；"知识题"（比如这个技术行不行得通）让持异议者再讨论一轮，最多两轮。谈不拢的异议会**原样记录**在最终成果里给你看，不许悄悄抹掉。

**产出**：stories.md、personas.md（用户画像）、traceability.json（需求→故事对照表）。**评审**：产品负责人。

### 2.5 Refined Mockups（精化原型）—— 有界面且前面画过草图时
**扮演**：设计师。把草图升级成中高保真原型 + 交互规格（每个组件什么状态、什么行为）+ 设计系统映射 + 无障碍合规清单。如果套餐跳过了构思阶段（比如 classic 档），这步会直接从需求和故事开始设计——**绝不编造没做过的草图的内容**。

### 2.6 Domain Design（领域设计）—— 需要新建组件时
**扮演**：架构师（AWS 平台、设计师协助）。把系统拆成**逻辑组件**：注意组件指"你要写的代码"——数据库、缓存、第三方 API 是依赖不是组件。这步不决定部署细节，只决定逻辑边界。

产出组件目录（同时有机器可读的 YAML 块和人类可读的图）+ **ADR**（架构决定记录：每个重要决定记一条——背景是什么、选了什么、放弃了什么、为什么。ADR 是软件工程的经典实践，半年后"当时为什么这么设计"就看它）。

如果组件边界有多种合理方案，它会把 Option A/B 和推荐理由都摆出来**让你在门点选**，而不是自己定。**评审**：架构评审人。

### 2.7 Units Generation（工作单元生成）—— 在本大阶段启用时总是执行
**扮演**：架构师（工程经理协助）。把组件进一步打包成**可独立交付的工作单元**（U1、U2……），每个单元标类型（service/ui/library/packaging/spec）和复杂度（S/M/L/XL），并画出单元间的**依赖图**（谁依赖谁）。

**注意一个刻意的分工**：这步**只产出依赖关系，不推荐先做哪个**——"先做什么"是下一步（交付规划）的经济决策，不让技术依赖绑架交付顺序。

单元依赖图是机器可读的（YAML 块），后面并行开发的调度就靠它算；有传感器专门检查这张图格式正确、没有循环依赖。**产出前有一个"计划批准门"**（Approve Plan / Revise Plan）。**评审**：架构评审人。

### 2.8 Contract Design（契约设计）—— 单元间要通信或有对外 API 时
**扮演**：架构师（AWS 平台协助）。把单元之间的接口当**正式合同**来设计：谁提供、谁消费、什么机制（REST/消息/共享 schema）、归谁管、版本怎么演进、错误超时重试怎么办。

**为什么单独一步？** 模块间接口是系统最容易腐烂的地方——写死在正式契约里（OpenAPI/AsyncAPI 规格），后面各单元并行开发时才不会互相扯皮。哪怕只有一个单元但对外暴露 API，这步也要走，因为没有别的地方管对外 API。

### 2.9 Delivery Planning（交付规划）—— 在本大阶段启用时总是执行
**扮演**：工程经理（架构师协助）。**Inception 的收尾**：决定先做哪个 Bolt 后做哪个（可以偏离技术依赖顺序，但**偏离必须写理由**）、每个 Bolt 的完成标准（DoD）、人员分配、外部依赖。

门之后还有三个小决定：迭代方式（按步骤逐层做 vs 按单元逐个做完整）、人员模式（单人还是团队）、检查节奏。然后跑第二次**大阶段边界验证**（需求是否都追踪到了设计、单元是否定义齐全、计划是否批准）才进入开发。

## 7.3 大阶段三：Construction 开发（7 步）

> 盖房子比喻：施工。从这里开始，流程按"单元"逐个推进——每个单元都可能走一遍设计→代码→测试。

### 3.1 Functional Design（功能设计）—— 有业务逻辑要设计时
**扮演**：架构师（开发协助）。对每个单元设计：数据实体（长什么样、谁拥有）、业务规则（编号 BR1.1……）、工作流程和状态机。**注意：这是设计不是编码**——最多写 15 行伪代码示意，完整实现留给代码生成步骤。

**产出按单元类型裁剪**：spec 型单元（纯规范）不欠业务逻辑模型，ui 型单元多产出一份前端组件清单。traceability.json 记录"验收标准→业务规则"的对应。**评审**：架构评审人（对抗式）。

### 3.2 NFR Requirements（非功能需求）—— 有性能/安全等要求时
**扮演**：架构师（安全、合规、质量协助）。把"要快""要安全"这种虚话变成**量化指标**：p99 延迟多少毫秒、可用性几个 9、并发多少。编号有讲究：继承需求阶段的编号加子号（NFR4 → NFR4.1），保证追踪链不断。**评审**：架构评审人。

### 3.3 NFR Design（非功能设计）—— 上一步执行过才执行
**扮演**：架构师（AWS 平台协助）。为每条非功能需求设计具体方案：用什么韧性模式（重试/熔断/降级）、什么缓存策略、怎么横向扩展、怎么做可观测。还产出一份"逻辑组件图"（服务边界、故障域、爆炸半径）作为下一步基础设施设计的桥梁。**评审**：架构评审人。

### 3.4 Infrastructure Design（基础设施设计）—— 需要云资源时
**扮演**：AWS 平台专家（安全、合规协助）。设计部署架构、基础设施服务清单、监控方案、CI/CD 流水线。**产出风格是表格优先**（部署表、服务表、告警表），散文只用来写理由。 spec 型单元不触发这步。**评审**：架构评审人。

### 3.5 Code Generation（代码生成）—— 总是执行（每个单元一次）
**扮演**：开发者。**这是全流程把关最严的一步**，值得细看：

1. **先出施工方案**：读这个单元的全部设计文档，写一份《代码生成计划》——逐条列出要写哪些文件、每个文件对应哪个需求/故事、测试怎么写（测试方法论来自团队规则里的 Testing Posture，比如 test-after 或 TDD，由程序生成一份带哈希指纹的"测试契约"）；
2. **计划批准门**：方案给你过目，**你批准了才能写代码**。批准记录和计划内容绑定——你后来改了计划，旧批准自动作废，要重新批。有专门的钩子强制这一点：没批计划就动工作区代码，直接被拦；
3. **派工写代码**：指挥把任务派给开发者子会话（任务书开头两行是单元编号和测试契约哈希，子会话不许自己重新解读规则）；
4. **收尾记账**：写代码摘要 + 一份 `source-manifest.json`（**清单列出这次创建/修改的每一个源码文件**——引擎会校验：工作区里出现清单外的代码改动，拒绝完工）。

**产出**：计划、测试指令、代码摘要、traceability + 真正的源代码（写到工作区根目录）。**评审**：架构评审人审计划。

### 3.6 Build and Test（构建与测试）—— 总是执行（所有单元完成后一次）
**扮演**：质量负责人（安全协助）。汇总所有质量目标（功能需求、非功能指标、测试契约），实际执行构建和测试，产出《目标验证矩阵》：每个目标一行——预期是什么、实际是什么、证据在哪、过没过。**不许有"待验证"残留**。

**测试失败怎么办**——这是最能体现方法论纪律的地方，四级阶梯：
1. **就地修**（最多 2 次）；
2. **修不好就分类诊断 + 估算影响**——绝不许在没估算影响的情况下说"没办法了"；
3. **自治模式下可以有界回跳**：跳回代码生成步骤修（整个工作流最多 3 次，记录在案），回跳后要重新走计划批准；
4. **以上都不行就停下来问你**：带着影响估算给你选——带修复重试 / 接受失败 / 放弃。**放弃永远是你的决定，AI 无权替你放弃**。

### 3.7 CI Pipeline（CI 流水线）—— 需要建或改 CI 时
**扮演**：CI/CD 工程师。产出 CI 配置（buildspec、workflow YAML 等）、质量门定义。然后跑第三次**大阶段边界验证**：所有单元都构建测试过了吗？跨单元的追踪门过了吗？CI 质量门确实会执行记录的命令吗？过了才进入上线阶段。

## 7.4 大阶段四：Operation 上线运维（7 步）

> 盖房子比喻：交付入住。通水通电、装监控、给物业手册。

### 4.1 Deployment Pipeline（部署流水线）—— 需要建/改 CD 时
**扮演**：CI/CD 工程师。设计部署策略（蓝绿/金丝雀/滚动）、环境晋升链（dev→staging→prod）、生产审批流程、回滚手册、特性开关策略。

**降级处理很务实**：精简套餐（bugfix 等）不建基础设施时，它会去看你工作区里**真实存在**的部署配置来干活；Express 绿地项目实在没有可部署目标，就如实报告"此步不适用"跳过——**绝不编造**。

### 4.2 Environment Provisioning（环境开通）—— 需要开通云环境时
**扮演**：AWS 平台专家（安全、合规协助）。用开发阶段产出的 IaC（基础设施即代码）真正开通环境，然后逐项验证：网络配置对不对、密钥注入对不对、跨账户连通是否正常。安全角色做安全姿态核查。

### 4.3 Deployment Execution（部署执行）—— 前面就绪后
**扮演**：CI/CD 工程师（开发协助，数据库迁移会派给开发做）。部署前检查清单 → 推制品过流水线 → 冒烟测试 → 健康检查。产出部署日志、冒烟测试结果、健康检查报告。

### 4.4 Observability Setup（可观测性配置）—— 需要监控时
**扮演**：运维/SRE。配仪表盘、告警（带严重度和升级路由）、SLO/SLI 追踪、日志查询、链路追踪、异常检测。围绕"黄金信号"（延迟、流量、错误、饱和度）展开。Express 套餐没做基础设施设计时，从需求和部署证据推导最小监控面，推导不出来的问你——不编。

### 4.5 Incident Response（事件响应）—— 需要运维手册时
**扮演**：运维/SRE。分析最可能的故障模式，产出应急预案库、事件响应计划、升级矩阵（什么问题找谁）、自动化修复文档、灾难恢复程序、备份配置。问 RTO/RPO（能容忍停机多久、丢多少数据）。

### 4.6 Performance Validation（性能验证）—— 需要压测时
**扮演**：质量负责人。设计负载测试（稳态/峰值/突发流量），在类生产环境执行，用监控证据分析结果。产出压测计划与结果、瓶颈分析、扩容验证、容量规划建议、**NFR 验证矩阵**（每条性能指标：目标 vs 实测）。

### 4.7 Feedback & Optimization（反馈与优化）—— 收尾
**扮演**：运维（AWS 平台协助）。**整个工作流的最后一步**。SLO 达标分析、成本优化建议、配置漂移检测、运维自动化建议，以及一份《反馈文档》——把运维中的发现变成下一轮构思的输入。

最后的门是三个选项：**批准（工作流完成）/ 要求修改 / 开启新一轮构思**（持续迭代）。

# 第八章 八份工作规范（Protocols）白话

`.aidlc/aidlc-common/protocols/` 下的 8 份文件，是"每一步具体该怎么干"的详细规范。引擎在合适的时机会点名让 AI 加载对应规范。你不用背，但值得知道各自管什么：

## 8.1 stage-definition.md —— 步骤说明书的格式规范
规定 33 个步骤文件的写法：头部必须有哪些字段（负责角色、产出清单、上游依赖……）、每个字段什么含义。**它保证所有步骤说明书格式统一**，这样程序才能解析它们、算出依赖图。

## 8.2 stage-protocol.md —— 主规范（1242 行，最厚的一份）
所有步骤都遵循的通用规则，核心内容：

- **语音契约**：AI 跟你说话用什么词、不说什么词（见 6.5）；
- **提问规则**：问题怎么写进文件、选项怎么设计（A-E + 必带"Other"）、问多少个看套餐深度、**绝不重问已答的**、问题必须自解释（不许问"FR3 还对吗？"这种没头没尾的，要展开成完整句子）；
- **矛盾检测**：发现你的回答互相打架时必须指出来，四类必查（范围矛盾、风险矛盾、技术矛盾、时间线矛盾）；
- **审批门细则**：开门后必须立刻停等你回复；不许编新选项；同一阶段被拒 3 轮后出现 "Accept as-is" 逃生选项；
- **完成消息五段式**：宣告（带专属 emoji）→ 成果摘要表 → 评审意见 → 批准问题 → 批准后显示进度条；
- **学习仪式**：详见 12.4；
- **阶段仪式原子性**：一个步骤一旦开始，提问→产出→评审→学习→开门**一步都不能省**。"跳到某步"只跳过中间步骤，目标步骤的仪式照走。

## 8.3 stage-protocol-construction.md —— 开发阶段专属规范
开发阶段最复杂，单独成册：行走骨架怎么处理、自治模式怎么选（梯子提示只问一次）、代码生成失败怎么停、测试失败怎么回跳、按单元迭代怎么走、并行批次怎么管。技术细节在第十六章。

## 8.4 stage-protocol-ensemble.md —— 多角色协作规范
当一个步骤有多个角色参与时怎么协作（下一章详细讲四种模式）。核心原则：**角色之间永不直接对话，指挥是唯一的传话人**；每个协助角色的意见写在独立的"意见文件"里，**意见文件缺一个都不许开门**——这是程序检查的，不是自觉。

## 8.5 stage-protocol-governance.md —— 大阶段边界验证
三个关卡：构思→设计、设计→开发、开发→上线。每个关卡做一次"追溯审计"：上一阶段的承诺在这一阶段都兑现了吗（比如每条需求都追踪到设计了吗）？验证报告存盘，发现问题先给你看再继续。

## 8.6 stage-protocol-recovery.md —— 恢复与变更处理
两大类情况：
- **崩溃/重启/压缩后怎么接上**：按固定顺序读五个数据源重建现场（第十五章细讲）；
- **中途改需求怎么办**：分小改（当前步骤内直接改）、大改（影响已完成步骤，给你影响分析后批准后重跑）、范围改（回需求步骤重新规划）三级。**改之前先归档**旧版本到 `archive/` 目录。

## 8.7 stage-protocol-reviewer.md —— 评审员规范
评审怎么请求、怎么记录、评审员能看什么不能看什么（只能看自己负责的单元的文件，**跨单元偷看会被钩子拦下**）、评审意见怎么附着在文档上、对抗式和咨询式的区别。第十二章细讲。

## 8.8 stage-protocol-swarm.md —— 蜂群规范
自治模式下并行开发的完整流程：分叉工作区 → 并行开工 → 逐个验收 → 统一合并。第十六章细讲。

# 第九章 Scope 系统：11 个流程套餐逐个讲

## 9.1 套餐是什么、怎么看表

每个套餐定义两件事：**哪些步骤执行（EXECUTE）哪些跳过（SKIP）**、**什么深度**（问多少问题、写多详细的文档）。三个独立旋钮可以进一步微调：`--depth`（深度）、`--test-strategy`（测试量）、`--review`（评审强度上限）。

| 套餐 | 深度 | 走几步/33 | 适合什么 |
|---|---|---|---|
| **poc** | Minimal | 8 | 概念验证："这想法行不行"，最快出活 |
| **bugfix** | Minimal | 9 | 修 bug：逆向工程→定位需求→改代码→测→部署 |
| **express** | Minimal | 10 | 小特性快速通道：需求→代码→测→部署，无设计无评审 |
| **refactor** | Minimal | 10 | 重构：多了功能设计步骤（要保证行为不变） |
| **security-patch** | Minimal | 10 | 安全补丁：多了 NFR 需求步骤（安全要求） |
| **infra** | Standard | 13 | 纯基础设施变更：跳过代码生成，但做基础设施设计和 CI/CD |
| **mvp** | Standard | 23 | 最小可行产品：全流程但不做上线运维阶段 |
| **classic** | Standard | 26 | **默认档**：跳过构思阶段（相当于 v1 老版行为） |
| **workshop** | Standard | 26 | 教学/研讨：同 classic 但测试量最小 |
| **feature** | Standard | 33 | 完整新特性：全 33 步 |
| **enterprise** | Comprehensive | 33 | 企业级：全 33 步 + 最深文档 |

## 9.2 套餐怎么选定

优先级从高到低：
1. 你显式指定（`/aidlc --scope bugfix ...`）；
2. compose 定制（`/aidlc compose "任务"`）；
3. **关键词自动推断**：描述里带 "fix/bug/broken" 会命中 bugfix 档之类；
4. 环境变量 `AWS_AIDLC_DEFAULT_SCOPE`；
5. 默认 `classic`。

工作流一旦开始，**状态文件里记录的套餐说了算**——你重跑 `/aidlc` 不会改变它（防止中途漂移）。想改走 compose。

## 9.3 深度（depth）到底影响什么

- **提问数量**：Minimal 每步问 2-4 个、Standard 5-8 个、Comprehensive 8-12+。这是引导不是硬上限——该问清楚的还是会问；
- **文档详尽度**：Comprehensive 的设计文档章节更多；
- **测试量**（test-strategy 独立控制）：Minimal = 每条需求一个可验证测试 + 每组件一个快乐路径（约 5-15 个测试）；Standard/Comprehensive = 每组件 5-8 / 10-15 个，按 75/20/5 的测试金字塔（单元/集成/端到端）。

# 第十章 适配器：opencode 是怎么接入的

这章稍微技术一点，但理解它能帮你理解"为什么 opencode 版长这样"。

## 10.1 问题：opencode 没有"钩子配置文件"

Claude Code 有个 settings.json 可以注册钩子；opencode 没有。opencode 的扩展方式是**插件**：`.opencode/plugin/` 下的 TypeScript 文件会被 opencode 进程加载，插件可以监听各种事件（工具执行前/后、收到消息、会话空闲……）。

所以 AI-DLC 在 opencode 上需要一个**翻译器**：把 opencode 的事件翻译成核心钩子脚本能懂的调用。这就是 `aidlc-opencode-adapter.ts`（774 行，本目录唯一为 opencode 写的程序）。

## 10.2 适配器做的三件事

**① 事件翻译**。opencode 的每个关键时刻，适配器调用对应的核心钩子（用 bun 起一个子进程，把事件数据按 Claude Code 的格式喂进去）：

| opencode 事件 | 调用的核心钩子 | 干什么 |
|---|---|---|
| 收到你的消息（首次） | session-start | 建立会话档案 |
| 收到你的消息（每次） | record-human-turn | 记"人类在场" |
| 工具执行前 | 各种守卫钩子 | 拦截违规操作 |
| 写文件后 | write-audit-log + run-sensors | 记账 + 质量检查 |
| 会话空闲 | continue-workflow | "还有活没干完？提醒它继续" |
| 对话压缩前 | validate-state | 校验状态、留恢复面包屑 |

**② 命令安检**。opencode 配置里"框架命令免询问"是宽门（`bun .aidlc/tools/*` 都算）。适配器里有一个**手写的 shell 命令解析器**做窄门：只允许"一个 bun + 一个登记过的工具文件"这种形态——拼接命令、重定向、命令替换、`$()` 全部拒绝。为什么？防止有人（或 AI 被诱导）往 `.aidlc/tools/` 里写个恶意脚本然后借宽门执行。

**③ 空闲时"推一把"**。opencode 没有"阻止 AI 停下"的强制通道，只有"会话空闲"事件。所以当核心钩子说"工作流还没干完"时，适配器的做法是**给会话注入一条带特殊标记的提醒消息**，让 AI 接着干。特殊标记（`[aidlc-forwarding-nudge]`）保证这条合成消息不会被误记成"你说的话"。

## 10.3 bun 不在会怎样

适配器找不到 bun 时，所有钩子**静默失效**（不报错不阻塞）——这是刻意的"失败开放"设计：辅助功能缺失不应该让你没法用 opencode。但这也意味着引擎的强制力会消失，所以装好后先跑 `/aidlc --doctor` 确认钩子心跳正常。

# 第十一章 质量把关：传感器与评审员

## 11.1 传感器（Sensor）：6 个自动检查器

传感器是"自动质检"。每个是一份声明文件（检查什么文件、跑什么命令、超时多少）加一个实现程序。步骤文件里声明自己要哪些传感器。

| 传感器 | 白话：它查什么 | 什么时候跑 |
|---|---|---|
| **claim-sources** | 意图文档里每句实质性的话都标了来源吗？标的来源能对应上吗？ | 审批门 |
| **required-sections** | 文档包含规定的章节吗？单元依赖图格式对吗、有循环吗？ | 审批门 |
| **upstream-coverage** | 这步声明"我要参考上游的 X、Y"，产出里真的引用了吗？ | 审批门 |
| **traceability** | traceability.json 里有没有断链（需求没着落、产物没来源）？ | 写文件时 |
| **linter** | 代码过 eslint 吗？（项目没配 eslint 就静默通过） | 写代码文件时 |
| **type-check** | 代码过 TypeScript 类型检查吗？ | 写代码文件时 |

审批门触发的传感器可以是**阻塞**的：不通过不给开门。此时你有两个选项：修掉问题 / 显式覆盖（覆盖会留下审计记录）。**自治模式下没有覆盖选项**——无人值守时不许放水。

团队还可以在运行时新增传感器（学习仪式可以沉淀"以后都检查这个"为一条新传感器）。

## 11.2 评审员（Reviewer）：成果给你看之前先内审

两个专职评审角色：**产品负责人**（审需求/故事/原型，代表客户视角）和**架构评审人**（审一切设计文档，看健全性/可实现性/一致性）。它们**只评审不产出**。

**两种评审强度**：
- **adversarial 对抗式**（开发阶段默认）：评审员的出发点是"这肯定有毛病"，带着证据找茬——能跑工具验证就跑工具。找到问题 → 责任角色修 → 再审，最多 2 轮；
- **advisory 咨询式**（构思/设计阶段默认）：评审员只过一遍，意见按严重度排好**原样**附给你——这些阶段很多东西本来就是判断题，终审权在你。

**评审的硬规矩**：
- 评审员只能读**自己负责的那个单元**的文件——想跨单元偷看会被钩子拦下（防止评审被无关信息带偏）；
- 评审通过后再改产物？**被冻结钩子拦下**——因为那会让"已通过"的记录失效。要改就得重新评审；
- 评审请求和结果都记账（带文件内容的哈希绑定），事后能查"当时评审的是不是这个版本"。

## 11.3 学习仪式：团队越用越顺手

每个步骤完成后、审批门之前，固定一问："**这次有什么值得下次记住的吗？**"

你说"以后 API 文档必须先评审再实现"，接下来的事全由程序处理：
1. 工具把你这步的工作日记整理成候选经验列表；
2. **冲突检查**：这条经验跟组织级规矩（org.md）矛盾吗？矛盾就告诉你，让你修订或放弃——**小规矩永远不能推翻大规矩**；
3. 确认后写进 `team.md` 或 `project.md`（带日期和内容哈希，崩溃重试不会重复写）；
4. 记一条审计（RULE_LEARNED）。

从此这条经验在每次会话都在场（规则文件被 opencode 配置自动注入上下文）。这就是"自学习"——不训练模型，而是**把经验沉淀成规则文本**。

# 第十二章 14 个角色与四种协作模式

## 12.1 为什么一个 AI 要扮演 14 个角色

不是 AI 有 14 个脑子——是同一个模型轮流换"人格"。好处有三个：

1. **专注**：评审员人格只挑刺、开发者人格只写码，防止"自己写的代码自己夸"；
2. **知识隔离**：每个角色有自己的参考书（`.aidlc/knowledge/<角色>/`），只在扮演时加载，不用把所有知识塞满上下文；
3. **可分工**：角色文件里声明了它能不能用子会话（opencode 里是 subagent），指挥按这个分派任务。

## 12.2 角色清单（按你接触频率排序）

**你打交道最多的（主会话直接扮演）**：

| 角色 | 它是谁 | 出现在哪 |
|---|---|---|
| conductor（指挥） | 运行 /aidlc 的主会话，不是正式角色文件但是最核心存在 | 全程 |
| product-agent（产品经理） | 需求、故事、范围、可行性 | 构思、需求步骤 |
| engineering-manager（工程经理） | 团队、交付计划、部署策略、阶段收尾 | 团队组建、交付规划 |
| developer-agent（开发者） | 设计实现、写代码、改 bug、升级依赖 | 功能设计、代码生成 |

**常在子会话里干活的**：

| 角色 | 干什么 |
|---|---|
| aws-platform-engineer（AWS 平台工程师） | 云架构设计、基础设施选型（不依赖 AWS 凭证也能干活） |
| quality-agent（质量负责人） | 测试策略、质量目标验证、性能验证 |
| devops-sre-agent（运维/SRE） | 监控告警、SLO、应急预案、成本优化 |
| cicd-agent（CI/CD 工程师） | 构建与部署流水线、CI 质量门 |
| security-agent（安全工程师） | 威胁建模（STRIDE 方法）、安全设计、渗透测试指导 |
| compliance-agent（合规专家） | 数据分类、监管要求（HIPAA/PCI/等保之类）映射 |
| designer-agent（设计师） | 用户流程、线框图、交互规格、无障碍 |

**评审与规划**：

| 角色 | 干什么 |
|---|---|
| product-lead（产品负责人·评审） | 对抗式审需求类产物（也主持知识导入评审） |
| architecture-reviewer（架构评审人） | 对抗式审设计类产物（最广的评审面） |
| adaptive-planner（自适应规划师） | 只在 compose 模式出现，评估复杂度、设计定制流程 |

每个角色的详细人格在 `.aidlc/agents/<名字>.md`（通用格式，引擎认这个）和 `.opencode/agents/aidlc-<名字>.md`（opencode 格式）。注意：**adaptive-planner 只有通用格式**——它由指挥用 Task 工具动态调用，不进 opencode 的角色注册表。

## 12.3 四种协作模式（拓扑）

步骤说明书里有个 `topology` 字段决定这一步怎么协作：

- **inline（内联，29 步）**：指挥在主会话里直接扮演角色干活。最常用——大多数步骤就是"一个角色唱主角"；
- **subagent（子会话，2 步）**：指挥把活派给一个子会话，子等命令（比如逆向工程第一步，开发者子会话扫完代码库回来交结果）；
- **pipeline（流水线，1 步）**：A 角色的产出**直接作为** B 角色的输入，接力完成（逆向工程：开发者扫描 → 架构师综合）；
- **mob（圆桌，1 步）**：用户故事步骤专用——产品经理主持，设计师/开发/测试**互盲**地各自写意见，然后汇总。互盲是刻意的：防止先发言的人带偏后面的人。

## 12.4 协作的三个硬规矩

1. **角色之间永不直接对话**——一切经过指挥（总线模式）。你在对话里能看到每一次协作的来龙去脉；
2. **意见文件缺一不可**——某步骤声明了三个协助角色，就必须有三份意见文件。程序检查，不是自觉。没齐不许开门；
3. **分歧不抹平**——圆桌里谈不拢的异议**原样记录**进最终成果给你看。评审员不同意主导者的结论？异议也留痕。

# 第十三章 17 个钩子与工具全家桶

## 13.1 为什么需要钩子

工具是"AI 主动调用的"（比如问引擎下一步）；钩子是"事件自动触发的"（AI 写了个文件 → 自动记账）。**AI 不需要知道钩子存在，钩子照样工作**——这就是"规矩不靠自觉"的实现。

## 13.2 钩子逐个白话（按触发时机分组）

**会话生命周期（4 个）**：
- `session-start`：会话开始 → 建会话档案（读规则文件、确认 bun 可用）；
- `session-end`：会话结束 → 归档（**注意：opencode 没有"会话结束"这个事件时刻，所以这个钩子在 opencode 上不触发**——它存在于核心目录是因为其他 harness 有；opencode 上靠压缩前校验和下次启动恢复兜底）；
- `pre-compact-validate-state`：对话太长要被压缩前 → 校验状态文件健康、写一个"恢复面包屑"（下次新会话靠它快速重建现场）；
- `record-human-turn`：每次你发消息 → 记"人类在场"（审计事件 HUMAN_TURN），并**守住目录完整性的最后一道防线**——有人把工作档案删了？在这里补建。

**写文件后（2 个）**：
- `write-audit-log`：AI 每写一个文件 → 自动记一条审计（FILE_CREATED/MODIFIED，带文件内容哈希）；
- `write-run-sensors`：写完文件 → 如果这一步声明了传感器，自动跑（traceability/linter/type-check 三个是这里触发的）。

**工具调用前的守卫（8 个）**——这是"强制执行"的主力：
- `guard-state-mutation`：想直接改状态文件？拦下——状态只能经工具改；
- `guard-readonly-session`：compose 模式下想写文件？拦下——规划器只能读；
- `guard-conductor-write-scope`：指挥想越权写到别的单元目录？拦下；
- `guard-reviewer-file-scope`：评审员想读自己负责单元之外的文件？拦下；
- `guard-artifact-freeze`：评审通过后想再改产物？拦下（要先解冻重审）；
- `guard-dod-verification`：想标记"完成标准已验证"？拦下——验证记录要程序写入；
- `guard-code-generation`：没批准施工方案就想写代码？拦下；
- `guard-stage-boundary`：没完成当前步骤仪式就想推下一步？拦下。

**工作流推进（3 个）**：
- `stage-report-audit`：`report` 命令汇报结果时 → 记审计 + 推进状态；
- `gate-response-audit`：你在门口做决定时 → 记审计（APPROVED/REVISION_REQUESTED/OVERRIDE……）；
- `continue-workflow`：会话空闲时 → 检查"还有活没干完？"有就提醒继续（opencode 版由适配器注入提醒消息实现）。

## 13.3 工具全家桶（50+ 个，按功能分组）

不需要背，知道"有这么个工具"即可，用时现查：

**调度与状态（核心 3 个）**：`orchestrate`（调度引擎）、`state`（状态读写）、`audit`（记账与查询）。

**工作流管理**：`compose`/`recompose`（定制流程）、`park`/`resume`（暂停恢复）、`intent`（意图档案管理）、`jump`（跳步）、`record-history`（把旧项目的流程记录回放进来）。

**质量与评审**：`run-sensors`（手动跑检查）、`review`（评审请求/记录）、`learnings`（经验沉淀）、`conflict-check`（规则冲突检查）、`traceability`（追踪链查询）。

**知识库**：`codekb`（代码知识库扫描/复用判断）、`documentkb`（文档知识库导入/检索）、`team-knowledge`（团队知识沉淀）。

**开发阶段**：`bolt`（构建冲刺管理）、`swarm`（蜂群调度）、`worktree`（并行工作区）、`merge`（统一合并验收）、`testing-contract`（测试契约生成）、`dod`（完成标准验证）、`source-manifest`（代码改动清单校验）。

**规则系统**：`memory-init`（规则种子安装）、`memory-read`（分层读取规则）、`practices-promote`（实践提升为团队规则）。

**回顾与报表**：`runtime-graph`（统计汇总）、`session-cost`（成本估算，查模型价格表）、`replay`（工作流回放）、`outcomes-pack`（成果打包）。

**自检**：`doctor`（体检）、`version`（版本）、`heartbeat`（钩子心跳写入）。

**插件开发**：`plugin-scaffold`/`plugin-validate`/`plugin-pack`（扩展开发三件套，第十九章）。

所有工具的共同特征：**输入输出都是结构化 JSON、错误有明确格式、修改状态前先校验**。它们彼此独立，但共享一份"数据模型"（`tools/data/` 里的静态文件）。

## 13.4 `tools/data/` 静态数据

- `stage-graph.json`：33 步骤依赖图（编译产物，**不要手改**，源在 stages/ 的说明书里）；
- `scope-grid.json`：11 套餐 × 33 步骤的执行/跳过矩阵；
- `model-pricing.json`：模型单价表（session-cost 用）；
- `event-taxonomy.json`：91 种审计事件的分类（22 大类）。

技能是"写给 AI 看的操作手册"。你直接用的很少，大多数是引擎和指挥内部调用的。

# 第十五章 状态、审计与恢复：它为什么"不会失忆"

## 15.1 五个数据源（按权威顺序）

恢复现场时按固定顺序读：

1. **stage-graph.json**：静态流程图（不会变）；
2. **aidlc-state.md**：当前进度（每步打勾没）——**唯一权威进度源**；
3. **audit/ 账本**：发生过什么（只增不删）；
4. **各步骤产物文件**：需求文档、设计文档等实际成果；
5. **session-journal.md**：会话日记（叙事性记录，"当时怎么想的"）。

**为什么状态文件是唯一权威？** 因为"进度"只能有一个说法。账本告诉你"发生了什么"，状态文件告诉你"现在算到哪了"。两者可能短暂不一致（比如刚记了账还没更新状态），恢复程序知道怎么调和。

## 15.2 审计日志的三个设计

- **AI 不许自己写**：所有审计条目由工具/钩子在状态变化时自动写入。AI 能"宣布"什么和"记录了"什么之间没有空隙——它说批准了，账本里就有 APPROVED；账本里没有，就是没批；
- **哈希绑定**：关键条目绑定文件内容哈希——"3 月 15 日批准的需求文档"和"今天的需求文档"是不是同一个版本，一算哈希就知道；
- **91 种事件类型**：分 22 大类（GATE、STAGE、SENSOR、RULE、SWARM、COMPACT……），查询时可以按类别过滤。

## 15.3 三种"失忆"场景的恢复

**场景 A：对话被压缩**（最常见）。压缩前钩子已校验状态 + 写了面包屑。压缩后 AI 从面包屑 + 状态文件重建现场，无缝继续。你基本无感。

**场景 B：重启/换电脑**。打开项目目录，输入 `/aidlc`（不带参数也行）——session-start 钩子探测到 `aidlc-state.md` 里有未完成的工作流，呈现菜单：**继续 / 重做当前步 / 跳到某步 / 重新开始**。

**场景 C：工作档案被删/损坏**。`record-human-turn` 钩子是最后防线：探测到目录缺失就补建骨架；状态文件损坏就跑 `doctor` 诊断，按提示修复（极端情况从账本重放重建状态——账本只增不删，是最后的真相）。

## 15.4 暂停（park）的正确姿势

别在步骤中间硬关窗口——说"先停一下"，它会：
1. 找一个干净边界（当前步骤仪式完成或明确暂停点）；
2. 把进度、上下文摘要、下一步该干嘛写进 park 存档；
3. 账本记 PARKED。

恢复时 `/aidlc --resume`：读存档 → 校验期间有没有人动过产物（哈希比对）→ 从存档点继续。动过就告诉你"你暂停期间这些文件变了"，让你决定怎么办。

# 第十六章 Construction 深入：开发阶段怎么运转

开发阶段是整个系统机制密度最高的部分，值得单独一章。

## 16.1 两种迭代方式

交付规划步骤末尾你会二选一：

- **按步骤迭代（stage-wise）**：所有单元先一起过功能设计，再一起过 NFR……逐层推进。适合单元间耦合紧的系统；
- **按单元迭代（unit-wise）**：一个单元走完全部设计→代码→测试，再开下一个。适合单元独立性强的系统。

## 16.2 行走骨架（Walking Skeleton）

团队规则里可设三档：`always`（每个项目先搭骨架）、`never`、`auto`（AI 判断，但建议你批准）。

骨架 = 第一个 Bolt 做一个"全链路打通但极薄"的版本：一个接口从 UI 调到数据库再回来，功能简陋但**证明整条技术栈能跑通**。它的价值是**最早暴露集成风险**——别等到三个月后才发现前端和后端的数据格式对不上。

骨架交付后触发**自治模式选择**（见下）。

## 16.3 自治模式：梯子提示

骨架批准后（或开发阶段开始时），只问一次的"梯子提示"：

1. **Continue autonomously（自动跑）**：剩下的 Bolt 自动连续执行，只有出错/完成才停；
2. **Gate every Bolt（每个都停）**：每个 Bolt 完成都开门等你批准。

选一次管整个开发阶段。**自治模式下的差异**：传感器失败没有"覆盖"选项（无人值守不放水）；代码生成失败会按阶梯自动处理（就地修→回跳→停）；蜂群可能被启用。

## 16.4 蜂群（Swarm）：并行开发

自治模式 + 依赖图允许时，引擎可能发出 `invoke-swarm` 指令：

1. **分叉**：`worktree` 工具为每个可并行的单元建独立 git 工作目录（互不干扰）；
2. **并行开工**：每个单元一个开发者子会话，任务书带单元编号和测试契约哈希；
3. **逐个验收**：子会话完成后，`merge` 工具统一验收——跑传感器、查评审记录、校验 source-manifest（清单外的代码改动拒绝）；
4. **合并回主干**：验收通过才合并，冲突时停下来给你看。

**你全程不需要操作 git**——但你能在账本里查到每一次分叉、验收、合并的记录。

## 16.5 测试契约（Testing Contract）

代码生成前，`testing-contract` 工具根据团队规则里的 Testing Posture（测试姿态）生成一份契约：这个单元要写哪些测试、用什么方法论（test-after/TDD）、覆盖率要求。契约带**哈希指纹**：

- 任务书开头必须引用这个哈希——子会话不许自己重新解读测试规则；
- 构建测试步骤验证"实际写的测试"和契约对得上——**测试缩水会被发现**。

## 16.6 完成标准（DoD）

每个 Bolt 有完成标准（交付规划时定的）。验证记录由 `dod` 工具程序写入——`guard-dod-verification` 钩子拦着，AI 不能自己宣布"达标了"。

## 16.7 失败处理全景

把开发阶段所有失败路径摆在一起看：

| 失败 | 处理 |
|---|---|
| 代码生成子会话出错 | 自治模式：自动重试/回跳（≤3 次）；非自治：停下来问你 |
| 测试失败 | 就地修 ≤2 次 → 分类诊断+影响估算 → 有界回跳 → 升级给你（带选项） |
| 传感器不通过（门处） | 修复 / 显式覆盖（自治模式无覆盖） |
| 评审不通过 | 责任角色修 → 重审（≤2 轮）→ 仍有异议则原样呈现给你 |
| 审批门被拒 3 轮 | 出现 Accept as-is 逃生选项 |
| 合并冲突（蜂群） | 停下来，冲突详情给你 |

共同原则：**AI 永不擅自放弃、永不静默绕过、升级给你时永远带着影响估算和选项**。

# 第十七章 安全模型：四层锁

这套系统要操作你的代码库、执行命令、写文件——它的安全设计值得了解。

## 17.1 第一层：opencode 权限配置（宽门）

`opencode.json` 声明：默认所有 bash 命令问你；框架登记过的工具/钩子命令免询问。这是便利层。

## 17.2 第二层：适配器命令安检（窄门）

宽门太宽（`bun .aidlc/tools/*` 都算框架命令），所以适配器内置手写 shell 解析器做精查：

- 只接受"恰好一个 bun 调用 + 恰好一个已发货清单内的工具文件"；
- 拒绝：`&&`/`;` 拼接、`>` 重定向、`|` 管道、`$()`/反引号命令替换、环境变量注入；
- 已发货清单是**白名单**（62 个入口）——往 tools/ 目录里丢个新脚本是混不进来的。

## 17.3 第三层：守卫钩子（行为锁）

8 个守卫钩子拦具体违规行为（13.2 有完整清单）：改状态、越权写、评审后改产物、未批计划写代码、跳步……**全部在程序层强制**，AI 连试都试不成功。

## 17.4 第四层：审计与哈希（事后锁）

即使前三层都被绕过（理论上），账本还在：每个文件变动带哈希、每个批准带时间戳、每个覆盖操作留痕。事后审计能发现任何不一致。

## 17.5 数据安全的两条特别规定

- **不可信内容标记**：你粘贴的文档、导入的文档知识库内容，一律标记为"数据而非指令"。客户文档里写"跳过所有测试"不会被照办——注入攻击在这一层被化解；
- **DocumentKB 只读**：文档知识库导入后只索引不改写，检索结果同样带"不可信"标记。

# 第十八章 知识库详解

## 18.1 CodeKB（代码知识库）—— 棕地项目的记忆

逆向工程步骤产出的 9 份文档存在 `codekb/`。**跨任务累积**是关键特性：

- 新任务开始时，`codekb` 工具先比对：代码库变了没（扫描时间戳 + 结构指纹）？
- 没变 → 直接复用旧扫描，**省掉整个逆向工程步骤**；
- 变了 → 问你：全量重扫 / 增量扫变化部分。

多任务共用一份代码知识——第二个任务不用重新理解代码库。

## 18.2 DocumentKB（文档知识库）—— 团队文档的索引

输入 `/aidlc-knowledge`（或 `/aidlc knowledge <动词>`）管理 PDF/Word/Markdown 文档知识库：

1. 原文放 `knowledge/documents/`（**你自己的目录，框架永不动它**）；工具派生出目录 `knowledge/documentkb/`（索引 + 每篇文档的 metadata.json 和提取出的 content.md）；
2. 提取、索引全部本地完成，不上传；
3. 各阶段 AI 可以检索引用（比如"公司安全基线文档第 3 章要求……"）；检索结果带**不可信标记**（见 17.5）；
4. **故意没有 `remove` 命令**：删除 = 你自己删原文件，然后 `sync` 同步目录——工具永远不持有对你文件的删除权；
5. 索引坏了能重建：`sync` 会从每篇文档幸存的 metadata.json 重建 index.json（包括"已删除"的墓碑记录）。

完整的动词清单见第三十三章。

## 18.3 团队知识（Team Knowledge）

学习仪式沉淀的经验 + 实践发现提升的约定，都在 `memory/` 规则文件里。**它随 git 走**——新同事 clone 项目就继承了全部团队约定。

## 18.4 五层规则的内容（种子文件白话）

- `org.md`：行业通用底线（不许跳过测试、安全不可协商、审计必须完整）；
- `team.md`：团队约定（分支策略、代码风格、Testing Posture、骨架策略）；
- `project.md`：本项目特殊（技术栈决定、性能预算、合规范围）；
- `phases/*.md`：大阶段规则（比如"开发阶段所有单元必须走 code review"）；
- 步骤级：个别步骤的特殊规则。

查看当前生效规则：`bun .aidlc/tools/aidlc-memory-read.ts`。

# 第十九章 插件开发：给 AI-DLC 加新步骤

框架本身可扩展。想加一个自定义步骤（比如"法务审查"）：

1. `bun .aidlc/tools/aidlc-plugin-scaffold.ts <插件名>` —— 生成插件骨架（目录 + 模板）；

# 第二十一章 场景手册：常见情况怎么用

## 21.1 修 bug
`/aidlc-bugfix 用户导出 CSV 时中文乱码` → 9 步精简流程：逆向（如已有 CodeKB 则跳过）→ 定位需求 → 改代码 → 测试 → 部署。Minimal 深度，问题少、动作快。

## 21.2 加个小功能

## 21.3 正经新功能

## 21.4 拿不准该用哪个套餐
`/aidlc compose "给系统加实时通知"` → 规划器评估后给你定制清单 + 推荐理由，你批了才生效。

## 21.5 老项目第一次用
先 `/aidlc --doctor` 自检 → `/aidlc 帮我梳理这个项目并加个小功能` → 它会自动走棕地路线（逆向工程 → CodeKB）。

## 21.6 中途改需求
直接说："等等，导出功能不要 CSV 了，要 Excel。"它会：判断影响面 → 影响已完成步骤就给你影响分析 → 你批准 → 归档旧产物 → 重跑受影响步骤。

## 21.7 想跳过某步

## 21.8 看看花了多少钱
`/aidlc-session-cost` → 从账本统计 token 用量 × 模型单价表。

## 21.9 工作流跑了一半想看看过程
`/aidlc-replay` → 从账本重建完整时间线：什么时候干了什么、谁批的、传感器结果如何。

## 21.10 项目收尾要汇报
`/aidlc-outcomes-pack` → 打包成果总结：交付了什么、走了哪些步骤、经验沉淀了哪些、指标如何。

# 第二十二章 常见问题（FAQ）

**Q：流程会不会太重？我就改一行代码。**
不会。bugfix/express 档只有 9-10 步且 Minimal 深度，提问极少。而且 compose 可以进一步裁。流程的价值恰恰在"可裁剪"——重的是企业级项目，轻的是小改动。

**Q：AI 会不会背着我做什么？**
机制上很难：状态只能程序改、批准只能你给、账本 AI 不能写、守卫钩子拦越权。你最需要做的只是：**认真看每个审批门再回 1**。

**Q：它问的问题太多了怎么办？**
三个办法：套餐降深度（`--depth minimal`）、用 self-guided 模式自己编辑问题文件、或直接说"剩下的问题你来定，我相信你"（授权只对本步有效）。

**Q：我不喜欢它选的架构/技术栈怎么办？**
设计步骤的门点会摆方案给你选；已经批了想改，直接说，走修订循环或影响重跑。所有决定都有 ADR 记录，改起来有据可查。

**Q：中断了/崩了/手滑关了窗口怎么办？**
重开项目目录，输 `/aidlc`。它会探测到未完成工作流给你恢复菜单。账本只增不删，进度丢不了。

**Q：团队规则跟我的想法冲突怎么办？**
规则是五层叠加的，下层的合理诉求可以走学习仪式沉淀；和组织级底线（org.md）冲突的会被冲突检查拦下——那时你要么修订想法，要么找规则的所有者谈。

**Q：aidlc/ 目录好大，都要提交 git 吗？**
tmp 和 worktree 不用（.gitignore 已配），其余都提交——这是项目的"过程资产"，也是追溯能力的基础。

**Q：不用 AWS 能用吗？**
能。AWS 平台工程师角色只管"云架构设计"这件专业事，不依赖 AWS 凭证。你的项目部署到哪都行。

**Q：支持什么语言/框架？**
方法论本身语言无关。传感器里的 linter/type-check 目前覆盖 JS/TS 生态；其他语言的检查可以在学习仪式里沉淀成自定义传感器。

**Q：这和直接让 AI 写代码比，慢多少？值吗？**
小改动几乎不慢（精简档）；大项目前期慢（问需求、做设计），但省的是后期的返工、扯皮和"这系统怎么搭的没人知道"。AI-DLC 的赌注是：**大项目的成本在后期，前期投入是赚的**。

# 第二十三章 心智模型总结：十句话记住 AI-DLC v2.0

1. **流程在程序里，不在 AI 脑子里**——引擎决定下一步，AI 只执行；
2. **每个步骤一道门，钥匙在你手里**——没有你的批准，什么都不会流向下一阶段；
3. **AI 不许记账**——账本由程序写，所以账本可信；
4. **提问走文件**——聊天记录会丢，问题文件永存；
5. **评审员只挑刺不干活**——产出的和审查的永不同一个人格；
6. **规则五层叠加**——小规矩不能推翻大规矩，经验靠仪式沉淀；
7. **套餐可裁剪**——修 bug 和做企业系统不走同一条路；
8. **追溯链贯穿始终**——每条需求能追到代码和测试；
9. **失败有阶梯**——就地修→回跳→升级给你，AI 永不擅自放弃；
10. **失忆有恢复**——状态文件 + 只增账本 + 面包屑，中断不可怕。

## 23.1 推荐学习路径

1. 读本文第一~四章（概念 + 上手）；
2. 拿一个小项目实跑一遍 `/aidlc`（建议 feature 或 classic 档）；
3. 跑的过程中对照第七章理解每个步骤在干嘛；
4. 遇到具体问题查本文对应章节；
5. 要深挖字段级细节时，翻同目录的 `AIDLC-PLUGIN.md`（技术参考手册）；
6. 想扩展框架时读第十九章 + `stage-definition.md` 规范。

# 第二十四章 提问与审批：交互层的完整细节

这章把"它会怎么问你、你该怎么答"讲到最细——因为这是你 90% 的交互界面。

## 24.1 问题文件的完整解剖

每个步骤的提问都落在 `aidlc/spaces/default/intents/<名字>/<阶段>/<步骤>/<步骤>-questions.md`。文件内部结构：

```markdown
## Q1: 这个工具的主要使用者是谁？

**Context**: 这决定了功能优先级和界面复杂度。
**Options**:
- A) 个人用户 — 自己管理自己的待办
- B) 小团队 — 多人共享任务列表
- C) 企业 — 需要权限和审计
- D) Other — describe what you want instead

[Answer]:

## Q2: ...
```

**关键规矩**：
- 每个问题必须有 `**Context**` 字段——告诉你"为什么问这个"，不是干巴巴的审问；
- 选项最多到 E，**永远有 Other**——它不能把你锁进预设答案里；
- `[Answer]:` 标签是你回答落盘的地方。**文件是事实源**：聊天里说过但文件里没写的答案，不算数；
- 新问题**追加**在文件末尾，已答的绝不重问（它会先通读全部历史问题文件）。

## 24.2 聊天里的渲染规则

问题在聊天里显示时：

- 一次只问**一个**（或强相关的一小组），不刷屏；
- 选项重新编号为 1/2/3……（文件里的 A/B/C 映射过来）；
- 问题必须**自解释**：不许问"FR3 还要保留吗？"——要展开成"FR3（用户可导出 CSV）这条需求还要保留吗？"，因为你可能不记得 FR3 是什么；
- 你回个数字就行；回一段自己的话也行（它会理解并写回 Other）。

## 24.3 三种答题模式详解

| 模式 | 怎么进入 | 适合谁 |
|---|---|---|
| **guided**（默认） | 它一条条问，你一条条答 | 大多数人，尤其第一次用 |
| **self-guided** | 你说"我自己填" | 喜欢一口气想清楚的人。它生成问题文件后你直接编辑 `[Answer]:`，改完说声 done |
| **chat** | 你说"咱们聊着来" | 发散讨论阶段。自由聊，它负责把结论整理写回问题文件 |

模式可以中途切换。所有模式殊途同归：**答案最终都在文件里**。

## 24.4 汇总确认：生成前的最后一道闸

所有问题答完后，它**不许直接**生成正式文档。必须先给你一份汇总：

```
## Summary of Your Answers

1. 主要使用者：个人用户（Q1）
2. 数据存储：本地 SQLite（Q2）
3. 必须有的功能：增删改查、按日期筛选（Q3）
……

**Does this look correct?**
1. **Looks correct** — proceed
2. **Request changes** — tell me what to fix
```

你确认（1）之后，它才动笔写 `requirements.md`。你选 2，就回到对应问题重答。

**为什么有这道闸？** 因为"逐条问答"和"整体理解"是两回事——单条都对，合起来可能不是你要的。这道闸防的是"每个回答都对，但拼出来不是你要的东西"。账本里有专门事件（SUMMARY_CONFIRMATION_RECORDED）记录这次确认。

## 24.5 审批门的完整解剖

每个步骤的完成消息是**五段式**，顺序固定：

```
🎯 **Stage Complete: Requirements Analysis**     ← ① 宣告（每个步骤有专属 emoji）

| Artifact | Path | Status |                     ← ② 成果摘要表
|---|---|---|
| Requirements | .../requirements.md | Created |
| Traceability | .../traceability.json | Created |

**Review (Product Lead — advisory)**             ← ③ 评审意见（如有评审员）
- [Medium] NFR2 的性能指标不可测量，建议量化
- [Low] FR5 与 FR7 的边界可以更清晰

**Approval** — Requirements Analysis complete.   ← ④ 批准问题
How would you like to proceed?
1. **Approve** — Continue to User Stories
2. **Request Changes** — Provide revision feedback
3. **Other** — describe what you want instead

（你批准后）                                    ← ⑤ 进度显示
▓▓▓▓▓▓░░░░░░░░░░░░░░ 6/33 stages · Inception 2/9
```

**铁律（违反任一都是 bug）**：
- 开门后必须**立刻停**——不许"顺便"开始下一步；
- 不许在 1/2/3 之外发明新选项（比如"4. 跳过后面所有门"是不允许的）；
- 你回 2 之后的**修订循环**：说哪里不满意 → 它改 → **产物变了就必须重新评审** → 再开门。改了不重审是作弊，钩子会拦；
- 同一步连续被拒 **3 轮**，选项里多一个 **Accept as-is**（带着已知问题往前走，记录在案）——防止无限返工死循环；
- "你看着办"式的授权 = **本步这一次**有效，下一步重新问。不存在"全权委托"按钮。

## 24.6 计划批准门（开发阶段特有）

代码生成的施工方案门和普通门不同：**批准记录和计划内容哈希绑定**。你批准的是"这个版本"的计划——它后来改了计划（哪怕一个字），旧批准作废，必须重新批。这就是为什么"AI 偷偷改了方案再执行"在机制上不可能：执行前钩子会校验哈希。

账本里有专门事件：`PLAN_APPROVAL_RECORDED`（批了）/ `PLAN_APPROVAL_BLOCKED`（未批就动手，被拦）。

## 24.7 你可以在门口说的所有话

- `1` / "批准" / "approve" / "LGTM" → 通过；
- `2` / "改一下 X" → 修订循环；
- `3` / 任何其他话 → 按你的意思处理；
- "跳过这一步" → 触发 recompose 确认门（跳过也是你的决定，要留痕）；
- "先停一下" → park；
- "这步不用问我了，直接过" → 本步自动通过（仅此一次）。

# 第二十五章 审计事件全景：账本里到底记了什么

账本（`audit/audit.md`）是一串只增的事件块，每块形如：

```
- **Event**: GATE_APPROVED
  **Timestamp**: 2026-09-08T12:20:33.121Z
  **Stage**: requirements-analysis
  **Hash**: 9f2c…（内容哈希）
```

全部事件类型按主题分组白话如下（共 84 种，均在 `aidlc-audit.ts` 中定义）。**你不需要记，需要查账时按这个表对照**：

## 25.1 工作流与会话（13 种）
`WORKFLOW_STARTED / COMPLETED / PARKED / UNPARKED`（工作流起止停续）、`SESSION_STARTED / RESUMED / COMPACTED / ENDED`（会话生命周期）、`HUMAN_TURN`（你说过话——证明"人类在场"）、`WORKSPACE_SCAFFOLDED / SCANNED / INITIALISED`（初始化三步）、`ERROR_LOGGED`（出错）、`RECOVERY_COMPLETED`（恢复完成）。

**用法**：`HUMAN_TURN` + `GATE_APPROVED` 的时序可以证明"批准是真人给的"——合规审计就看这个。

## 25.2 阶段与步骤（10 种）
`PHASE_STARTED / COMPLETED / VERIFIED / SKIPPED`（大阶段）、`STAGE_STARTED / AWAITING_APPROVAL / REVISING / COMPLETED / JUMPED / SKIPPED`（步骤）。

**用法**：`STAGE_AWAITING_APPROVAL` 之后必须紧跟 `GATE_*` 之一——如果账本里出现"等待批准"后直接"完成"而没有门事件，说明有人作弊。

## 25.3 门与提问（6 种）
`GATE_APPROVED / GATE_REJECTED`（你的门决定）、`QUESTION_ANSWERED`（每个回答）、`SUMMARY_CONFIRMATION_RECORDED`（汇总确认）、`PLAN_APPROVAL_RECORDED`（施工方案批准）、`DECISION_RECORDED`（其他决定）。

## 25.4 评审与产物（8 种）
`REVIEW_REQUESTED / COMPLETED`（评审起止）、`ARTIFACT_CREATED / UPDATED / REUSED`（产物创建/修改/复用——复用指的是 CodeKB 命中）、`REVIEWER_SCOPE_BLOCKED`（评审员越界被拦）、`REVIEW_FREEZE_BLOCKED`（评审后改产物被拦）、`PLAN_APPROVAL_BLOCKED`（未批计划写码被拦）。

**用法**：三个 `_BLOCKED` 事件是**守卫钩子立功的记录**——看到它们说明安全机制在工作。

## 25.5 单元与构建（10 种）
`UNIT_STARTED / PAUSED / RESUMED / COMPLETED / MERGED`（单元生命周期）、`UNIT_OWNERSHIP_SET`（单元归谁）、`UNIT_GATE_RHYTHM_SET`（门节奏设定）、`BOLT_STARTED / COMPLETED / FAILED`（构建冲刺）、`AUTONOMY_MODE_SET`（自治模式选择）。

## 25.6 蜂群与并行（14 种）
`SWARM_STARTED / UNIT_CONVERGED / SOURCE_MERGED / UNIT_FAILED / BATON_RETURNED / COMPLETED / DEGRADED`（蜂群全程）、`WORKTREE_CREATED / MERGED / DISCARDED`（工作区）、`STATE_FORKED / MERGED` 与 `AUDIT_FORKED / MERGED`（并行时**连状态和账本都要分叉再合并**——保证并行期间各自的记录完整，合回来后账本依然是一条不间断的链）。

## 25.7 配置与流程变更（8 种）
`SCOPE_DETECTED / CHANGED`（套餐）、`DEPTH_CHANGED`、`TEST_STRATEGY_CHANGED`、`REVIEW_CLASS_CHANGED`（三个旋钮）、`RECOMPOSED`（流程重塑——含跳过步骤）、`PLUGIN_SELECTION_CHANGED`（插件启用变化）。

**用法**：想知道"什么时候决定跳过市场调研的"——查 `RECOMPOSED` 事件的载荷，里面有理由。

## 25.8 实践与规则（8 种）
`PRACTICES_DISCOVERED / AFFIRMED / OVERRIDE / SECTION_EMPTY`（实践发现四态）、`GUARDRAIL_LOADED`（规则加载）、`MEMORY_EMPTY`（规则为空——新项目的正常起点）、`RULE_LEARNED`（学习仪式沉淀了新规则）、`SENSOR_PROPOSED`（学习仪式提议了新传感器）。

## 25.9 传感器（4 种）
`SENSOR_FIRED / PASSED / FAILED / BUDGET_OVERRIDE`（触发/通过/失败/被覆盖）。**`SENSOR_BUDGET_OVERRIDE` 是最该被定期审计的事件**——每次"检查没过但放行"都在这。

## 25.10 合并派遣与知识库（6 种）
`MERGE_DISPATCH_INVOKED / RETURNED / FALLBACK`（蜂群合并派遣——FALLBACK 是派遣失败降级为本地合并的记录）、`DOCUMENT_INDEXED / UPDATED / REMOVED`（文档知识库）、`HEALTH_CHECKED`（doctor 体检）、`PIPELINE_LINK_COMPLETED`（流水线模式的角色交接）、`SUBAGENT_COMPLETED`（子会话完成）。

## 25.11 账本的防篡改设计（技术细节）

- **只增**：文件以 append 模式打开，API 层面没有"修改历史条目"的操作；
- **哈希链**：关键操作（fork/merge）记录前后内容的 SHA-256——能证明"这条记录所描述的版本"就是磁盘上这个文件；
- **禁符号链接**：打开账本文件时带 `O_NOFOLLOW` 标志——防止有人用符号链接把账本指向别的文件做手脚；
- **字段保留字**：`Event` 和 `Timestamp` 字段只能由工具写——AI 就算伪造一段文本贴进账本，这两个字段的写法它碰不到。

# 第二十七章 Compose 与 ARS：自适应规划的细节

## 27.1 ARS 五个分量怎么打分

ARS（Adaptive Risk Score，自适应风险评分）的原始定义在 `tools/data/ars-priors.json`——一组**先验权重**（未经校准的默认值，文档明说"纯咨询性质"）。五个分量每个 0-10 分：

| 分量 | 规划器问自己的问题 | 高分意味着什么 |
|---|---|---|
| **Intent Ambiguity**（意图歧义） | 用户说清楚要什么了吗？ | 需要更多提问和确认 |
| **Structural Uncertainty**（结构不确定性） | 代码库/问题域有多复杂难懂？ | 需要逆向工程和领域设计 |
| **Verification Entropy**（验证熵） | "做对了没有"好不好检查？ | 需要更强测试策略 |
| **Blast Radius**（爆炸半径） | 搞砸了影响多大？ | 需要评审、审批、灰度发布 |
| **Open Assumptions**（未决假设） | 有多少事是猜的？ | 需要可行性分析、风险登记 |

## 27.2 从分数到裁剪

总分和各分量的分布共同决定推荐：

- 总分低 + 各分量都低 → 推荐 express/poc 级别的精简流程；
- Intent Ambiguity 高 → 保留构思阶段和全部提问仪式；
- Structural Uncertainty 高（棕地）→ 保留逆向工程和领域设计；
- Blast Radius 高 → 保留对抗式评审和部署关卡；
- Verification Entropy 高 → 测试策略上调。

**每个跳过的步骤都附带理由**，呈现给你的是这样的清单：

```
Proposed flow (23 stages, standard depth):

EXECUTE: workspace-detection, reverse-engineering, requirements-analysis, …
SKIP:
  - market-research — 内部工具，无市场面（Intent Ambiguity 低）
  - team-formation — 单人项目
  - performance-validation — 无明确性能 NFR

1. **Approve this flow** — proceed
2. **Adjust** — tell me what to add back or remove
3. **Use a preset instead** — pick a scope
```

## 27.3 Compose 的只读纪律

自适应规划器有专属守卫（`guard-readonly-session` 钩子）：compose 模式下**任何写文件操作都被拦**。它只能读你的代码库、提问、出方案。规划不落盘就不算数——你批准后，引擎才写入状态。

## 27.4 中途重塑（recompose）

工作流进行中改流程（跳步/加步），走 `recompose`：
1. 呈现差异（"跳过 X、Y，理由___"）；
2. 你批准（记 `RECOMPOSED` 事件）；
3. 引擎更新剩余步骤图，**已完成的步骤不受影响**。

# 第二十八章 主手册的行为准则：指挥的 268 行军规

`.aidlc/skills/aidlc/SKILL.md` 是 `/aidlc` 的主手册。它约束"指挥"这个角色的全部行为。逐块白话：

## 28.1 开场定调

手册开头就规定身份："你是 AI-DLC 工作流的协调者（facilitator），**不是执行者**"——你的工作是按引擎的指令协调角色干活，不是自己埋头写代码。这一句定下了后面所有规矩的基调。

## 28.2 硬规则区（手册里最不容商量的部分）

1. **永远问引擎**："下一步是什么"的唯一合法答案是 `orchestrate next` 的输出。不许凭记忆、凭推测、凭"我觉得"；
2. **每次只执行一条指令**：拿到 `run-stage` 就干这一步，干完 `report`，再问。不许预取、不许批量；
3. **门的绝对性**：引擎说"这步有门"，你就必须开门等真人回答。沉默≠同意，离开≠同意，"之前的对话里他好像同意过"≠同意；
4. **不许自己写状态/账本**：一切经过工具；
5. **语音契约**：不说内部术语、不播报工具调用、只在四类时刻说话（6.5 节）。

## 28.3 恢复检测区

启动时检查：是否存在未完成的工作流（状态文件 + park 存档）？存在就呈现恢复菜单。这一区还规定了**压缩后怎么重建现场**（读面包屑 → 状态文件 → 账本 → 产物 → 日记，按权威顺序）。

## 28.4 新工作识别区

就是 6.6 节讲的三分支（接着干/新事情/改计划），手册里写成了明确的决策树，**每个分支的"问用户"都是强制的**。

## 28.5 各阶段执行区

指向 33 个步骤的说明书——手册本身不重复步骤细节，而是规定**通用仪式**：加载步骤说明书 → 加载规则 → 扮演角色 → 提问 → 产出 → 评审 → 学习仪式 → 开门 → report。每个环节指向对应的协议文件。

## 28.6 结束区

工作流完成（`done` 指令）时的收尾：总结成果、提示可用的回顾命令（session-cost/replay/outcomes-pack）、提醒提交 git。

## 28.7 为什么手册只有 268 行却管得住一切

因为**手册不管细节，细节在程序和协议里**。手册只保证一件事：AI 永远走"问引擎→按说明书执行→经程序汇报"的环路。只要环路不断，33 个步骤、17 个钩子、50 个工具就会自动各就各位。这是"用最小的提示词撬动最大的确定性"的设计。

# 第二十九章 opencode 版与其他版本的差异（完整清单）

如果你以后读 AI-DLC 的通用文档或别人的 Claude Code 版教程，这些差异要心里有数：

| 主题 | 通用/Claude Code 版 | opencode 版 |
|---|---|---|
| 钩子注册 | settings.json 声明式注册 | 适配器插件进程内翻译（无独立注册文件） |
| 钩子运行 | 每个钩子直接是 shell 命令 | 经适配器 spawn bun 子进程 + 命令安检 |
| "阻止停下"机制 | 有强制阻止通道（Stop hook 可拦截） | 只有空闲事件 → 注入提醒消息"推一把"（软性） |
| bun 缺失 | 钩子在配置里就存在，报错可见 | 钩子静默失效（失败开放），靠 doctor 发现 |
| 角色注册 | 全部进 agents 配置 | adaptive-planner 不进注册表（Task 动态调用） |
| 权限 | 各 harness 自己的权限语法 | opencode.json 的 permission 段 + 适配器白名单 |
| 工具/引擎/步骤/协议/传感器/知识库 | —— | **逐字节相同**（这部分完全跨 harness 共享） |

**实际影响最大的只有一条**：opencode 版"推一把"是软性的——理论上 AI 可能忽略提醒消息。实践中配合 continue-workflow 钩子的持续提醒，工作流都能推进；但如果你发现它"停下来不动了"，手动发一句"继续"即可，引擎状态不会因此错乱。

# 第三十章 故障排查手册

## 30.1 症状 → 原因 → 处方

**症状：钩子好像不工作（写了文件没记账）**
原因：多半是没装 bun 或不在 PATH。
处方：`bun --version` 确认；不在 PATH 就装到 `~/.bun/bin/bun`（适配器会探测这个位置）；然后 `/aidlc --doctor` 看钩子心跳。

**症状：它停下来不动了**
原因：opencode 版"推一把"是软性提醒（见 29 章）。
处方：手动发"继续"。不放心就先 `/aidlc --doctor` 确认状态没坏。

**症状：它说"计划批准被阻止"（PLAN_APPROVAL_BLOCKED）**
原因：施工方案批准后内容变了（你或它改了计划文件）。
处方：让它重新呈现计划，你再批一次。这是安全机制正常工作。

**症状：想改评审通过的文档被拦（REVIEW_FREEZE_BLOCKED）**
原因：冻结规则——评审结论和文档版本绑定。
处方：说要改，它会走"解冻→修改→重审"流程。

**症状：恢复时提示"产物被改动"**
原因：park 期间有人（可能是你自己）手动改了产物文件，哈希对不上。
处方：它会列出变了哪些文件，你选"以文件为准继续"或"回滚到存档版本"。

**症状：测试一直失败，它反复修**
原因：正常——失败阶梯第一级就是就地修（≤2 次）。
处方：看着；超过次数它会带着影响估算来找你，那时再做决定。

**症状：doctor 报 stage-graph 损坏**
原因：`tools/data/stage-graph.json` 被手动改过或不完整。
处方：这是编译产物——从发行包恢复原文件（或重装插件），不要手修。

**症状：问题问得太多/太少**
处方：调深度——`/aidlc --depth minimal`（或 comprehensive）。工作流进行中也可以让它改（记 `DEPTH_CHANGED` 事件）。

**症状：想完全推翻当前工作流重来**
处方：明确说"放弃这个工作流，重新开始"。它会确认（这是破坏性操作）→ 归档现有档案（不删除，进 archive/）→ 开新 intent。**放弃永远是你的决定**。

## 30.2 实在不对劲时的终极手段

1. `/aidlc --doctor` 先体检，照报告修；
2. 看账本末尾几条事件，理解"最后发生了什么"；
3. 状态文件和账本矛盾时，**以账本为准**（它只增不删），让工具重放重建状态；
4. 都不行：把 `aidlc/spaces/default/intents/<名字>/` 整个目录打包存档，删掉状态文件，重新开始——档案不会丢。

# 第三十一章 工作档案目录精解：你的数据到底存在哪

## 31.1 一个 intent 档案的完整结构

每个任务的档案目录是 `aidlc/spaces/default/intents/<名字>-<8位id>/`（文档里简写 `<record>/`）：

```
<record>/
├── aidlc-state.md          # 总控状态（唯一权威进度源）
├── audit/                  # 账本（注意：按"克隆"分片，见 31.3）
├── runtime-graph.json      # 统计报表（git 忽略，见 31.4）
├── intents.json            #（在 intents/ 层级）意图登记册
├── ideation/               # 构思阶段产物
│   └── intent-capture/
│       ├── intent-statement.md
│       ├── intent-capture-questions.md
│       └── memory.md       # ← 这步的"观察日记"
├── inception/
│   └── requirements-analysis/
│       ├── requirements.md
│       ├── requirements-analysis-questions.md
│       ├── traceability.json
│       └── memory.md
├── construction/ ...
└── operation/ ...
```

## 31.2 memory.md：每步的自动日记

每个步骤目录里都有一个 `memory.md`——**引擎在发出 run-stage 指令时自动从模板创建**，步骤进行中自动更新，**不许手工编辑**。它记的是叙事性内容："这步干了什么、用户说了什么、我们怎么判断的"。

日记的价值在恢复和学习：恢复现场时它是第五数据源（"当时怎么想的"）；学习仪式时工具从它提炼候选经验。

## 31.3 账本按克隆分片

`audit/` 不是一个大文件，而是**按克隆（clone）分片**：每个 checkout 出来的仓库副本有个令牌文件 `aidlc/.aidlc-clone-id`，这个副本产生的审计写进自己的分片。合并时靠 git 的正常合并——因为分片只增不改，合并永远无冲突。

**这解决了什么？** 多人/多机协作时，如果大家写同一个 audit 文件，git 合并会冲突不断。分片后各写各的，合起来自然是一条完整历史。蜂群并行时的 `AUDIT_FORKED / AUDIT_MERGED` 事件同理。

## 31.4 哪些文件不进 git（及原因）

`.gitignore` 精确排除了这些东西，每一条都有原因：

| 排除项 | 为什么 |
|---|---|
| `aidlc/active-space`、`intents/active-intent` | **每个用户的游标**——"我现在在看哪个空间/任务"是个人状态，不该共享 |
| `aidlc/.aidlc-clone-id`、`aidlc/.aidlc-sessions/` | 克隆令牌和会话缓存，机器本地物 |
| `intents/.aidlc-*` | 意图创建前的钩子健康检查暂存 |
| `**/.aidlc-sensors/` | 传感器运行缓存（引擎格式，可再生） |
| `intents/*/runtime-graph.json` | 统计报表，可随时从账本重新汇总 |

**其余全部提交**——状态、账本、产物、规则、知识库都是项目的过程资产。

## 31.5 runtime-graph 与三个回顾命令

`runtime-graph.json` 是从账本和日记**汇总**出的统计（每步耗时、传感器触发计数、经验条数、单元耗时……）。它是派生物（所以进 gitignore），丢了随时能重建。

三个回顾命令的数字**全部**来自 `bun .aidlc/tools/aidlc-runtime.ts summary --json`——**不让 AI 自己数数**（AI 数数会数错，程序不会）：

- `/aidlc-session-cost`：token 用量 × `model-rates.json` 单价表 = 成本。只打印到终端；
- `/aidlc-replay`：按账本时间线回放工作流。只打印；
- `/aidlc-outcomes-pack`：唯一会写文件的——生成 `OUTCOMES.md` 成果总结。

这三个技能被归类为 **read-only**：它们永远不推进工作流指针、永远不发审计事件。

## 31.6 恢复时引擎怎么找你上次的工作

启动顺序：读游标 `aidlc/active-space`（当前空间）→ 读 `intents/active-intent`（当前任务）→ 打开 `<record>/aidlc-state.md`。找到未完成的工作流 → 给你恢复菜单。**游标是每用户一份的**（git 忽略），所以队友 clone 同一仓库后，各自有自己的"当前任务"，互不干扰。

# 第三十二章 单步运行与跳转：主流程之外的入口

## 32.1 三种"不走主流程"的入口

正常用法是 `/aidlc` 一路跑主流程。但有时你想**单独**做某一步（比如"就想重新生成一下用户故事"）。三种方式：

1. **跳转**：`/aidlc --stage user-stories`——主流程跳到该步。**会改变主流程进度**；
2. **单步运行**：`/aidlc --stage user-stories --single` 或直接用单步技能 `/aidlc-user-stories`——**隔离运行，不动主流程的 Current Stage 指针**；
3. **大阶段跳转**：`/aidlc --phase construction`。

## 32.2 `--single` 模式的原理

引擎命令是 `aidlc-orchestrate next --stage <slug> --single`。它和主流程的区别：

- 主流程：`next` 返回的指令会推进状态、`report` 会打勾；
- `--single`：`next --single` 只记录一个"合成起点"，`report --single` 关闭这次尝试——**主流程的进度指针纹丝不动**。

所以单步运行是"排练/补做"的安全场所：产物照样写、传感器照样跑、账本照样记（可追溯），但主流程的"已完成"清单不受污染。

## 32.3 30 个单步技能是生成出来的

`.aidlc/skills/` 里那 30 个 `aidlc-<步骤>/` 单步技能**不是手写的**——由 `bun .aidlc/tools/aidlc-runner-gen.ts write` 从编译后的步骤图自动生成，还有 `check` 子命令做**漂移守卫**（步骤图变了但技能没重新生成，会报警）。所以插件加了新步骤后，跑一次 runner-gen 就有对应的 `/aidlc-<新步骤>` 命令。

**例外**：初始化三步骤没有单步技能——它们没有独立存在的意义（总不能"单独扫描一下项目"算一次工作流）。整个初始化打包成一个 `/aidlc-init`：一步完成"建第一个工作流档案 + 初始状态"。平时你不需要它——描述新工作时自动初始化；它是给"想显式控制"的人准备的。

## 32.4 跳转的规则

- 跳转**不跳过仪式**：跳到某步，那步的提问→产出→评审→门照走；
- 被跳过的中间步骤记 `STAGE_JUMPTED/SKIPPED` 事件，留痕；
- 跳转到**前置条件不满足**的步骤会被引擎拒绝（比如没做领域设计就跳契约设计）——依赖图是硬约束。

# 第三十三章 DocumentKB 动词详解

文档知识库的全部操作动词（`/aidlc knowledge <动词>` 或 `/aidlc-knowledge` 技能）：

| 动词 | 干什么 | 细节 |
|---|---|---|
| `onboard` | 把一篇（或全部新）文档纳入目录 | 提取文本、生成 metadata、进索引 |
| `sync` | 让目录和文件夹对齐 | 新文件入库、改了的更新、丢了的打墓碑；**索引丢了也能靠它重建** |
| `list` | 列出全部文档 | 含状态和关联 |
| `show <id>` | 看某篇的提取内容 | 输出内嵌"不可信数据"警告 |
| `associate <id> --intent <名>` | 把文档限定给某个任务用 | 不加 `--intent` 就是全空间可用；已结束的任务要加 `--allow-inactive` |
| `dissociate <id>` | 解除限定 | |
| `rebind <id> --to <路径>` | 文档**既被移动又被修改**后修复身份 | 这是 sync 唯一解决不了的情况——位置和指纹同时变了，工具无法确定"新文件就是旧文档"，需要你显式确认 |
| `summarize <id> --text-file <文件> --source-revision <sha256>` | 登记一份 AI 写的文档摘要 | **带内容哈希**——文档在摘要写完后变过，拒绝登记（防止摘要和内容对不上） |

**两个值得记住的设计**：

1. **没有 `remove`**：工具永远不持有删除你文件的权力。删除 = 你删原文件 + `sync`；
2. **目录可重建、树不可重建**：只丢 index.json 能完美重建（墓碑都会回来）；整个 `documentkb/` 树被删就救不回来（metadata 没了，文档身份就没了，sync 会把幸存原文当全新文档重新入库）。

# 第三十四章 多空间与跨 harness（进阶，初学可跳过）

## 34.1 space（空间）的真实用途

单人单团队永远只用 `default` 空间。空间是给**一个 monorepo 里多个团队**用的：每个团队有自己的 `spaces/<团队>/`（独立的规则、知识库、任务档案），互不干扰。

切换命令：`/aidlc space <名字>`——它会把 opencode.json 里的规则文件 glob 指向新空间（**保留 JSONC 注释**，不会毁掉你的配置文件格式），并更新 `aidlc/active-space` 游标。

## 34.2 跨 harness 迁移

`aidlc/` 工作树是 **harness 中立的**（里面没有任何 opencode 特有的东西）。理论上同一个项目可以从 opencode 版搬到 Claude Code 版继续——官方支持但标注"未测试"，真要搬，用框架的打包机制保持两边的树同步。

## 34.3 插件选择（select-plugins）

框架是"开放世界"：`plugins/<名字>/` 下的插件贡献额外步骤/套餐/角色，`select-plugins` 决定本安装启用哪些。本文的所有计数（33 步骤、14 角色）描述的是**基础框架**——你的实际启用集以 `/aidlc --doctor` 和 `stage-graph.json` 为准。启用变化会记 `PLUGIN_SELECTION_CHANGED` 审计事件。

# 第三十五章 完整实战走查：一次工作流的逐幕剧本

把前面所有机制串起来，看一场"真实对局"。场景：你在一个已有的 Express 后端项目里，输入 `/aidlc 加一个用户导出 CSV 的功能`。以下每一幕标注了**背后在发生什么**（括号里是你看不到的机制）。

## 第一幕：开场（10 秒）

**你看到**：
```
Let me get started on 加一个用户导出 CSV 的功能.
```

**背后**：session-start 钩子建会话档案、加载五层规则；初始化三步自动跑完（检测到这是棕地项目）；关键词推断 + 你的描述被定为 `feature` 套餐；账本记下 WORKFLOW_STARTED。

## 第二幕：逆向工程（棕地才有）

**你看到**：一阵安静（它在扫代码），然后：

```
🎯 **Stage Complete: Reverse Engineering**

| Artifact | Path |
|---|---|
| Codebase overview | .../codekb/codebase-overview.md |
| Architecture | .../codekb/architecture.md |
| （共 9 份）| |

**Approval** — Codebase scan complete. Proceed?
1. **Approve** — Continue to Practices Discovery
2. **Request Changes**
3. **Other**
```

**背后**：pipeline 模式——开发者子会话扫描（subagent），架构师综合成文档。你回 1，账本记 GATE_APPROVED。

> **下次任务的彩蛋**：CodeKB 已建好，下一个任务到这步会提示"代码没变化，复用已有扫描？"——回 1 就整步跳过，记 ARTIFACT_REUSED。

## 第三幕：实践发现

**你看到**：
```
**Question** — 我从 git 历史和 CI 配置推断出你们的实践，请确认：

- 分支策略：trunk-based（从最近 30 个提交推断）
- 测试：Jest，test-after（从 jest.config.js 和测试文件命名推断）
- 部署：暂无 CI 配置

1. **Confirm all** — 都对
2. **Correct something** — 告诉你哪里不对
```

**背后**：四个角色（CI/CD 主导 + 质量/开发/安全独立盲审）交叉验证。你确认后，`practices-promote` 工具把结论**写进 team.md**——从此团队所有任务都按这套实践走。账本记 PRACTICES_AFFIRMED。

## 第四幕：需求分析

**你看到**（产品经理人格，guided 模式逐条问）：
```
**Question** — 导出的 CSV 包含哪些用户字段？

1. **基本字段** — id、姓名、邮箱
2. **全部字段** — 含内部字段
3. **可配置** — 管理员自选字段
4. **Other** — describe what you want instead
```

你回 3。几轮问答后，它给汇总 → 你确认 → 写 requirements.md（FR1：管理员可配置导出字段；NFR1：100 万用户导出 < 5 分钟……）→ 产品负责人评审意见附上 → 学习仪式（你答 "nothing to add"）→ 审批门 → 你回 1。

**背后**：每个回答记 QUESTION_ANSWERED；汇总确认记 SUMMARY_CONFIRMATION_RECORDED；评审记 REVIEW_REQUESTED/COMPLETED；传感器在门处检查必备章节和需求编号格式。

## 第五幕：用户故事（圆桌）

**你看到**：一阵较长的安静（三个角色在各自写意见），然后成果 + 评审 + 门。

**背后**：mob 模式——设计师/开发/测试**互盲**地写意见文件；产品经理汇总。假设开发提出"可配置字段的权限模型会和现有 RBAC 冲突"——这是**知识题**，持异议者再讨论一轮；如果最终没谈拢，异议**原样**出现在你看到的成果里。三份意见文件不齐，门不开。

## 第六幕：设计三连（领域 → 单元 → 契约）

**你看到**：架构师给出组件图，其中有个选择摆给你：

```
领域划分有两个合理方案：
- **Option A**：导出功能并入 UserService（简单，但导出任务重会拖慢用户接口）
- **Option B**：独立 ExportService（多一点基础设施，隔离性好）
**推荐 B**（导出是重 IO 操作）。1/2/Other？
```

你选 2。单元生成产出 U1（export-service, M）、U2（admin-ui 变更, S），依赖图 U2→U1；计划批准门你批了；契约设计写出 OpenAPI 规格。

**背后**：架构评审人对设计文档做对抗式评审（找茬 2 轮）；单元图过 required-sections 传感器（格式 + 无环检查）；每步一个门。

## 第七幕：交付规划

**你看到**：Bolt 计划——Bolt 1 = U1（骨架：从 UI 到 DB 打通最薄链路），Bolt 2 = U2 完善。完成标准列明。批准。

**背后**：大阶段边界验证跑了一遍（每条 FR 都追踪到单元了吗？）记 PHASE_VERIFIED。

## 第八幕：施工方案与编码

**你看到**：开发者给出 U1 的《代码生成计划》——文件清单 + 每个文件对应哪条需求 + 测试契约。**计划批准门**你批了 → 一阵安静（子会话写码）→ 代码摘要。

**背后**：测试契约生成（带哈希）；计划批准记 PLAN_APPROVAL_RECORDED 并和内容哈希绑定；子会话任务书开头是单元号 + 契约哈希；写完校验 source-manifest——清单外没有多出来的代码。

## 第九幕：自治模式选择

骨架批准后，**只问一次**：
```
**Skeleton delivered.** Remaining bolts:
1. **Continue autonomously** — 自动跑完，出问题再停
2. **Gate every Bolt** — 每个都等你批
```

你选了 1。账本记 AUTONOMY_MODE_SET。此后 U2 自动开工。

## 第十幕：构建测试，测试红了

**你看到**：
```
Bolt 2 测试失败：导出 100 万行时超时（NFR1：5 分钟，实测 12 分钟）。

已就地修复 2 次（加流式写入、加索引），仍不达标。
**影响估算**：改用异步任务 + 完成通知，需新增一个队列组件，影响契约设计（契约要加一条）。

1. **Retry with fix** — 按建议修改并重试
2. **Accept failure** — 接受 12 分钟，改 NFR1
3. **Abandon** — 放弃此功能
```

**背后**：失败阶梯走到第三级（有界回跳已用过 1 次额度）。注意它**带着影响估算**来找你，而且把"放弃"留给你决定。你选 1 → 回跳代码生成（重走计划批准门）→ 修复 → 测试绿。

## 第十一幕：上线四连（精简版）

你的项目已有部署配置，所以：CI 流水线更新 → 部署执行（冒烟测试过）→ 监控告警配好（导出任务时长告警）→ 反馈文档。

## 第十二幕：闭幕

```
🎉 **Workflow Complete** — 26 stages · 2 units · 1 bolt retry
经验沉淀：0 条新增 · 传感器覆盖：全部通过
可以用 /aidlc-outcomes-pack 生成成果总结，/aidlc-session-cost 查看成本。
别忘了提交 aidlc/ 目录到 git。
```

**背后**：WORKFLOW_COMPLETED 入账；runtime-graph 汇总完毕。

## 整场对局你做的事

回数字回答约 10 个问题、在约 12 个门点回 1、做了 3 个真正的决策（Option B、自治模式、测试失败怎么办）。**总投入约 20 分钟，产出是一个带完整档案的功能**——需求、设计、ADR、契约、测试、部署、监控、账本，全部可查。
