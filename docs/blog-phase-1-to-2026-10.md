## 第 0 章：背景速成班（已熟悉的读者可跳过）

在讲 Phase 1 之前，先把几个关键词讲透。这些词后面会反复出现。

### 什么是 harness？

**harness（脚手架/工具箱）** 就是承载 AI 编程助手的那层软件，比如 Claude Code、OpenCode、Cursor 这类工具。它们负责：

- 让你和 AI 对话；
- 让 AI 能读你的文件、改你的代码、执行命令。

不同的 harness 能力大同小异，但**彼此并不兼容**——就像不同的浏览器装着不同的插件系统。这一点很重要，因为它决定了我的一个核心设计约束，后面会反复提到：**我做的这套东西不能绑定任何一家 harness**。

### 什么是"技能（Skill）"？

技能就是**一包预先写好的规则文档**，塞进 harness 里，让 AI 在做某类任务时"照章办事"。你可以把它理解成：给 AI 的一本《操作手册》。AI 每次接到任务，先翻手册，再动手。

我这个项目的技能叫 **aidlc-workflows**，最初是纯 Markdown 文档——没错，就是一堆 `.md` 文本文件，零代码。

### 什么是 AI-DLC？

DLC = Development Life Cycle（开发生命周期）。**AI-DLC** 就是"由 AI 驱动的开发生命周期"：把一次软件开发拆成一个个**阶段（Stage）**，比如：

```
需求分析 → 用户故事 → 工作规划 → 应用设计 → 单元拆分
        → 功能设计 → 代码生成 → 构建与测试 → ……
```

每个阶段 AI 产出一份**制品（artifact）**——需求文档、设计文档、代码、测试报告……每个阶段结束时有一个**审批门（Gate）**：AI 停下来，把成果摆给你看，你来决定"继续"还是"打回"。

我这个项目里的完整流程是 **3 个相位（Phase）、14 个阶段**：

| 相位 | 含义 | 阶段 |
|---|---|---|
| Inception（孕育期） | 搞清楚要做什么 | 工作区探测、逆向工程、需求分析、用户故事、工作流规划、应用设计、单元生成（7 个） |
| Construction（施工期） | 把它做出来 | 功能设计、NFR 需求、NFR 设计、基础设施设计、代码生成、构建与测试（6 个） |
| Operations（运营期） | 跑起来之后 | 占位（1 个） |

> NFR = Non-Functional Requirements，非功能需求，就是性能、安全、可用性这类"不是功能但很重要"的要求。

几个高频缩写，后面会反复用到：

- **WD** = workspace-detection（工作区探测）
- **RE** = reverse-engineering（逆向工程）
- **RA** = requirements-analysis（需求分析）
- **WP** = workflow-planning（工作流规划）
- **CG** = code-generation（代码生成）
- **B&T** = build-and-test（构建与测试）
- **FR** = functional requirement（功能需求，RA 阶段产物里的编号条目）
- **US** = user story（用户故事）

### 两个版本和一个分叉

这个故事有三个主角：

- **v1.0**：一个纯 Markdown 技能。优点是轻、哪儿都能跑；缺点是原作者停止维护了，而且有一些结构性痛点（后面细讲）。
- **v2.0**：同一个理念的进化版，做成了特定 harness（opencode）的插件，包含 **50 多个 TypeScript 工具、17 个钩子、33 个阶段、11 种任务类型、14 个角色人设**。功能很强，但重，而且绑死了 opencode。
- **我的分叉**：拿 v1.0 当底座，**原地进化**——分阶段把 v2.0 的先进理念搬进来，但始终保持"harness 无关"：任何能加载技能、能执行 shell 的 AI 编程工具都能用。

分叉早期还自建了几个扩展（extension）——比主流程低一档的规则包，按需加载。后面会出场的主要有三个：**AM**（autonomous-mode，自主模式）、**CTX**（checkpointing，上下文检查点）、以及工作流通用约定（workflow-conventions）。

### 本项目的宪法

v2.0 有一句纲领性的话，是我这整个项目的精神主线，我把它叫做这套系统的"宪法"：

> **"判断归 LLM，精确归工具，决定归人类。"**

翻译成大白话：

- **该动脑的（判断）交给 AI**：需求该怎么理解、方案怎么权衡、问题该问什么；
- **该精确的（算数/记录/路由）交给程序**：现在走到第几步、下一步是什么、状态有没有被人改坏——这些不能靠 AI"记性"，必须交给确定性代码；
- **该拍板的（决定）留给人**：AI 永远不能替你批准一个方案。

后面所有批次做的事，本质上都是让这句话一步步落地、落稳、落干净。判断和精确的分界线在哪里、哪些决定必须无条件下放给人类——每一次架构争论，最后都是在给这句话补注释。

有了这些背景，我们正式开始。

## Phase 1（与 Phase 0 同批交付）：让文档学会"一处定义，处处生成"

**完成时间：2026-09-11**

### 遇到的问题：阶段清单抄了 8 遍

v1.0 最头疼的结构性问题是：**同一份"阶段清单"在仓库里被手工复制了 8 处左右**。

我先把这 8 处逐一列出来，让你感受一下"重复"具体长什么样：

| 文件 | 重复内容 |
|---|---|
| `SKILL.md`（技能主入口） | 阶段列表 + 各阶段执行块 + 目录结构 |
| `references/common/process-overview.md`（流程总览） | 阶段分类 + Mermaid 流程图 + 阶段描述表 |
| `references/common/welcome-message.md`（欢迎词） | ASCII 字符画里的阶段行 |
| `references/common/terminology.md`（术语表） | 按相位分组的阶段清单 |
| `references/common/session-continuity.md`（会话恢复） | 恢复时该加载哪些产物的清单 |
| `references/inception/workflow-planning.md`（工作流规划） | 执行计划模板 + 状态文件模板 |
| `references/extensions/.../autonomous-mode.md` | 硬编码阶段名列表（最隐蔽、最容易漏） |
| …（另几处散件） | 各自角度的"抄写" |

这带来两个恶果：

1. **改不动**。想新增一个阶段？你得记得改 8 个地方。漏改一处，文档之间就开始互相打架，而 AI 读到互相矛盾的规则时行为是不可预测的。
2. **必然漏改**。人（和 AI）的记性就是靠不住的。这不是态度问题，是结构问题——**重复本身就是错的**。

写过程序的人一眼就能看出解法：这就是典型的"没有单一事实源（SSOT, Single Source of Truth）"问题。数据库课程会告诉你：同一份数据存两份，迟早不一致。文档也是数据。

### 解题思路：给每个阶段建"户口"，让脚本抄清单

我借鉴了 v2.0 的一个关键设计：**阶段契约（Stage Contract）**。

思路分三步：

**第一步：让每个阶段文件自己声明自己的属性。**

在每个阶段 Markdown 文件的顶部加一段 **frontmatter**（前置元数据块）。frontmatter 就是文件开头用 `---` 包起来的一段结构化数据，写博客的人应该很熟悉（Hugo/Jekyll/Hexo 都用它）。比如需求分析阶段的文件顶部从此变成这样：

```yaml
---
slug: requirements-analysis        # 阶段唯一标识（必须等于文件名）
phase: inception                    # 属于哪个相位
execution: ALWAYS                   # 总是执行 / 有条件执行
gate: approve-continue              # 审批门类型
produces:                           # 本阶段产出哪些制品
  - inception/requirements/requirements.md
consumes: []                        # 依赖哪些上游制品
requires_stage: []                  # 前置阶段（DAG 的边）
scopes: ...                         # 任务类型适用性（Phase 2 才填）
---
（下面才是原来的规则正文，一字不动）
```

这就像给每个阶段上了户口：身份、归属、产出、依赖，全在一张表里，**机器可读**。完整的字段表如下（这也是后来所有批次的地基，值得多看一眼）：

| 字段 | 含义 | 例子 |
|---|---|---|
| `slug` | 阶段唯一标识，必须等于文件名 | `requirements-analysis` |
| `phase` | 所属相位 | `inception` / `construction` / `operations` |
| `execution` | 执行方式 | `ALWAYS` / `CONDITIONAL` |
| `condition` | 条件阶段的执行/跳过条件（给人读的散文） | "仅当项目为棕地时执行" |
| `gate` | 审批门类型 | `approve-continue` / `2-option` / `none` |
| `produces` | 本阶段产出的制品清单 | `inception/requirements/requirements.md` |
| `consumes` | 依赖的上游制品 | RA 的产物等 |
| `requires_stage` | 前置阶段（构成有向无环图 DAG 的边） | `requirements-analysis` |
| `depth` | 深度策略（可选） | `adaptive` |
| `scopes` | 各任务类型下的执行/跳过映射（Phase 2 填充） | `classic: EXECUTE` / `bugfix: EXECUTE` / `express: SKIP` |

注意一个刻意的分工：`condition` 是**给人读的散文**，不进任何机器校验——"这个项目算不算棕地"是判断，判断归模型。这个伏笔到 Phase 3 会收。

**第二步：写一个生成器脚本 `scripts/generate.py`。**

它扫描全部 14 个阶段文件的 frontmatter，先校验再生成。校验规则包括（挑几条有代表性的）：

- slug 必须等于文件名（防止"文件叫 A 户口写着 B"）；
- 必填字段齐全；
- `consumes` 引用的产物必须真的有某个阶段声明生产（防止悬空依赖）；
- `requires_stage` 构成的图不能有环（防止"A 等 B、B 等 A"的死锁）；
- 后来到 Phase 2 追加：`scopes` 必须为每个已注册 scope 显式填值，漏一个就报错并列出清单。

校验全过后，**自动重新生成**那 8 处清单。

**第三步：在被生成的位置画上"标记区"。**

用 HTML 注释对 `<!-- BEGIN GENERATED: xxx -->` / `<!-- END GENERATED -->` 圈出"这块内容是机器生成的，人不要手改"。标记区外的内容，脚本一个字都不碰——这点很重要：生成器不是"重写你的文档"，而是"替你抄清单"，规则正文的著作权还在作者手里。

这里有个容易混淆的点，值得讲透——**这个脚本是"作者期"工具，不是"运行期"组件**。什么意思？它是给**维护技能的人**（我）用的，不是给使用技能的 AI 用的。用户拿走技能时，这个脚本静静躺在目录里不参与任何运行时逻辑。所以它不破坏"harness 无关、零依赖"的承诺——只要维护者机器上有 Python 就行。

"作者期 / 运行期"这对概念后面会反复出现，可以这样记：

- **作者期** = 改技能的人在自己电脑上干活（跑生成器、跑 CI）；
- **运行期** = 用户带着 AI 用技能干活（AI 读规则、调引擎）。
- 原则：**作者期可以随便上工具，运行期依赖越少越好。**

### 实际方案

落地的交付物清单：

- `references/common/stage-contract.md`：契约规范文档，定义每个字段的含义和校验规则（后来膨胀到 16 条校验规则）；
- **14 个阶段文件**全部加上 frontmatter，规则正文零改动；
- `scripts/generate.py`：纯 Python 标准库（零第三方依赖），带校验和 `--check` 漂移检测，初版约 700 行；
- 7 个消费方文件里圈定了 13 个生成区；
- 一个 GitHub Actions 工作流 `contract-check.yml`：每次 push/PR 自动跑 `--check`——万一有人改了 frontmatter 忘了跑脚本，CI 直接红给你看；
- 20 个单元测试，锁定解析器的各种边界行为。

`--check`（漂移检测）值得多讲一句：它重新生成一遍内容，和磁盘上的文件对比，**只要有一个字节不一样就以非零退出码报错**。这就把"忘了跑脚本"从"靠自觉"变成了"机器把关"。

### 结果

冒烟测试通过：**新增一个阶段，现在只需要"新建一个带 frontmatter 的阶段文件 + 跑一次脚本"，全仓库 12+ 处清单自动同步**。生成器二次运行幂等（再跑一遍不会有任何变化），标记区外的内容零改动。

审查环节还抓出并修掉了一批潜伏问题，比如：

- 解析器遇到引号里的 `#` 会把后面内容当成注释**静默截断**——如果某个产物路径里恰好有 `#`，数据就悄悄丢了；
- 某个产物名在两个文档里不一致（一个文件说产物叫 workflow-planning.md，另一个说叫 execution-plan.md）——这正是"手抄清单"时代留下的陈年伤；
- 计划模板里预置的 `(COMPLETED)` 勾选状态会被生成器冲掉——改为不预置。

这里有个让我很满意的纪律：审查发现的每个问题都"**先考证、后修复**"——先翻历史决策文档确认这个行为是不是当初故意设计的，再决定改不改。事实证明有几次"看起来像 bug"的行为其实是记录在案的已知取舍（后面 Phase 3 的 dogfood 还会再验证一次这条纪律的价值）。

### 价值

- **扩展痛点根除**：从"改 8 处"变成"改 1 处 + 跑一次命令"。
- **埋下了最重要的地基**：这一步让"阶段"从散文描述变成了**结构化数据**。当时看只是消除了文档重复，回头看，这是后面一切（scope 矩阵、运行时引擎）的前提——就像先有了户口数据，才谈得上户籍系统数字化。
- **确立了一个架构原则："地基按未来要盖两栋楼设计"**。frontmatter 这份事实源，Phase 2 从这里转置出矩阵，Phase 3 把它编译成引擎吃的 JSON——**三个阶段都是给同一份事实源新增消费者，事实源本身一次都没返工**。当初否决的替代方案（搞一个独立的中央注册表存阶段数据）就是因为引擎落地时还得回头给每个阶段补契约，属于重复改造。

## Phase 2：给工作流装上"任务类型"这档变速器

**完成时间：2026-09-12**

### 遇到的问题：修个 bug 也要走全套仪式？

Phase 1 之后，文档不再打架了，但工作流本身有个体验问题：**v1.0 对所有任务一视同仁**。

你想啊：开发一个全新产品，走 14 个阶段是合理的；可如果我只是要**修一个 bug**、**改一段重构**、**打一个安全补丁**呢？让我先做需求分析、写用户故事、拆单元……这就像去楼下便利店买东西也要先做市场调研。

v1.0 的做法是靠模型在"工作流规划"阶段**逐个阶段临时判断**该不该跳过。这有两个毛病：

1. **十四次判断 = 十四次出错机会**，判断质量看运气；
2. **每次都从头想一遍**，同样的"修 bug"场景，这次跳三个阶段、下次跳五个，没有沉淀。

v2.0 对此有个漂亮的解法：**scope（任务类型）预设**。它定义了 11 种任务类型，每种类型预先裁剪好一套"哪些阶段执行、哪些跳过"的执行矩阵。我决定把这个理念搬过来——但砍到一个务实的子集。

### 解题思路：一个字段，转置出一张矩阵

方案非常顺滑，因为 Phase 1 的地基已经打好了：

1. 在 `references/common/scopes/` 目录下定义 scope：每个 scope 一个文件，说明这种任务类型的定位、默认深度（后面讲）、关键词（用于自动识别）；
2. 给 14 个阶段 frontmatter 里的 `scopes:` 字段填值——**每个阶段对每个 scope 声明 EXECUTE 或 SKIP**；
3. 让 generate.py 把这份"阶段 × scope"的映射**转置**成一张"scope × 阶段"的矩阵表，自动注入到工作流规划的规则文件里；
4. 运行时流程升级为"**先选 scope，再微调**"：模型在需求分析阶段根据任务特征推荐一个 scope，然后在工作流规划时以该 scope 的矩阵为基线，允许逐阶段微调。

"转置"值得多说两句，因为它是 SSOT 思路的漂亮应用：阶段文件里存的是"**这个阶段**在各 scope 下做不做"（一行一阶段），而规划时需要看的是"**这个 scope** 下哪些阶段做"（一列一阶段）。同一份数据，两种视角，靠脚本转置生成，人永远只维护一种视角。

这里解释一下 **depth（深度）** 这个配套概念：每个 scope 除了裁剪阶段，还带默认深度档位——**minimal（最小）/ standard（标准）/ comprehensive（全面）**。同样是"需求分析"，express（速通）档下就写一页纸，comprehensive 档下就可能要写透。"哪些阶段做"由 scope 定，"每个阶段做多细"由 depth 定，两个旋钮配合，就把"流程重量"调到了连续可调。

### 实际方案

**定义了 6 个 scope**：

| scope | 定位 | 关键词（用于自动识别） | 默认深度 |
|---|---|---|---|
| `classic` | 默认全家桶，新功能开发 | feature / add / build / create… | standard |
| `bugfix` | 修 bug | bug / fix / error / crash / fails… | standard |
| `refactor` | 重构 | refactor / clean up / restructure… | standard |
| `security-patch` | 安全补丁 | vulnerability / CVE / exploit… | comprehensive |
| `infra` | 基础设施 | CI / pipeline / deploy / IaC… | standard |
| `express` | 速通小改动 | typo / rename / quick / trivial… | minimal |

生成的矩阵（简化示意，真实矩阵是完整的 14 行 × 6 列）：

| 阶段 | classic | bugfix | express |
|---|---|---|---|
| workspace-detection | EXECUTE | EXECUTE | EXECUTE |
| reverse-engineering | CONDITIONAL | CONDITIONAL | CONDITIONAL |
| requirements-analysis | EXECUTE | EXECUTE | EXECUTE |
| user-stories | EXECUTE | SKIP | SKIP |
| workflow-planning | EXECUTE | EXECUTE | SKIP |
| application-design | EXECUTE | SKIP | SKIP |
| units-generation | EXECUTE | SKIP | SKIP |
| functional-design | EXECUTE | EXECUTE | SKIP |
| …（其余行同理自动生成） | | | |

为什么是 6 个而不是 v2.0 的 11 个？这是个有记录的取舍：`poc`/`mvp`/`workshop` 这几种要等运营期阶段补齐后才有区分度，`enterprise` 可以用深度档表达——**先不引入**，等将来运营期补齐，各 scope 只需"加一行"，定义本身不用改。你可以在矩阵表里想象一下：加一种任务类型 = 矩阵加一列 = 14 个阶段各填一格——纯数据增量，零架构改动。这就是"数据驱动"的好处第一次兑现。

**几个刻意的设计细节：**

- **scope 自动选定，后来又"淡化"了**。最初设计是"模型推荐 + 用户确认"，上线一周后用户（我）就烦了：明显是一个 bug，还要问我"用 bugfix 还是 classic"？于是 09-14 做了一次修订：**无歧义场景（用户显式指定，或关键词唯一命中）自动选定、不设门**，事后一句话告知并记录审计；真有歧义才问，而且只问 1-2 个最可能的候选，**永不展示完整目录**（把 6 个选项全摆出来让用户做选择题，是把本该机器干的活推给人）。
- **一个不对称原则**在此埋下：scope 可以自动选定，因为选错可以零成本纠正（下次纠正即可）；但**扩展配置绝不自动开启**——扩展一开就是阻塞性约束（比如安全基线会强制一堆检查），静默开启会让用户莫名被门拦住。"可以自动的"和"必须问的"边界清晰。

### 审查抓出的隐蔽坑

审查环节抓出一个很隐蔽的问题：某些 scope（比如 bugfix）会跳过"单元生成"阶段，那后续那些本该"逐单元执行"的阶段（功能设计、代码生成等按单元循环的阶段）怎么办？——没有单元清单可循环了。

约定：**退化为对整个任务执行一次**。听起来简单，但这个约定当时只存在于两个阶段的正文里，其他四个逐单元阶段没写——意味着模型在四个阶段里会拿到自相矛盾的指引（"逐单元执行"但"没有单元清单"）。修法是把前提条件写进所有相关阶段 + 生成器加了条防回归规则（advisory 规则 16），谁以后改坏了会报错。

另一个修复：某些 scope（如 security-patch）会跳过功能设计，但下游 NFR 阶段的规则里写死了"Functional Design must be complete"——每次运行必触发矛盾指令。修法是给这些前提加条件分支："计划无 FD 阶段时改从需求文档 + 逆向产物取数"。

### 结果

从那以后，"修个 bug"这个请求会自动落到 bugfix scope：需求分析保留（还是要理解问题），用户故事、应用设计、单元拆分全部 SKIP，直接进功能设计 → 代码生成 → 构建测试。**模型从"现场判断十四次"变成"确认一次基线、偶尔微调"**。

还有一个意外之喜：scope 的引入让**扩展延迟加载**成为现实——不被选中的 scope 文件根本不进上下文，实测显著节省了 AI 的 token 消耗（AI 的上下文窗口是有限资源，这个概念后面 Phase 3 还会再讲）。

### 价值

- **轻任务终于轻得起来**：流程重量和任务重量匹配，这是工作流可日常使用的关键一步。
- **经验第一次被"固化"**：什么样的问题该跳哪些阶段，从模型每次的临场发挥，变成了可审查、可版本管理的**数据**。
- **再次验证 SSOT 架构**：整个 Phase 只往 frontmatter 里填了一个字段的值，矩阵、目录表、规则注入全部由生成器自动完成。改一个阶段对某 scope 的适用性？改一格、跑脚本，全仓库同步。

## Phase 3：把方向盘交给模型，把仪表盘交给程序

**完成时间：2026-09-14；后续两天各有一轮增量修复**

这是整个项目最重要的一次跃迁。前两个 Phase 还是"整理文档"，Phase 3 开始**写真正的运行时代码**。本章会比较长，分七个小节：问题、决策转向、全景架构、状态文件、动词体系、report 流水线、完整性三角，最后是一次真实运行的回放。

### 7.1 遇到的问题：谁还记得我们走到哪一步了？

Phase 2 之后，流程轻重的问题解决了，但一个更根本的问题浮出水面：**"现在走到哪个阶段了"这件事，一直靠 AI 的记性和自觉**。

具体来说，v1.0 的运行时是这样的：

- 有一个状态文件（`aidlc-state.md`），记录每个阶段完成没有、当前在哪个阶段——但这个文件**由模型手写维护**；
- "下一步该做什么"由模型读文档、读状态、自己推导；
- 全仓库有 **20 多处散文指令**在教模型"完成阶段后去把状态文件的第 X 行勾上"——这些指令散落在各个阶段规则文件里；
- 还有一个审计文件（`audit.md`）记录每次阶段转移，也是模型手写追加。

这套机制的隐患，用一次真实的项目使用（dogfood，"自己吃自己的狗粮"，即用这套工作流开发真实项目来验证它）暴露得淋漓尽致：

- 长对话里模型会**遗忘**开头读过的规则，状态更新走样；
- 会话中断后重开，"恢复现场"全靠模型重新读文档推导，**每次恢复都可能不一样**；
- 状态被改坏了（无论故意还是手滑）**没有任何检测手段**；
- 路由逻辑（下一步是什么）在文档里写着，但文档不是代码，**不保证被遵守**。

这正是开篇那句宪法纲领的反面："精确"的事（状态、路由、审计）落在了 LLM 手里。LLM 擅长判断，但不擅长一丝不苟的记账。你可以把 LLM 想成一个聪明但健忘的新同事：让他做设计决策没问题，让他记住"第 7 个阶段做完没有"就是为难他。

### 7.2 一个重要的决策转向：引擎从"可选"改为"必选"

动手前先做了一轮技术摸底：把 v2.0 的编排工具链（8600 行的 orchestrate + 6800 行的 state）逐个拆解，确认它"选下一步阶段"的算法本质就是——**全图线性扫描 + scope 网格过滤 + 状态覆盖 + 勾选跳过**。没什么黑魔法，完全可以自己写个轻的。

最初我打算让引擎是"可选增强层"——没 Python 也能退回纯 Markdown 模式，看起来更兼容。后来放弃了，因为**双模镜像会掐死演进**：引擎每加一个功能，就得手写一份等效的 Markdown 约定给"无引擎模式"，两份还得永远保持一致——这恰恰是 Phase 1 刚刚消灭掉的那种重复。于是立场修订为 D6 决策：**引擎必选，无引擎 = 硬停（HARD STOP），提示安装 Python**。

配套决策：

- **D7 技术栈 = Python 标准库**：与生成器同栈，零第三方依赖，用户不用 `pip install` 任何东西；
- **D12 分发形态 = 随技能目录分发**：用户侧前提只有两条——harness 能加载技能 + 机器能跑 python；
- **验收硬标准 = 裸项目 dogfood**：把技能目录复制到一个全新的空项目（不带任何其他文件），全流程必须跑通。

### 7.3 全景架构：一张图看懂谁编译、谁判断、谁执行

```
AUTHORING TIME（作者期：改技能的人在自己电脑上）
+------------------------------+
| references/<phase>/*.md      |
|   YAML stage frontmatter     |
|   slug/execution/gate/scopes |
|               |              |
|               v              |
|     scripts/generate.py      |
|               |  compile     |
|               v              |
|     scripts/data/            |
|       stage-graph.json       |
+------------------------------+
         ^
         |  engine reads ONLY this compiled graph.
         |  It never parses frontmatter or condition prose;
         |  generate --check (CI) guards drift.

RUNTIME（运行期：AI 带着用户干活）
+------------------------------------+
|              AI model              |
|  judgment: Execute-IF / SKIP,      |
|  scope pick, question files,       |
|  artifacts, gate presentations     |
+-----------------|------------------+
                  |  reads stage rules, writes artifacts,
                  |  and calls the 8 engine verbs (below)
                  v
+------------------------------------+
|         scripts/engine.py          |
|  precision: routing, transitions,  |
|  digest, audit, park, stamp        |
|  (Python 3.8+ stdlib only)         |
+-----------------|------------------+
                  | atomic read/write
                  v
+------------------------------------+
|             aidlc-docs/            |
|   aidlc-state.md     audit.md      |
|   handoff.md (engine-only writer)  |
+------------------------------------+
```

这张图是整个系统的"总平面图"，几个要点：

**编译而非解析（compile-to-JSON）。** 引擎运行时**只读 stage-graph.json，永不解析 frontmatter，也永不解析 condition 散文**。打个比方：阶段规则是建筑图纸，generate.py 是晒图车间，stage-graph.json 是装订成册的标准图集，引擎是施工监理——监理只认盖章的图集，不认工头口头转述的"图好像改了"。这样规则解析出错的风险被压缩在编译期一处（作者改规则时当场就能发现），运行期引擎读到的永远是结构化、已校验的数据。JSON 的漂移同样被 `--check` 和 CI 盯着。

**condition 永不进引擎。** frontmatter 里那段给人读的散文（"仅当项目为棕地时执行"），引擎不解析——CONDITIONAL 阶段照常派发并标 `conditional: true`，模型判断不适用就用 `report --result skipped --reason` 报告跳过并说明理由。判断权老老实实留在 LLM，工具只负责记账。这就是"判断归 LLM"在接口设计上的体现。

三归分工的完整对照表：

| 归属 | 内容 | 诚实边界 |
|---|---|---|
| **精确归工具（引擎管）** | 跨阶段路由、状态机、审计日志、完整性校验 | — |
| **判断归 LLM（模型管）** | 条件阶段适用性、scope 推荐、深度自适应、需求澄清、写一切文档和代码 | — |
| **决定归人类（你管）** | 每个审批门双选项（Approve & Continue / Request Changes） | 无钩子环境下"模型伪造批准"工具层防不住，靠提示词纪律 + 审计留痕 |

### 7.4 状态文件：合租公寓的记事本

状态文件还是 Markdown（人随时能用记事本打开），但内部划了"租区"：

```
aidlc-state.md
+--------------------------------------------------------------+
| MODEL-OWNED ZONE（标记区之外：模型专属）                       |
|   ## Project Information / ## Workspace State                |
|   ## Execution Plan Summary                                  |
|      - Scope: classic      - Depth: standard                 |
|      - Stages to Execute / Stages to Skip                    |
|   ## Extension Configuration   (| CTX | No |)                |
|   ## Autonomous Mode           (Enabled: No ...)             |
|==============================================================|
| <!-- BEGIN ENGINE-STATE -->   ENGINE-EXCLUSIVE ZONE          |
|   ## Stage Progress    - [ ]/[x]/[S]/[R]/[?] <slug>          |
|   ## Current Status    Current Stage / Last Parked           |
|   ## Unit Progress     per-unit marks                        |
|   ## State Digest      sha256: <64 hex>                      |
| <!-- END ENGINE-STATE -->                                    |
+--------------------------------------------------------------+
```

**上半区：模型专属。** 项目信息、执行计划摘要、扩展配置、自主模式开关——AI 按模板自由填写，引擎从不改写。

**下半区：引擎专属。** 阶段进度勾选表、当前阶段、完整性指纹——只有引擎能写，模型手改这里会被完整性校验当场抓住（下面 7.7 讲）。

进度表每行前面的方括号是一个字符的"印章"：

| 印章 | 含义 |
|---|---|
| `[ ]` | 还没做 |
| `[x]` | 做完了（completed，或门批准 approved） |
| `[S]` | 跳过（skipped，附理由） |
| `[R]` | 门被否（rejected） |
| `[?]` | 需修订（revised） |

最妙的是中间那道墙上的**三条"模型写、引擎读"通道**：模型在上半区写的三个结构化信息，引擎会（宽容地）读——

1. **执行计划摘要**（Scope/Depth/Stages to Execute/Skip）：模型在工作流规划批准后按固定格式写入，引擎读它做路由过滤。**Phase 0/1 时"无人消费的计划文档"这个遗留问题就此收口**——计划第一次有了程序化读者；
2. **扩展配置表**（后来 Phase 3.3 加）：引擎判断要不要做 checkpoint 检查；
3. **自主模式区**（后来 Phase 3.3 加）：喂给 status 输出的 `autonomous` 键。

注意"宽容读取"：这三条通道读的时候**不挑刺**——格式不对、缺字段、写了乱码，引擎不报错，当作"没配置"处理。因为这些区归模型所有，引擎若因区外内容报错，就等于侵犯了自己不该管的辖区。所有权是双向的：你不碰我的区，我也不拿你区里的坏数据惩罚你。

### 7.5 八个动词：权限最小化

引擎的对外接口就是 8 个命令行子命令，AI 在对话里通过 shell 调用。按"能改什么"分层：

```
+-------------+----------+-----------------------------------------------+
| layer       | verb     | effect                                        |
+-------------+----------+-----------------------------------------------+
| setup       | init     | create state + audit files (STATE_CREATED)    |
| transition  | report   | the only transition write entry (5 results)   |
| transition  | jump     | re-point current; --fresh archives aidlc-docs |
| annotation  | park     | Last Parked + handoff.md only                 |
| read        | status   | recovery briefing + artifact sensors          |
| read        | next     | emit run-stage directive for current stage    |
| read        | stamp    | authoritative UTC timestamp; zero side effects|
| repair      | rebase   | replay audit transitions into the region      |
+-------------+----------+-----------------------------------------------+
```

逐个过一遍（stamp 和 park 是后来批次加的，这里先总览）：

- **`init`**：开户。创建状态文件和审计文件，审计里第一条就是 `STATE_CREATED`。
- **`report`**（**唯一的常规转移写入口**）：阶段做完，报告结果。五种结果各对应严格定义的转移语义（下面 7.6 详讲）。
- **`jump`**：改道。回跳会重置指针之后的所有阶段，前跳会标注跳过的阶段，全部留审计；`jump --fresh` 整体归档重来。
- **`park`**：临时停车留条（Phase 3.1 加）。
- **`status`**：出具"恢复简报"——停在哪、最近发生了什么、有什么警报。
- **`next`**：回答"下一步干什么"——引擎按"线性扫描 + scope 过滤 + 状态覆盖 + 勾选跳过"算出下一步，返回一条**指令 JSON（directive）**：要么是"执行某阶段"（附上该阶段的全部契约信息：产物、依赖、门类型、规则文件路径、是否条件阶段），要么是"全部完成"，要么是"出错了"（错误对象三件套：机器可读的 `code`、人类可读的 `message`、补救提示 `hint`）。
- **`stamp`**：只报权威 UTC 时间戳，零副作用（Phase 3.3 加）。
- **`rebase`**：保修通道，状态被改坏时以审计流水为准重放修复（下面 7.7 讲）。

动词分层的本质是**权限最小化**（这是后来 D13 纪律的雏形）：想改进度？只能走 report/jump 这两扇门，而门后有四道验证关卡；只想留个便签？park 物理上就摸不到进度数据。一个动作能改什么，由它用的动词决定，而不是由调用者小心不小心决定。类比：电视遥控器上换台键、贴便签键、看时钟键各管各的——按"看时间"永远不会把频道弄乱。

错误处理也有个值得学的细节：**连命令行用法错误都输出 JSON**（为此重写了 argparse 的错误处理类），所有错误统一 `{kind, code, message, hint}` 三层结构 + 退出码 1，所有成功输出统一注入 `timestamp` 字段。为什么？因为消费方是 AI，AI 解析结构化 JSON 比解析自由文本可靠得多；统一的形状意味着"遇到错误"本身成为一个可编程处理的事件，而不是一次崩溃。

### 7.6 report 流水线：四道关卡 + 盖章记账

`report` 是整个系统唯一的常规进度写入口，全部逻辑是一条流水线：

```
report --stage <slug> --result <R> [--reason <why>]
   |
   v
四道验证关卡 _validate_transition()
   |-- [1] slug 在图里存在吗？................ 不在 -> 错误 unknown-stage
   |-- [2] 票种匹配：
   |       有门的阶段用了 completed ........... -> 错误（应使用 approved）
   |       无门的阶段用了 approved/rejected/revised -> 错误
   |-- [3] skipped 的资格审查：必须是条件阶段/当前 scope 下条件执行/计划内显式跳过
   |       且必须给 --reason .................. 否则 -> 错误
   |-- [4] 只能 report 当前阶段 ............... 不是 -> 错误
   |
   v
盖章：completed/approved:[x]  rejected:[R]  revised:[?]  skipped:[S]
作废停车便签（parked = None——你已经重新上路，便签没意义了）
   |
   v
原子写入状态文件（先写临时文件再一步替换，断电也不出半截文件）
   |
   v
审计追加一条事件（append-only，账本不撕页）
   |
   v
完成/获批时顺手做 produces_missing 软探测（fail-open，出错静默放行）
   |
   v
JSON 回执：记上了，现在轮到 <下一个待办阶段>
```

四道关卡每道都在堵一类作弊/失误：

1. **查票**：阶段名必须真实存在——防幻觉（模型编造一个不存在的阶段名来"完成任务"）；
2. **票种匹配**：带审批门的阶段**必须**用 `approved`/`rejected`/`revised`——不允许用 `completed` 蒙混；这把"该让人拍板的事必须让人拍板"焊死在代码里。AI 想跳过用户审批直接说"完成了"？引擎直接拒绝。**注意这一条的实际含义：宪法里"决定归人类"不靠自觉，靠类型系统**；
3. **跳过资格审查**：`skipped` 不是想跳就跳——只有条件阶段、被 scope 裁剪的阶段、或计划里显式列入跳过的阶段才允许跳，且必须给理由。必做阶段想偷懒？引擎让你改走 `jump`（人类决定的改道），而不是静默跳过；
4. **本人办理**：只能 report 当前阶段，不能跳着报、不能补报很久以前的。

五种结果的转移语义矩阵（这是测试的基准，每个格子都有用例钉死）：

| result | 勾选 | 指针 | 适用 |
|---|---|---|---|
| `completed` | `[x]` | 推进 | 无门阶段完成 |
| `approved` | `[x]` | 推进 | 门阶段用户批准后 |
| `rejected` | `[R]` | 停本阶段 | 门拒绝 |
| `revised` | `[?]` | 停本阶段 | 修订后再提交 |
| `skipped` | `[S]` | 推进 | 仅条件/计划跳过，须理由 |

### 7.7 完整性三角：digest + 审计交叉核验 + rebase

状态文件是普通 Markdown——人随时能用记事本打开它。怎么防止"有人手改进度表作弊"？答案是**两道互相独立的证据链**，每次状态操作前交叉核验：

```
   ENGINE-STATE region                     audit.md
 (marks / current / digest)         (append-only, engine-only)
           |                                     |
           v                                     v
 [1] 内容指纹（digest）                [2] 审计交叉核验
     对引擎区内容算 sha256，               解析审计里的全部转移事件，
     存在指纹行里                          与进度表印章逐一对账
           |                                     |
           +------------------+------------------+
                              |
                              v
                    两道都过？                对不上？
                 integrity: ok          tampered / 越权手改
                                              |
                                     修复：rebase
                                     按审计流水重放，重建进度区 + 新指纹
```

两道链条抓的是不同的贼：

- **[1] 指纹抓"改了内容"的**：引擎区文字（除指纹行本身）算出 sha256 存档。下次操作前重算：文件被改过哪怕一个空格，哈希就对不上——当场识破；
- **[2] 交叉核验抓"绕过引擎伪造记录"的**：每次合法转移都会在审计里留一条。引擎把审计事件解析出来，和进度表印章**逐一对账**：进度表说 `requirements-analysis [x]`，审计里就必须有对应记录。多一枚章、少一枚章、章对不上事件，都算账目不符。哪怕有人连指纹一起重新算好，审计里没有对应流水，照样露馅。

对不上账怎么办？**以审计流水为准 rebase**——审计是 append-only、引擎独写的，比状态文件更可信。rebase 把审计里的转移历史重放一遍，重建整个进度区和指纹。相当于"存折丢了，拿银行流水重新补一本"。

要诚实说明它的边界：这是**检测，不是阻止**——没有钩子的环境拦不住模型真的去改文件，但"改了必被发现"这件事是确定的。它的威胁模型是"模型疏忽/手滑"，不是"模型蓄意对抗"（一个铁了心要伪造批准的模型，在无钩子环境下工具层确实防不住——这条诚实边界记录在案，对策是提示词纪律 + 完整审计留痕）。

### 7.8 全文档收口：最大的一块暗活

实施中最大的一块暗活不在引擎里，在文档里：grep 全部规则文件，把 **20 多处"教模型手改状态"的散文指令逐一改写或删除**——否则模型会同时收到"引擎独占写状态"和"完成后去把第 X 行勾上"两组矛盾指令，实际使用必撞车。这批收口还揪出一个清单外文件（reverse-engineering.md），证明"系统性 grep"比"凭记忆列清单"可靠。

错误恢复协议也整体重定向：过去教模型手改状态自救的一堆路径（标 SKIPPED、标 incomplete、修正 current stage……），统一改成"完整性挂起 → 人工确认 → 引擎重定基线"。

### 7.9 一次真实运行的回放

光讲机制容易抽象，下面是一次真实运行的完整命令序列（可以对照 7.5-7.7 看）：

```
status -> state:none                        开局探测：没有状态文件 = 新项目
   |
   v
init -> STATE_CREATED (14 stages)           开户：状态 + 审计同时创建
   |
   v
next  -> run-stage: workspace-detection     第一个待办阶段
   |
   v
report wd completed ----------------------> 指针移到 reverse-engineering
   |
   v
next  -> run-stage RE (conditional:true)    引擎照发不误（它不懂"是不是老项目"）
   |
   v
report RE skipped [S] --reason greenfield   模型判断：新项目，RE 不适用
   |                                        （能过关卡[3]：RE 本就是条件阶段）
   v
指针 = requirements-analysis
   |
   v
[模型工作：写问题文件 -> 提问工具收集答案 -> 回写文档]
   |          这一大段完全没有引擎参与——写文档是模型的活
   v
park --note "..."                           会话要中断，留停车便签
   |                                        进度和指针原封不动
   v
status -> 恢复简报：便签 + 便签年龄 + 自主模式配置
           + 传感器警报（发现 RA 半成品文件已存在）
```

它演示的是职责分工的**节奏感**：引擎调用（一行命令、一个 JSON 回执）和模型工作（读规则、写文档、提问）交替出现。引擎像地铁闸机——刷一下，过去几步，再刷一下；乘客在两台闸机之间怎么走，闸机不管。

### 7.10 实施期裁决与验收

分工上，4 个执行者子任务并行（编译层 / 规则文件引擎化 / 状态指令收口 / SKILL.md 改写），引擎本体（engine.py + 测试）由我亲自实现。实施期留了六个裁决记录在案（挑三个有教育价值的）：

- **per-unit 阶段引擎单次发射**：逐单元执行的阶段（功能设计、代码生成等），引擎只发射一次指令，单元内的循环归模型——引擎的粒度到阶段为止，不钻进阶段内部；
- **审计交叉核验在 rebase 后豁免**：重定基线后，重放的印章天然没有逐条对应的新审计事件，若不豁免，rebase 永远"修复失败"——修复机制自身不能被校验机制卡死；
- **jump 不绕过计划过滤**：跳到计划外的阶段时，引擎照样执行跳转但附带 note 提示"目标不在 Stages to Execute 里"——路由纪律对改道同样生效。

**验收：**

- 引擎初版约 1000 行（经过后续所有批次的迭代，如今 1741 行），纯标准库；
- 77 个单元测试全绿（生成器 30 + 引擎 47）；二次运行幂等；`--check` 零漂移；
- **裸项目验收**（硬标准）六项全过：全新项目全流程走到完成、棕地项目 bugfix 裁剪、手改状态触发挂起→重定基线、会话中断恢复、向后跳、归档重来。

上线后两天内又做了两轮快速迭代，值得记录的几件：

1. **真实项目二次 dogfood**（一个课程表应用）：确认"引擎下限收益已兑现"——长对话跑偏之后，恢复现场零歧义（状态是引擎写的，指哪读哪）；同时暴露了一个逗号解析 bug，被引擎的严格校验当场拦下——这恰好证明"精确归工具"的价值：散文时代的这类错误会静默滑过去。这次 dogfood 还沉淀了一条编辑纪律进仓库指南："**先考证，后修复**"——当时我初判两个"缺陷"，考证后发现一个是契约里写明的既有语义、一个是记录在案的已知弱点，修复方案因此收窄。**看起来像 bug 的行为可能是故意的，改之前先查出生证明**；
2. **token 账本**：实测整个技能加载约 18 个文件、171KB（≈4.3 万 token），引擎带来约 +15% 增量，其中大头是引擎契约文档被放进了"每次必读"清单。考证后发现没有任何决策要求它必读——纯属改写时的分组惯性。把它改成按需加载后，引擎净增量压到约 +3~4%。同日评估了给 SKILL.md 本体瘦身，**全部暂缓**——因为按需化省下的 18.7KB 已经超过 SKILL.md 的引擎化净增，先摘低垂的果实，不为了优化而优化；
3. **一轮全面审查**修掉三个实质缺陷：
   - 工作流变更规程和引擎路由语义冲突（文档教的两类变更步骤会被引擎拒绝——因为"Skip 行恒胜 Execute 行"这类优先级规则只存在于引擎里，文档作者不知道）；
   - 截断状态（BEGIN 标记在、END 缺失）被误判为旧格式静默兼容（现在精确区分 legacy/corrupt，corrupt 直接报错给修复路径）；
   - CI 只查漂移不跑测试（引擎回归对 CI 完全不可见——测试套件补进 CI）。
   
   有意思的是其中两条"疑似缺陷"考证后被判为**故意设计**不改：Skip 优先级、jump 不绕过计划过滤——都是实施期裁决在案的。审查和"先考证后修复"再次形成闭环。

### 价值

- **状态从此有了唯一权威源**。走到哪一步、发生过什么，一查便知，不再依赖任何模型的记性。会话中断、换人、换机器，恢复动作都是同一个：跑一下 `status`。
- **每次转移都留痕**。审计日志由引擎原子追加，"这个需求为什么被打回过"这类问题有了可靠答案。
- **"改主意"有了正门**。完整性校验堵死歪路（不许手改状态），`jump` 敞开正门（正规改道通道）——二者是阴阳配套：缺了 jump，每次正常的需求变更都会以"完整性告警"的形态呈现，体验就裂了。
- **Phase 4 的死结解开了**。未来的多会话团队协作需要"锁"（防止两个会话同时认领一个任务），而锁的前提恰恰是"引擎必选、状态唯一写入者"。Phase 3 的这个决策等于提前给 Phase 4 铺了路。

## Phase 3.1：让 AI 记得住"上次做到哪"

**完成时间：2026-09-22**

### 遇到的问题：换个会话就"断片"

引擎解决了"状态在哪"的问题，但真实用户反馈很快指出下一个软肋（这条反馈价值千金，它直接催生了 3.1 和 3.3 两个版本）：

> 长会话跑到一半，新开一个会话说"从上次结束的地方继续"，结果**加载旧制品不完整，工作流跑偏了**。

有意思的是诊断结论：**路由没漂**（引擎管着呢，下一步算得清清楚楚），漂的是**执行层**。代码级考证找到三个断点：

1. **状态机的粒度是"阶段"，而中断发生在阶段内部**。引擎知道"当前在功能设计阶段"，但不知道这个阶段做到一半时停在了哪一步。而且没有"收尾"动作——中断不留任何痕迹。具体到代码：`cmd_status` 输出里没有任何子阶段信息，Unit Progress 区预留着但没启用；
2. **恢复协议是一份"必须全量加载"的散文清单**。旧规则写着"MANDATORY: 加载上一阶段全部制品"——平铺几十条、无优先级、无验证。这在物理上就执行不了（上下文窗口装不下），于是模型开始**抽样加载**，抽样就漏，漏了就偏；
3. **半成品无探测**。当前阶段的产物文件如果已经存在（上次写到一半），引擎一声不吭——模型不知道该接着写还是从头写。

立项同一天，我顺手调研了一个外部框架 **Trellis**，发现它押注的正是"状态保活"这个方向，验证了问题形态和解法方向（这部分借鉴到 3.2 展开）。

### 解题思路：泊车留条 + 分级阅读 + 第一代传感器

**第一件：`park`（泊车）动词。**

```
engine.py park --note "功能设计写到第 3 节，还差错误处理部分"
```

效果有两笔：

- 状态文件当前状态区写一行 `Last Parked: functional-design —— 功能设计写到第 3 节……`（计入完整性指纹）；
- 追加一份交接文件 `aidlc-docs/handoff.md`（引擎独写、只增不删、永不参与完整性解析）。

四个关键设计，每个都值得琢磨：

- **泊车不是转移**——它不动阶段指针、不勾任何勾选框、**不写审计**。为什么审计要"分家"？审计是"转移账本"，只记阶段变化，天然有界；如果把每次泊车也记进去，日志无限膨胀，每次操作前的交叉核验成本随之上涨。泊车记到专门的交接文件里，各走各的账。这个决策当时看是小优化，后来 Phase 5 讨论"审计分段"时才发现它是提前消解了一颗雷；
- **写序固定：先状态区、后交接文件**。崩溃窗口被压缩为"交接文件缺一条历史"——而状态区（权威源）永远不缺。宁可少一条冗余，不可丢一次权威；
- **便签卫生**：必填、换行折叠成分号、截断 300 字符——防住"一部长篇小说塞进一行状态"的滥用；
- **转移自动作废便签**：一旦发生 report/jump，`parked = None`——你已经重新上路，旧便签没意义了。而 rebase 会保留可解析的便签行（修复不该丢注记）。

**第二件：`status` 升级成"恢复简报"。**

新会话开局跑一次 `status`，引擎返回的不只是"当前阶段"，还有一组恢复专用键：

- `resume_note`：上次泊车的便签（有就给，没有就空）；
- `note_age_seconds`：（Phase 3.3 加）便签贴了多久——只报客观数字，判不判断"过时"留给模型；
- `recent_events`：最近 5 次阶段转移，从**审计日志尾部**提取——这个数据源一直躺在那，过去没人用。实现上有个讲究：解析器被限定只在审计的 `## Engine Transition` 节内找事件行——因为审计里还允许记录用户原话，不限定节的话，用户输入里恰好出现 "Event:" 字样就会伪造历史；
- `artifact_alerts`：**传感器读数**（下面细讲）；
- `audit_entries` / `audit_bytes`：审计计数——为将来的"审计分段" contingency 提供触发度量（512KB 阈值），顺手输出零成本。

配套地，恢复协议从"全量加载"改写成**三级阅读**：

| 级别 | 读什么 | 为什么够 |
|---|---|---|
| 第 1 级 | 引擎输出（状态 + 便签 + 近期事件 + 告警） | 引擎是权威，几十行读全 |
| 第 2 级 | 下一步指令里声明的必需上游产物（`consumes`） | 只读马上要用的 |
| 第 3 级 | 按需查"产物地图"（生成区维护的查阅表） | 地图是"哪里有什么"，不是"加载清单" |

**第三件：第一代传感器（artifact_alerts）。**

引擎在 `status`（恢复时）和 `report`（收单时）两个时机做检查，两类检查采用**不对称语义**：

- **missing-produces（缺产物）**：已完成的阶段，声明的产物文件在不在？——只有当某阶段有 **2 个以上"具体产物"且全部缺失**时才告警。为什么这么保守？考证发现很多产物是**条件性**的：RA 的问题文件只在"有问题"时生成；B&T 的 4/8 个产物标着 As-Needed；基础设施设计的唯一具体产物本身是条件产物；WD 的产物恰好就是引擎文件（必然存在）……单个产物缺席，分不清是"条件不满足"还是"真忘了"。**宁可漏报，不可误报——误报会训练用户无视告警**，那是比漏报更糟的失败模式；
- **resumed-artifacts（半成品残留）**：当前阶段的产物文件如果**已经存在**，提醒"可能有半成品，先读再写、能追加别重写"。存在信号的误报代价低（"先读后写"本来就是正确动作），所以语义反过来：任一存在就提示，封顶 5 条。

传感器的整体纪律有三条，条条都有出处：

1. **fail-open（失效放行）**：探测过程出任何异常，返回 `alerts_unavailable: true` + 空数组，**绝不阻断正常流程**。传感器可以坏，大门不能锁死；
2. **告警不带强制力**：每条告警带一个"处置纪律"字段（`action_discipline`），明确写着"报告用户，不要自作主张去补制品"。这是防**古德哈特定律**——当告警变成任务，模型就会为了消除告警而编造产物；
3. **引擎自有文件不参与检查**：状态文件和审计文件必然存在、零信号价值，排除后 WD 阶段自然豁免。

**两条新决策（写进了项目的决策记录，编号 D13/D14）：**

**D13 动词三层纪律 + 注记转移不变律**：引擎动词分三层——读（无副作用）、**转移（report/jump，封闭集合 = 唯二改变阶段指针的动词，今后永远不再新增第三个）**、生命周期（init/park/rebase，park 是注记子类）。"转移不变律"：注记动词必须保证指针和勾选零变化（重算指纹不算转移）。以后每加一个新动词，入场券是"和全部既有写动词的两两交互测试"——**交互矩阵自此成为 CI 的法定成本**。这条纪律是为了防止动词集随版本膨胀最终失控：十个动词的两两交互是 45 对，二十个动词就是 190 对——晚管不如早管。

**D14 传感器 fire 点与 finding 接口**：传感器的触发点永远锚定在引擎动词上（status=恢复时 / report=收单时），永久不变——这是 harness 无关性使然（我们没有写入钩子，只有模型调引擎时才有代码执行的机会）。告警对象固定五个字段 `{type, severity, subject, message, action_discipline}`，字段集只增不删、同一状态版本内形状永不破坏性变更——这成了 Phase 5 传感器体系的正式接口，今天的第一代实现（硬编码清单）将来升级为 manifest 化时，必须通过"固定夹具下输出逐字节一致"的等价测试。**换心脏不换接口**。

### 结果

测试 102 → 141 → 144 全绿。新增的测试覆盖很有代表性，列几类感受一下密度：

- ParkTests 约 9 例：泊车写入且审计零新增 / 指纹自洽 / 指针不动 / 便签卫生（换行折叠、截断）/ 无状态与完成态的拒绝 / 去重两分支 / 转移清除 / **写序用 mock 断言"状态区先于交接文件"**；
- 反误报六连：RA-minimal 无问题文件不告警 / B&T 缺 e2e 不告警 / 基础设施设计 N=1 豁免 / 运营阶段 N=0 豁免 / WD 初始态无残留告警 / RA 单缺不告警；
- 交互矩阵 4 例：park × report、park × jump --stage、park × jump --fresh、park × rebase（D13 纪律的第一次兑现）。

两轮审查又抓出并修掉 3 处应修项——最典型的一个：某个旧文档（workflow-changes）残留着"恢复时读取全部已完成阶段的产物"旧指令，和新分级阅读直接打架——**全量加载时代的遗物**。这类问题说明：改协议必须全树清扫，改一处漏一处，模型就多一分精神分裂。

### 价值

- **"换会话继续"从碰运气变成确定性操作**。泊车一秒留痕，恢复三级阅读，半成品有预警。
- **审计账本天然有界**——分家设计让它永远保持小而快。
- **传感器体系有了第一块基石和正式接口**。Phase 5 要做的"制品自检清单"将直接复用这套接口。

### 诚实边界：park 防不了"强杀"

写到这里必须主动交代 park 的边界，因为它经常被问：**如果模型正在思考时强行关闭 harness，再新开会话继续——park 能生效吗？**

答案是**不能**，而且不是实现疏忽，是记录在案的取舍（负债清单第⑥条原文："未 park 且当前阶段零制品的中断不可探测——**park 是自律层，非传感器**"）。

原因很根本：park 是模型的**主动自律动作**。泊车仪式定义的三个触发时机——用户说停、话题要切换、预感中断——全部要求模型还有一轮行动的机会。强杀 harness 是唯一不给任何窗口的场景：`park` 命令永远不会被发出。而"进程被杀"这个事件本身，在 harness 无关的世界里**没有任何手段能捕获**——传感器的触发点只能锚定在引擎动词上（D14），因为只有模型调用引擎时才有代码执行的机会。v2.0 靠 opencode 的钩子能多做一点，我们刻意不换——这又是"可移植性 vs 自动化程度"的交换。

但强杀之后并不是全丢。新会话跑 `status`，恢复精度分层：

| 信息层 | 强杀后 | 靠什么 |
|---|---|---|
| 阶段级位置（在哪个阶段） | ✅ 完好 | 指针来自最后一次 report/jump，引擎原子写 + 指纹校验 |
| 时间线（最近发生了什么） | ✅ 完好 | recent_events 从审计尾部取最近 5 次转移 |
| 精确断点（阶段内做到第几步） | ❌ 丢失 | 本来靠 park 便签提供 |
| 半成品探测 | ⚠️ 视情况 | resumed-artifacts：中断前已写出一部分制品文件就告警 |

真正的盲区收窄到一种情况：**中断发生在当前阶段还没写出任何制品时**。改善路径已经排期：Phase 4 的单元级检查点会在更细粒度上留痕。

我一直觉得，"一个机制防不了什么"比"它能做什么"更能说明系统的成色——这条边界和它的兜底方案、改善排期，在项目文档里是同一页纸上的三行字。

## Phase 3.2：隔壁框架的好东西，搬机制不搬代码

**完成时间：2026-09-22（同日立项、同日完成）**

### 遇到的问题（或者说：遇到的机遇）

3.1 立项同一天，我顺手做了一次外部调研：考察了另一个 AI 工作流框架 **Trellis**。它和我们是同一个哲学（也是"判断归 LLM、精确归工具、决定归人类"），但押注的方向不同——我们押"阶段路由的确定性"，它押"状态保活与知识复利"。正因如此，它山之石特别多：同一个问题的正交投影，能看到我们视角外的解法。

调研产出了四档借鉴清单：

| 档位 | 含义 | 项数 |
|---|---|---|
| ① 立即搬 | 当天立项当天落地 | 5 项 |
| ② 排期搬 | 挂到未来某个 Phase | 3 项 |
| ③ 相位触发 | 等某个 Phase 设计时再核对 | 8 项 |
| ④ 仅记录 | 写下触发条件，出现再议 | 3 项 |

3.2 这个"立即批"承载①档全部 5 项 + ②档 2 项，**原则是搬机制、零代码复制**——学的是思路，落的是自己的实现。这个原则值得强调：直接抄代码会把别人的架构假设一起抄进来（Trellis 的触发机制依赖它的钩子系统，我们没有），只有理解"它为什么这么做"之后用自己的语言重写，借鉴才成立。

### 实施前插曲：三轮审核的方法学

这个批次本身不大，但它的**计划审核过程**成了一个方法学转折点，值得单独记录。

计划写完后我派了多轮独立 reviewer（审核子代理）审，模型各不相同：

- **R1（引导性提示词）**：1 阻断 + 6 应修 + 8 建议。微观精确度高——连"指南自带的示例和自己的规则矛盾"这种细节都抓到了；
- **R2（中性提示词，换模型）**：1 阻断 + 7 应修 + 4 建议 + 6 项独有建议。系统思维最强——独有发现包括"四档借鉴清单没有来源出处""消融对照在当前架构下违宪（引擎必选，无引擎对照组根本构造不出来）""批次串行理由与实际改动面不符"；
- **R3**：因服务中断两次未完成，放弃；
- **R4（新 reviewer 定义首跑）**：1 阻断 + 7 应修 + 6 建议。首次出现了"核对通过项"的正向确认节和"不可核验范围"的显式声明。

**方法学副产物**：比较 R1 和 R2 发现，**中性提示词优于引导性提示词**——R2 在没有预埋任何线索的条件下覆盖了 R1 的全部发现，且增量发现更重（都是系统性问题而非细节问题）。引导性提示词（"请重点检查 X 是否正确"）会把审核方的注意力锚定在你怀疑的地方，而你怀疑的地方往往不是真正的雷区。

这个发现直接改变了我此后所有批次的审核方式：**给 reviewer 的提示词只包含三样东西——制品位置、背景、中性开放问题；疑似问题单独列为"待验证主张"并标注来源，绝不预埋为结论**。

### 实际方案：七个工作包

**WP-1 Evidence-First 提问纪律（证据优先）。**

过去规则里到处写着"拿不准就问用户"，结果 AI 拿着**代码库里明明有答案的问题**去烦用户（"这个项目用什么数据库？"——配置文件里写着呢！）。新的纪律写在提问规范的最顶部，带优先级条款：

> **凡是可以靠探索代码库/制品回答的问题，必须靠探索解决并引用出处，不进问题清单。** 这条纪律的优先级高于各阶段文件里一切"when in doubt, ask"类指令。

配套豁免表（纪律必须有边界，否则会误伤）：scope 选择聊天问题（本来就是和用户协商的）、扩展 opt-in 问题（问的是用户偏好，探索不可解）。再加两个配套改造：所有选项题在"存在推荐项"时必须给推荐理由 + "如果你另选会怎样"的代价说明；9 个文件做了系统性收口（每处"积极提问"指令旁边都加上了"先过证据门"的限定——又是全树清扫，和 Phase 3 收口状态指令同款操作）。一句话：**把用户的注意力当成稀缺资源来花**。

**WP-2 dogfood 协议。**

过去"自我试用"没有章法，试用完只能说"感觉不错"。新的协议文档定义了六条度量：

1. 重复解释次数（→ 审计条目趋势）
2. 需求文档范围清晰度（→ 定性评估）
3. 重复评审次数（→ rejected/revised 趋势）
4. 换工具稳定性（→ 引擎 JSON 一致性）
5. 新人首任务独立完成度（→ 定性）
6. RCA 问题沉淀率（→ 知识树落地后生效）

数据源全部取自引擎已有的客观记录。还有一条诚实声明我很喜欢：**消融对照（"没有引擎会怎样"的对照组）在当前架构下无法构造**——因为引擎已是必选组件，拆掉它工作流根本不启动。所以对照只能用"历史版本对比"和"引擎内开关对比"替代。**承认实验设计的局限，和做实验本身一样重要**——这条声明后来在双臂验收（最后一章）又被引用了一次。

**WP-3 长制品导航索引（DOC-06）。**

规则：超过 300 行的内容制品，顶部必须维护一张"任务→章节"导航表，覆盖全部二级标题（可机械核对）。注意它是 **advisory（建议级）**而非阻塞级：违反了只列出来、不拦门。理由是"缺失无危害，但阻塞级告警会训练用户无视告警"——和传感器的保守哲学一脉相承。这个"全库唯一 advisory 规则"的定位当时只是个小决定，后来在活文档增长观察（D15 之后）里反复被引用——因为它是唯一没有硬触发器的文档卫生机制。

**WP-4 构建与测试阶段的提交协议（Commit Protocol）。**

AI 帮你写完代码，最后一步提交（git commit）怎么管？时序定死：

```
门批准 → 引擎记账（report approved）→ 完成消息里呈现提交计划
→ 你说"继续"（Approve & Continue）= 阶段批准 + 执行提交的授权 → 执行提交
```

注意顺序里藏着的谨慎：**提交计划必须先呈现在完成消息里，"继续"才是对它的授权**——不能反过来"批准后才看到要提交什么"。提交计划的内容纪律六条：只提交本次会话工具实际写过的文件（判定依据是工具调用记录，绝不静默夹带）；一次性展示完整计划；禁止 amend、禁止 push（除非你明说）；不是 git 仓库就标注跳过；提交计划与确认结果进审计，hash 记入测试报告；自主模式下**绝不自动提交**，只列清单等发话。

**WP-5 逆向工程阶段的可选产物。**

棕地项目（在已有代码库上工作）做逆向工程时，可以产出一份"工作约定"文档（working-conventions.md）——关键是**每条约定必须带来源引用**（从哪个文件的什么情况总结出来的），拒绝空话。它同时被定位为未来"知识树"（Phase 5A）的种子：防止将来出现两套平行的约定存储。实现上有个巧劲：它的落点在 RE 既有的通配产物声明（`inception/reverse-engineering/*`）之内，**自动进入会话加载清单和传感器探测范围，frontmatter 零改动**——数据模型的弹性又一次兑现。

**WP-6 契约硬规则单测清零。**

Phase 1 的阶段契约定义了 16 条校验规则，其中 13 条一直没有专门的单元测试（另外 3 条已有间接覆盖）。本批补齐 25 个测试，13 条规则全覆盖，还用"保留字段夹具"锁定了"预留但不启用的字段"（reviewer/sensors）不会被误伤——给未来留的门，用测试守住。实施中还发现一条规则的实际校验点在另一个函数里——按实际实现写测试，行为与契约一致，零出入。

**WP-7 落档。** 把四档清单正式登记进决策文档（加"状态"列），Phase 5 拆写为 5A/5B，Phase 4 节末挂上设计输入清单——**借鉴来的东西必须有名有姓有去向**，否则三个月后没人记得某条规则为什么存在。

### 结果

七包全部同日完成（并行分发了三个执行者子任务，强耦合的主包我自己做）。测试 144 → 169 全绿。全树扫描确认没有互相矛盾的指令残留。实施后又两轮审核（通过 + 复审通过），期间的典型修复：提交协议的时序表述被发现有歧读空间（"批准后才呈现计划"的错误读法），重排为无歧义版本并回改历史记录。

### 价值

- **提问质量**是这个批次最直观的收益：问题清单变短了，每个问题都带着"我已经查过什么"的诚意。
- **自我验证有了章法**：后续每个版本的"好不好用"都有了数字可看，而不是体感。
- **提交安全**：AI 再也不会背着你在 git 里夹带私货。
- 方法论上验证了一件事：**跨框架借鉴的正确姿势是"机制移植"**。零代码复制，全部原生。

## Phase 3.3：真实项目验收之后，把教训变成机制

**完成时间：2026-09-24（同日立项、同日完成）**

### 遇到的问题：验收一个真项目，暴露的真问题

3.2 落地的 dogfood 协议，服务的第一个完整周期是一个真实项目：一个计算器应用（代号 fx991，模拟卡西欧 fx-991，跑了两个迭代）。验收通过了，但验收的价值全在细节里。

**第一笔账：一项悬而未决的旧决策有了答案。** 3.1 做的"缺产物软警告"要不要升级成"硬阻断"（升级 = 缺产物直接拒绝转移）？两个迭代里它**一次都没触发**——因为这个传感器的定位就是"灾难检测"（N≥2 全缺才报警），正常流程天然碰不到。而实际观测到的制品类问题（检查点遗漏、审计误替换、计数不准）都在它的管辖之外。**加严现有警告对已观测问题零解**——于是裁决：不升级，关闭。同时诚实声明：这是"无证据支持升级"的保守裁决（0 触发 = 无正例），后续周期出现新证据可重开。

**第二笔账：三处"记录表定性偏差"。** 验收时对照引擎代码核实我自己的验收记录，发现三处描述失真。有意思的是它们的共同点：**全部是"模型对规则文本的引述失真"**——规则就在那里，模型（包括做验收记录的我）复述的时候走样了。例如一处记录说"强制扩展未说明"，查证后发现规则在 SKILL.md 里声明得好好的，真因是**加载流程的编号步骤没有覆盖到那段规则**——"规则存在"和"流程会经过它"是两回事。

由此沉淀出本批的批次原则，我认为它值得单独抄下来：

> **修法优先选择"把正确行为变成最省力的路径"（一个流程步骤、一条命令），而非追加规则条文。**

规则越写越多，模型引述失真的面就越来越大。与其教它背更多，不如让正确做法顺手得不像故意。

### 实际方案：六个工作包

**WP-1 引擎扩展（四件小而锋利的工具）：**

- **`stamp`（盖章）动词**：零副作用的权威时间戳——跑一下，返回引擎级 UTC 时间。为什么需要它？过去审计条目的时间戳由模型自报，模型时钟不可靠（模型的"现在"来自训练数据的语感，不是系统时钟），条目可能出现**时序倒挂**（后面的事记录成更早）。现在审计规则改为：时间戳优先取同一次交互里引擎输出的 `timestamp` 字段（任何引擎调用都带），实在没有才专门跑一次 `stamp`，条目还要附来源标注 `(engine|stamp|clock)` 使合规可核验。按 D13 分类它落**读层**——零写入、零副作用；
- **`status` 新增 `autonomous` 键**：把状态文件里模型手写的"自主模式"配置区读出来（宽容解析，读不懂就返回空，绝不连累 status 本身）。第三条"模型写、引擎读"通道；
- **泊车便签附年龄**（`note_age_seconds`）：只报客观数字，判不判断"过时"留给模型。一条旧便签可能已经不再反映现实，年龄是最便宜的风险提示。实现上还有个守卫：交接文件尾条必须与当前便签对应，不符返回空——防止"读了别的工作区的旧账"；
- **checkpoint-missing 告警**：检测"该有阶段检查点的地方没有检查点"（仅当扩展配置表显示 CTX 启用时才查，表缺失视为未启用，fail-open 不变）。

**WP-2 强制扩展发现步骤。**

dogfood 暴露的流程漏洞（上面那处"规则在、流程不通"）的修法正是批次原则的示范：给加载流程补一个**机械可执行的第 4 步**——"列出各子目录全部规则文件，减去有 opt-in 伴随文件的，剩下的立即加载"——而不是加一条"别忘了某某"的叮嘱。前者是算法，后者是祈祷。

**WP-3 范围收缩规程（工作流变更家族新增 Type 10）。**

真实项目里发生了"砍需求"：做到一半，一批功能要撤掉（计算器砍掉了科学计算模块）。当时的操作（在关卡如实报 rejected → 跳回最上游受影响阶段 → 就地修订 12 处文档 → 重走全链）被实践验证有效，本批把它固化成正式规程。几个考究的细节：

- **问答/决策历史文本受保护不得改写**——历史就是历史，只能追加修订说明（这条后来演化为 DOC-04 规则，D-清批还会提到）；
- **Deferred（推迟）的编号永不回收**：FR-30 被推迟了，将来新需求就从 FR-35 开始编——追溯链永不断裂。"砍掉的需求"和"没提过的需求"在编号空间里必须可区分；
- 决策树补全分支：审核发现"最上游受影响阶段恰好是当前阶段"时跳转必被引擎拒绝（jump 不绕过计划过滤），规程补了"跳过跳转、就地修订重走本阶段关卡"的分支——**一个连真实项目都没暴露的边界，被静态审核抓了出来**。

**WP-4 文档判例与自证治理。**

给"redo 时哪些文本受保护"补了正反判例（问答历史 vs 计划清单行的二分）；清扫类声明（"我检查过全仓库没有 X"）从今往后**必须附上所用的搜索模式和扫描范围**——否则就是自说自话。这条的动机很实际：模型的"我检查过了"零成本，声明不绑定证据就等于没有声明。

**WP-5 追溯矩阵脚本。**

`scripts/trace-matrix.py`（纯标准库，作者期工具，不进 CI）：读需求文档的 FR 编号与推迟标记 + 用户故事的追溯映射表，输出三样东西：FR 覆盖矩阵、计数核对（声明数 vs 实际解析数）、Deferred/Reserved 保留核对。用真实数据冒烟：FR 总数 29（24 生效 + 5 推迟），和项目文档自述完全一致；4 条推迟的故事和修订记录吻合。实现中有个真实数据的坑：追溯行里出现 `FR-30~34` 波浪号范围，初版静默只取首号——改为范围展开（上限 50 防滥用）+ 超限维持旧行为 + 测试更新。**工具的边界行为要在真实数据上冒烟才知道**。

**WP-6 提问工具能力抽象。**

dogfood 之外顺手修了一个 harness 无关性违规：规则里写死了 OpenCode 的 `question` 工具名——换个工具（Claude Code 的等价物叫 AskUserQuestion，有的工具压根没有）就对不上了。改法不是枚举工具名，而是**按能力特征定义**：

> "凡能在同一次交互里呈现一组带选项的问题并收回答案的工具，无论何名；按能力特征识别，不按名字匹配。"

具体参数（每题一条/短标题/选项短标签+说明/推荐项置首/单选多选）全部改成语义要求，调用时适配。8 处文档同步。这条的普适价值：**写规则时描述"需要什么能力"，而不是"用哪个产品"**——产品会换，能力不会。

### 结果

单日完成全部六包（主包自做，三路并行分发执行者，逐个 diff 复核）。执行者复核环节本身也立了功：揪出两处清单外残留（AM 文件与 QT 新规则的语义张力）和一个继承语义 bug（追溯矩阵把 US2-25 误继承 US2-24 的推迟标记——裁决为"继承源仅限节级标题，不含条目 ID"，发回原会话修复 + 反例单测锁定）。**169 → 205 个测试全绿**；`--check` 零漂移；真实数据冒烟通过。

随后一轮独立全面审查：0 阻断、1 应修、6 建议，全部当天修复——包括波浪号范围那个坑、`_note_age_seconds` 的尾条对应性守卫、AUD 回退触发条件的自相矛盾改写。

### 价值

- **时间戳从此权威**，审计的时序可信。
- **砍需求有了合法通道**，且历史不可篡改、编号永不复用——这两条对"项目记忆"的价值会随时间复利。
- **多会话前的最后加固**：这批修的每一个问题（恢复、审计、时间戳、砍需求），到了 Phase 4 的多会话团队场景都会被放大。先在单会话里钉死，是给未来上保险。

## 完成态再入修复批（D15）：MVP 做完了，然后呢？

**完成时间：2026-09-27**

### 遇到的问题：想加个功能，AI 却把一切都归档重来

fx991 计算器的 MVP 全流程做完之后，我新开了一个会话，说"加一个新功能"。模型的操作是：执行 `jump --fresh`——**把整个文档树归档封存，从零重建一套**。

表面上看这不算"错"（毕竟引擎允许这个命令，归档也不丢数据），但代价很大：

1. **功能需求编号重置**：迭代一的 FR-1~FR-5 和迭代二重新从 FR-1 编起，跨迭代的追溯链断了——"这个功能是什么时候加的、为什么加"再也对不上账；
2. **迭代一的上下文被封存**：新流程默认不读归档目录，需求文档、用户故事里积累的理解全部作废，相当于一个失忆的接班人；
3. **逆向工程产物被一起搬走**：迭代二大概率要重跑一遍对既有代码的逆向分析——纯浪费。

### 根因诊断：一条"四环链路"

这次的诊断过程堪称本项目最好的一次"破案"。逐处代码考证后发现，模型走到 `--fresh` 不是偶然，是被**四条路径合流推过去的**：

1. **引擎的"教唆现场"**：完成态（当前阶段为空）收到 `jump --stage` 会被拒绝，而错误提示里"好心"地指路："工作流已完成，如需重来请用 jump --fresh"——park 的完成态错误也是同样话术。模型试错时按提示走，一走一个准；
2. **主文档没有路由**：SKILL.md 对完成态只有一句"开始新东西前和用户确认"，没说确认完该走哪条路；
3. **恢复菜单的暗示**：菜单 A 空转（"工作流已完成"）、B 是导航框架、**C 是唯一写着'开始'的选项——而 C 就是 Start Fresh**。排除法都会选到它；
4. **变更规程的域限定**：workflow-changes.md 的标题和概述写着"Mid-Workflow"（流程**中途**的变更），严谨的模型不会把完成态的新需求往"中途变更"上套。

四环合流的结论：**模型无论主动选择还是试错（先试 B 被拒、按提示走 C），必然收敛到 `--fresh`。不是模型不守规矩，是系统把它推过去的。**

这个结论改变了解题的性质。如果原因是"模型不守规矩"，修法是加规则、加惩罚；如果原因是"系统把它推过去的"，修法是**修系统**——把正确的路修通、把错误的路标拆掉。这次是后者。

### 解题思路：同一产品的功能演进，不是"新产品"

用户裁决（记为 D15，写进决策记录）：

> **同产品的功能演进（新功能/修复/需求变更）不是新产品意图，应走"就地再入"**——跳回最上游受影响的阶段，目标及其后的阶段重置为待办，原地修订、重走下游。`jump --fresh` 保留给两个真场景：新产品意图，或用户显式要求干净重启。

这也让一条更早的原则（D11）落了地：**一个 git 版本就是一个产品意图**，版本边界由 git 提交承载；同产品多迭代 = 同一意图下的多个版本。`aidlc-docs/` 文档树是跨迭代共享的"活文档"，不是每轮一份的快照——历史在 git 里，现状在文档树里。

### 实际方案

**引擎**：完成态收到 `jump --stage <slug>` 从"拒绝"改为"放行为再入"——方向按回跳处理、目标及其后所有阶段勾选重置为未完成、审计条目记 `re-entry`（含 "from complete (backward)" 注记）。早先为防误操作定下的"jump 不绕过计划过滤"对再入同样生效：跳到计划外的目标照样执行但附 note 提示。

**实施中发现的真实语义**（测试首跑失败才发现，记录在案）：如果模型先删掉状态里的 Skip 行，工作流会通过既有通道**自行复活**——引擎每次调用都按计划行即时重算指针，删掉 Skip 行后第一个待办阶段自动成为当前阶段，根本不需要 jump。所以再入分支覆盖的其实是"全做完"场景，**两条通道并存**，规程把两条都写了（还配了防呆提示：对已成当前阶段的目标再 jump 会被拒——先删行就直接 `next`）。

**四处文档现场同步修复**（对应四环链路的 2/3/4 环 + 引擎提示改写拆掉第 1 环）：

- SKILL.md 的完成态行补路由，并明示"同产品迭代禁止用 Start Fresh"及理由；
- 恢复菜单 C 的定位收缩为 "for a new product intent … **NOT** for a new iteration"；
- 变更规程的适用域从"流程中途"扩展到含完成态，新增"Re-Entering a Completed Workflow"完整一节（分类 → jump 最上游受影响阶段 → 就地修订 → 重走）；
- 错误恢复文档把"需求大变 → 建议 Fresh Start"的旧条款移出——**这条逐字是 v1.0 的原始文本**，是四环链路之外被审核揪出的"第 5 现场"（上游原始缺陷的又一次隔代遗传）。

测试 205 → 209（新增再入主路径、再入首阶段、再入计划外目标、再入后 park 可用四例 + 两个驱动辅助函数）。

### 审核与验收

独立审核 0 阻断、1 应修、6 建议，全部当天修复。修复清单里有几个值得一看的：

- 计划外目标测试补三断言，钉死"跳转后指针落在其后第一个路由内待办阶段"的精确语义（审核发现原断言过弱，语义回归仍可能绿——**测试断言的强度要匹配语义的精度**）；
- 引擎 jump 的 note 文案补前提："若目标在 Stages to Skip 行则先删——Skip 恒胜 Execute"（一个提示文案的精确性，省未来一次调试）。

真正的验收在四天后：fx991 迭代 3（第 10 章详讲）端到端复现了正确行为——新会话正确选择原地再入，审计记录写着 "from complete (backward); re-entry"，RE 未重跑、FR-6/US-12 续编、无新归档树。

### 价值

- **"做完再加功能"从此成为一等公民操作**。软件的常态就是迭代，工作流必须善待迭代而不是惩罚它。
- **一次方法论示范**：当 AI 的行为系统性出错时，先查系统是不是把它推过去的，再考虑加规则管它。四个"教唆现场"拆掉三个、堵住一个，行为立刻正确——零新增禁令。

## 一次冷静的设计追问：活文档会不会"爆炸"？（2026-09-28）

D15 落地次日，我追着一个问题不放：**所有迭代的制品都集中在同一棵 `aidlc-docs/` 树里，文件和文档长度会不会随迭代数"爆炸"、拖垮 AI 的上下文？** 这一章没有产出代码，但产出了一条重要的思考记录——它示范了"用复杂度语言思考"和"不过早设计"。

### 分析：三笔账

**第一笔：文件数。** 增长 = O(功能数)，**不是** O(迭代数)。固定路径的活文档（requirements.md、stories.md、B&T 的 8 个固定文件等）跨迭代**原地更新**，文件数恒定；只有按单元组织的目录（`construction/{unit}/...`）随单元数增长。反倒是 D15 之前"归档旧树 + 新建"的模式，才是 O(迭代数 × 全文件) 的爆炸路径——**D15 恰恰是消除文件爆炸的那个决策**，我担心的正是它刚消灭的东西。版本历史交给 git（B&T 提交协议定死了时序），磁盘不留快照。

**第二笔：上下文。** 目录变大不等于上下文变大，中间有三道闸：

1. status 恢复简报只返回**异常发现**，不返回目录清单；
2. 分级阅读第 2 层只加载当前阶段的**必需上游产物**，且圈定细到单元（代码生成只读当前单元的设计目录）；
3. 第 3 层按需查导航索引（DOC-06）。

**第三笔：单文件。** 这才是真实的残余风险所在，两条：

- **单文件单调增长**——stories.md 这类"现状型"制品按契约**只增不减**：砍需求时推迟条目永久保留、修订记录只追加、DOC-04 保护历史文本。增长正比于历史功能总数（含推迟的），粗估 15-20 个故事就过 DOC-06 的 300 行阈值——而 DOC-06 是全库唯一 advisory（建议级），没有硬触发器；
- **B&T 全单元 consumes**——构建与测试要读**全部单元**的代码，是唯一输入随产品规模线性增长的阶段，单元数大时最先痛。

### 裁决：不过早设计

结论是**不立即设计压缩规程**——避免为未被实证的担忧写规则。挂了一个观察项，触发条件写死：核心活文档过 500 行，或再入/设计场景全量读产生可感知的上下文压力。届时方向也已想好：**rollup**——已交付且稳定的条目压缩成一行索引（编号 + 标题 + 一句话 + git 提交指针），编号永不回收（与 Deferred 编号纪律同构：编号是追溯链的锚，内容可以蒸馏，锚不能动）。

> 后来的部分验证：fx991 的 requirements.md 出现了**自发的** rollup——已交付的 FR 被压成一行摘要 + git 提交指针 + 编号永久保留，和预设方向同构。这说明方向想对了；也说明在证据出现前不动手是对的——真实需求自己长出来的形态，比预先设计的更贴合。

### 同日的第二场考古：v1.0 的备份遗产

顺手追问了一个问题：原始 v1.0 是怎么处理历史制品的？git 考古（回到迁移基线 `fc17ad5` 逐处查证）的结论很干脆：**v1.0 根本没有归档机制，只有"在原文件旁边放一个 `.backup` 副本"的惯例**——全库 6 处 archive 提法全部是这个意思，没有集中归档目录、没有清理规则、没有迭代概念、"重来"靠模型手改状态文件。

分叉里还残留 5 处这种写法（错误恢复文档 2 处、变更规程 3 处），和"git 承载版本边界"的 D11 相抵，三宗罪：`.backup.{timestamp}` 是一个**平行的第二历史层**（git 之外又一套版本史，无生命周期管理）；目录污染原样潜伏（v1.0 时代的原病）；传感器干扰（引擎的半成品探测按通配展开，`.backup` 文件会被计入命中、挤占告警上限）。

于是立项"**备份遗产清理批**"，立场是校准而非全盘废除（非 git 工作区里破坏性重做前做轻量备份仍有真实价值）：条款改条件式——git 工作区 → 当前状态先 commit 承载历史；非 git 工作区 → 保留手动备份；引擎探测排除 `.backup` 文件。

**截至今天，这个批次已立项、规格已审、尚未实施**——它是我诚实的待办清单上的第一项。写在这里也是提醒自己：登记了不等于做完了。

## 自主模式的"过期"问题（D16）：开启一次，不能代代相传

**完成时间：2026-09-28**

### 背景：什么是自主模式

先补一个背景：**自主模式（Autonomous Mode，下称 AM）**是分叉早期自建的一个 opt-in 扩展，一组编号规则（AM-01 起）。你对 AI 说"激活自主模式"，之后：

- 遇到澄清问题，AI 自动选择推荐答案（不再每题都问你）；
- 遇到审批门，AI 自动批准（不再每门都停）；
- 一轮工作流从头跑到尾不需要人盯。

它解决的是"我就想让它跑完，别每一步都问我"的场景——和"决定归人类"的关系是：**自主模式是用户一次性授权的委托**，授权本身就是一次人类决定。状态文件的上半区（模型辖区）有一个 `## Autonomous Mode` 配置区记录开关和相关配置。

（AM 在这一章之后还会经历两次简化——D17/D18——所以这里记住它"最初的样子"就行：激活时问两个问题[问题怎么处理 + 哪些阶段保留人工审核]，配置持久化在状态文件里。）

### 遇到的问题：权限没有生命周期

dogfood 再次立功，实证了一个持久化缺陷（fx991 迭代 2/3 都踩中）：状态里的 `Enabled: Yes` 在工作流完成后**没有任何人把它翻回 No**。下一个迭代（无论再入还是新会话）会毫无询问地恢复自主模式，还沿用上一轮的问题处理配置。

一句话：**"开启一次、代代相传"**。

这违背直觉：我上一轮开了自主，不代表这一轮也想自主。尤其迭代之间往往换了会话甚至换了人——权限静默继承比权限泄漏只是好听一点。而且这不是理论担忧：迭代 2/3 的实际记录显示，新会话真的就带着上轮配置自主跑下去了。

期望语义：**AM 持续到当前工作流完成或用户显式停止；新迭代默认关闭；重新开启必须重新问配置。**

### 三项用户裁决

1. **过期动作放引擎侧**：完成转移时由引擎确定性翻转开关，不依赖模型合规——"精确归工具"哲学的直接应用。什么时候过期是个**事实问题**（工作流完成没有），事实问题就该工具管；指望模型记得去关，就是把精确活派给判断层；
2. **存量自愈放在再入跳转分支**：一并翻转，顺带覆盖"已完成 + Yes"的旧工作区——修复机制要能自愈存量，否则每个老用户都要手动踩一遍坑；
3. **暂停即彻底关闭**：恢复需要重新激活、重新问配置，废除"挂起可恢复"的旧语义——半开不开的权限状态最容易出事（"到底还自不自主？"每一步都要猜）。

### 实际方案

**引擎侧**：新增 `_expire_autonomous` 宽容翻转函数，挂在两个**轮次边界**上：完成转移（report 后无下一阶段）、再入跳转。所谓"宽容"：解析为开启的行（大小写不敏感）翻转为 No；区域缺失、畸形、已是 No——全部无声跳过（no-op），绝不因一个可选区的格式问题炸掉主流程。翻转实际发生时，确认回执带 `autonomous_expired: true`，审计条目附注记；没发生就什么也不带——**确认对象的键存在性本身就是信息**。

这个函数成了**引擎唯一一次写"模型辖区"的窄窗口**——状态文件所有权矩阵自 Phase 3 建立以来第一次出现"引擎写模型区"的例外。契约专门写了一节界定它：写什么（仅 Enabled 行 + 既存 Last Updated 行）、何时写（仅两个轮次边界）、以及诚实的边界——**触发互斥是纪律约定而非机制保证**（该区不在指纹里、没有锁，多会话并发同时翻转的彻底语义留给 Phase 4）。

**规则侧**：新增 AM-10（三边界规则：完成 = 引擎翻转 + 收尾宣告 / 再入 = 跳转翻转 + 自复活路径模型兜底 / 归档 = 随树消失）；AM-05 重写（暂停 = 优雅关闭的完整仪式：停止 → 泊车 → 审计 → 翻转 → 宣告 → 二选一[标准继续 / 重新激活]）；激活提问升级。

**自复活路径的兜底**值得一提：D15 那条"先删 Skip 行、工作流自行复活"的通道**不经过任何转移动词**，两个引擎翻转点都不会触发——审核把它列为阻断项，最终裁决是模型侧兜底（AM-10 要求任何方式开启新轮前确保 Enabled: No，模型翻转 + 审计）。不是所有洞都要用机制堵：这个通道本身是低频路径，为它上锁的成本（改引擎、改契约、二次修订所有权矩阵）超过收益，纪律兜底 + 记录在案是当时的正确取舍。

### 三轮审核连环抓漏

这批的审核轮次特别能说明"为什么要多轮"：

- **一轮（实施前计划审核）**：三条待验证主张全部证实；三个阻断项（自复活绕过 / 与 Phase 4 移出项的张力 / 残留引用 5 处）全部处置；
- **二轮（实施后审核）**：抓出 **B-1 前向跳转完成漏触**——前向 jump 越过中间阶段跳到末尾，可以把活跃工作流直接置为完成态（中间体标 `[S]`），但翻转的挂钩条件是"跳转前完成态"为假 → AM 不翻转。与再入分支"跳转后保持完成态仍翻转"不对称。修复 = 挂钩条件放宽为"跳转前**或后**处于完成态"，审计注记分流（re-entry / jump completed the round）；
- **三轮（修复后终审）**：对修复本体做矩阵推导（跳转分支 × 跳转前后状态的全部组合），证实新条件恰好覆盖无过度触达与漏触；但又抓出**契约文档 §6 残留"两边界"旧枚举**，与同文件 §8 的新表述相抵——B-1 修复时同步了三处文档，漏了第四处。

测试 209 → 224 → 226 → 227，每一跳都是审核发现驱动的。最后一轮还补了"(再入, 保持完成态)"矩阵格的显式用例——把审核时的推导固化成回归测试，推导才不会随时间失效。

### 价值

- **权限有了生命周期**："恰好覆盖当前这一轮"，轮次终点由引擎确定性收口。验收口径很干净：新轮起点 status 报 `autonomous.enabled=false` → 扩展存根不加载规则 → 标准模式；想再自主，必经一次显式激活。
- 架构上留了个注脚：这是"**扩展的精确部分才下沉引擎**"原则的第一次实践——过期的**时机**（精确）归引擎，暂停的**语义**（判断与授权）留在规则文本。这条原则后来被正式写入 Phase 4 的架构原则。

这是本周期最有分量的证据，因为它是一次**自然实验**：

**"组合行为盲区"**值得展开：迭代 2 交付后实测发现 DEL 键 × Ans 键的组合行为有 bug（按了 DEL 再按 Ans，行为和预期不符）；迭代 3 "DEL × 幂后缀"没有显式声明，靠实现侥幸没炸。两期的共同模式：**新加入的交互维度 × 既有横切行为（编辑、清除、续算……）的交叉格子没人检查**。这是三个迭代里唯一连续复发的真实产品缺陷类别——也就是说，其他问题都被流程接住了，只有这一类漏网。

### 收尾小批：四件事

**1. Depth 值纯净双侧修复。**

dogfood 两次实录同一个故障形态：状态文件的 Depth 行被填成 `standard（scope`——模板里的括号引导语（"(scope default, or user override)"）被模型连着抄了进去，引擎把注解当成了值的一部分解析，深度档位悄悄变成一个非法值。

修法是双侧的：

- 引擎侧：新增 `_strip_inline_note`（首个半/全角括号截断），**仅用于 Depth 分支**——对 Scope 行则保持严格拒绝（粘连注解直接 plan-invalid 硬阻断）。原则："机器可校验项从严"：Depth 的合法值是封闭枚举，剥掉注解后仍可校验，从宽；Scope 行的注解粘连说明计划本身可能被污染，从严；
- 模板侧：把教注式模板改成裸值，从源头消灭诱因；工作规划规则补一条"值纯净"规则（Skip 行的 `(reason)` 是唯一合法括号内容）。

一个小 bug 的修复牵出四份文件、契约一节、四个测试——这就是"双侧修复"的成本，但只修一侧等于修一半。

**2. AUD-05 追加纪律。**

迭代 3 的三次审计失误都是同一形态：模型把编辑锚点放在了**已有的标题行**上，改写了历史条目（审计本是 append-only 的账本，模型做编辑时贪图标题唯一性好定位）。新规则：新条目一律锚定文末、单次追加，禁止以既有标题行为编辑锚点。依据（三次失误均同交互自愈留痕）留在决策文档里、不进技能文件——规则文本只留结论，论据留在档案，各归各位。

**3. 组合边界检查项（本批最有普适价值的一条）。**

把"组合行为盲区"机制化，写进需求分析阶段，普适规则：

> 凡引入新交互/行为维度（新输入 token/实体类、按键/命令/手势、状态或转移、数据实体、外部接口），必须对每项**既有横切行为**（编辑/删除、重置/清空、错误处理与恢复、结果态/空闲态续算、撤销重做、持久化）的**组合边界逐项声明**：被功能需求覆盖（或注明由后续故事验收标准承担），或显式声明范围外并给理由。对新项目与再入迭代同构生效。

本质上这是把"测试矩阵"的思路前置到需求阶段：新产品每加一个维度，就自动生成一张"新维度 × 旧行为"的核对表，每个格子必须有说法。连续两期的真实 bug 都栽在这些交叉格子上——那就把交叉格子变成必填项。

**4. 登记杂项**：缺产物软警告正式关闭（累计 5 周期零触发，关闭时点仍回溯到 2026-09-24 的原始裁决）；活文档 rollup 记录首批实证（stories.md 已 356 行过阈值且没维护导航索引；requirements.md 出现自发 rollup）；dogfood 协议补"度量 N/A 规则"与"决策回填行泛化"。

测试 227 → 231 全绿，`--check` 零漂移。实施后审核 0 阻断、3 应修全修——包括一处有意思的：组合边界规则里"由后续故事的验收标准承担"这个分支，在用户故事被 scope 跳过的场景（6 个 scope 中 5 个）下悬空——重排为"仅当用户故事在计划内才可推迟到故事 AC"，否则必须当场声明。**规则的分支要对着 scope 矩阵全量过一遍，不然总有一个 scope 下它是死路**。

### 价值

这一批没有大架构，但它是"**用机制结账**"的范本：dogfood 发现的每一类问题，要么变成一条规则（组合边界）、要么修一个模板（值纯净）、要么关闭一个悬念（软警告），没有一条停留在"下次注意"。六度量的账本也展示了诚实记录的价值：两条度量记了 N/A（配置性失效、零样本），一条挂账（RCA 沉淀 0）——**度量体系自己的健康状况也要度量**。

## 把自主模式改到"一问开启"（D17 + D18）：做减法的连续剧

**完成时间：2026-09-29，一天两批**

### 需求是怎样"聊"出来的

这两批的需求演进本身就很有代表性，值得按时间线记录——**功能是对话聊出来的，不是一次性想清楚的**：

1. 我先提出：激活自主模式时加一问——**要不要在代码生成前停一次**？动机很实际：设计类工作用强模型，实施类工作（写代码）可以切到快而便宜的模型，停一下正好换窗口。选"是"则停一次，说"继续"后一路跑到本轮完成；
2. 期间我追问：激活时的另一问（审核阶段多选——"哪些阶段保留人工审核"）是哪来的？**考古发现它是历史遗留**：最初藏在"暂停菜单"的选项 B 里（一个几乎没人用的编辑入口），D16 重写菜单后才迁进激活流、摇身变成必问项。来历如此，果断裁决：**整个去掉**。人工把关改由"随时暂停"承担；
3. 最后一步：既然审核阶段不问了，问题处理方式（遇到澄清问题：自动选推荐答案 / 每次问我 / 自定义）也不需要问了——**默认就是自动选推荐答案**。理由：想干预的用户随时可以说话（轮内显式指示），不需要预先配置一个"每题都问"的模式把自己锁死。

于是激活自主模式从"双问"收敛到"**单问**"（只问代码生成前停点），一天之内两批落地（D17、D18）。

### 最终语义（值得抄的设计）

**激活 = 单问**，且每次全新问，任何持久化值**不作预选**——防止"上次说要停"悄悄变成"这次也停"。配置的默认行为是"不悄悄复活"，和 D16 的"不悄悄继承"一脉相承。

**AM 期间全阶段自动批准**，问题自动选推荐答案；人工干预的出口有三个：轮内显式指示（说一句就改）、暂停（下面讲）、升级路径（复杂到需要结构化提问时模型主动暂停问）。

**暂停 = 优雅降级，不是急刹车**（AM-05 二次重写）：

```
你说"暂停/停止自主模式"
   → 模式关闭（状态行翻转）
   → AI 把手头工作完成到一致状态（不启动超出当前门的新工作）
   → 标准模式继续走到下一个审批门（当前阶段自己的门，或其后的首个门）
   → 等你。直到本轮结束不再自动恢复，除非你显式重新激活（重新走单问）
```

这个语义很讲究：你中途喊停，多半是想"看看"，不是想"推翻"。急刹车会把工作流卡在一个不一致的中间态；优雅降级让它滑行到最近的安全点（下一个审批门）再等你。**暂停的体验设计核心是"停在哪"，不是"停不停"**。

**代码生成前停点（Code-Gen Hold，AM-11 新规则）**，四个要点：

- **布防条件 = "代码生成工作尚未开始"**——这个条件不是多余的：计划审核轮发现，如果激活时工作流已经推进到代码生成阶段内部（引擎的待办序列包含当前阶段），不设此条件的话"待停"状态会悬空、恢复条款会在开工后中途打断。堵触发空洞的通用手法：给"布防"加时点条件；
- **触发三路径**：转移到达代码生成阶段时 / 激活时恰在代码生成前 / 会话恢复时重新呈现（停点是跨会话状态，写在状态区的 `Code-Gen Hold` 行里——模型写、模型读，引擎零改动）；
- **放行 = 继续语义**：你说"继续"，Pending→Passed、刷时间戳、审计；你说别的（比如"先看看设计"），按意图处理，但**仍然等继续语义**——停点不因你说了别的话就消失；
- **每次激活最多一次**：重激活可以在窗口开放时重新布防；回跳重做不重触发（你重做的是上游阶段，停点已经用过了）。

**工程细节三条**，都有普适价值：

- **AM-06（审核阶段机制）整体移除但编号退役不重排**——墓碑保留两行："AM-06 已退役（2026-09-29），编号不复用"。后来的人看到 AM-01~AM-11 里缺 AM-06，不会误以为是编号错误，也不会"顺手"重排编号把所有引用打散。**删除东西时，给编号办退休手续，别销户**；
- **引擎删掉 review_stages 字段解析**（约 -9 行），生成器的 stage-names 注册表随之退役（唯一消费者已删，渲染器、标记注册、映射表三处一起清）——**功能删干净时，它的支撑代码也要跟着删干净**，否则就是下一批"文档减法"要清的沉积物；
- 自定义停点答复（用户说了句不在枚举里的话）**逐字写入状态行**，跨会话存活——配置区的值忠实记录用户的原话，不做翻译。

### 审核与方法学升级

两轮审核零阻断。D18 的审核还有个方法论升级值得一提：审核方拿 **GitHub 远端 HEAD**（与本地一致性先确认）作为前基，对 9 个文件做**等效真实 diff 对账**——因为审核环境没有本地 git 历史，用远端基线重建了 diff 能力。这个升级立刻抓出一项真问题：文档里 D17 的历史条目被 D18 的插入点**拆开了**（D17 的"实施后审核"段被挂到了 D18 标题之下，其时点事实会误挂到 D18 名下）——纯移动归位修复。

你看，连"历史记录的完整性"本身都会被编辑事故破坏，何况代码。**时间线类文档的插入点要对着时间线找，不对着相似度找**。

### 价值

三批 AM 改造（D16 → D17 → D18）连起来看是一条完整的弧线：**先给权限装上生命周期（防代代相传），再把它简化到一问开启（防过度配置）**。加法和减法说的是同一件事：权限该有的时候恰好在，不该有的时候确定不在，而日常使用不该为它付出超过一个问题的成本。

## 做减法：文档减法清理批（D-清系列）

**完成时间：2026-09-29（计划两轮审核后，三个实施批次 + 一个收尾批次，四个 commit）**

### 遇到的问题：加法做多了

Phase 1 到 3.3 一路加东西，技能文件里沉积了大量**不再被需要的文本**。我把它们归成五类（这个分类后来成为本批的删除判据）：

| 类别 | 定义 | 例子 |
|---|---|---|
| **重复副本** | 同一信息多处维护 | 条件阶段的执行判据在 SKILL.md / 阶段正文 / 规划文件三处各一份 |
| **路由遗物** | 教模型做"已归引擎"之事的指令 | "完成阶段后自动继续下一阶段"——Phase 3 起路由归引擎 |
| **墓碑纪事** | 退役机制的"生前事迹"整段保留 | AM-06 的历史沿革叙事 |
| **教学冗余** | 给人类读者的示例块、模板复读 | ✅/❌ 对照教学块、同一模板的三次复述 |
| **死文件** | 整个文件零引用 | terminology.md——术语表，无人引用 |

这些东西不是无害的：AI 的上下文是稀缺资源（这在双臂验收里会被量化证实），每一段过时文本都在稀释有效指令的浓度，还在按 token 收费。

### 纪律：减法比加法更需要判据

这个批次最值得学的不是删了什么，是**怎么保证删了不出事**：

- **五类判据，无法归类不删**——拿不准的那一段，无论多可疑都留下。"删得果断"在这类工程里是贬义词；
- **纯减法、语义等价**——删完行为必须不变。这比加法难：加法可以"宁可多余"，减法没有"宁可"；
- **计划过两轮独立审核才动手**——第一轮证伪了我"判据权威在阶段正文"的假设（详见下文），第二轮抓出两个执行面阻断；
- **每个实施批次独立跑全量测试和漂移检查**——三个 commit 各自可回滚。

### 最惊险的发现："副本"其实是"分歧变体"

原计划里最"安全"的一步是删判据副本——三处写的是同一个条件，留一处（frontmatter）删两处就行。**结果三方比对发现它们根本不一致**：

- units-generation 的判据在两处的**内容不同**（SKILL.md 版 vs 阶段正文版，各自演化过）；
- user-stories 有独有条目（technical debt cleanup / developer tooling）**只在一处存在**。

也就是说，这些"副本"在漫长的演进中各自发生了变化——**你以为的重复，可能早已是分歧**。直接删会静默丢失语义：某个阶段会悄悄在一种视角下"忘了自己什么时候该执行"。

于是批次重排：先做**三方调和**（把判据收编进阶段 frontmatter 的 `condition` 字段——浅映射 `{execute_if, skip_if}`，成为唯一权威），生成器把权威判据渲染成 "CONDITIONAL Stage Criteria (authoritative)" 清单注入规划文件，然后才删得放心。ALWAYS 阶段的 condition 保持标量——一个字段两种形态，校验规则和测试夹具都做了双形态化。

二审还抓出两个执行面阻断，都是"顺序不对会当场炸"的坑：

1. **doomed 渲染器陷阱**：condition 改成映射的那一瞬间，两个即将被删除的旧渲染器还活着——它们会把 Python 字典的 repr 直接写进**恒载文件**（每次会话都加载的文件），内容当场变成垃圾。改法：批次重排为"**删除先行**"——注定要死的代码先死，再上新格式；
2. **校验形态未定义**：新校验规则没定义映射形态怎么校验，一上线当场爆红 5 个阶段文件 + 17 处测试用例。改法：先在契约里定双形态规范，夹具先双形态化，再动真实文件。

### 三批落地

**批 1（删除先行）**：

- 整删 process-overview.md（10.3KB 恒载文件——它里面还藏着一句 "No fixed sequences"（无固定顺序），与引擎路由**直接矛盾**：引擎就是按固定顺序路由的。这段遗物每天都被加载、每天都在稀释路由指令）；
- 整删 terminology.md（10.6KB 零引用死文件——术语解释写得很好，但没有任何文件引用它，AI 按需加载的机制根本不会走到它）；
- 生成器删掉 2 个标记注册（7 个生成区）和 4 个死渲染函数；
- 新增 RenderMapCoverageTests：**每个渲染函数必须有标记区消费、每个标记区必须有渲染函数**——把"静默死渲染器"这个失败模式固化成防回归测试。

**批 2（判据通路）**：9 个条件阶段的 frontmatter 写入调和后的判据；生成器渲染权威清单；契约三处对齐；测试夹具迁移。调和本身有留痕纪律：units-generation 的每一项取舍（哪些并入、哪些剔除、为什么）都记录在决策文档——**被删掉的语义要有尸检报告**。

**批 3（散文减法）**：SKILL.md 631 → 343 行（删用户故事评估矩阵副本、14 块 Execute IF/Skip IF 判据散文、执行模板复读、审计弹幕去重指向规则组、勾选说明两级合并、✅❌ 教学块）；错误处理文档 17.4KB → 9.4KB（140 行按阶段复读的恢复指引收敛为指针 + 两条跨阶段规则）；墓碑清扫（AM-06 压缩为两行；D 系列纪事剥除；pre-AM-10 叙事中性化）。

**收尾批**：审核发现的 6 项全修——最有意思的一项：US 的判据摘要要求附"试写样例"（execute_if 压缩三档优先级、skip_if 五项含独有条目），**压缩后的摘要必须能对上正文程序**，冲突以 frontmatter 为准的锚行写明；另一项：新增 DeletedNameHygieneTests——把"删掉的文件名不许再被任何技能文件引用"固化成防回归测试，覆盖全部 .md/.py 甚至两份 README。

### 结果

**必加载文档集 97,064 → 73,262 字节，-24.5%**（其中 SKILL.md 单文件 -33%；错误处理文档 -46%，按需加载）。测试 231 → 237 全绿，`--check` 零漂移，悬空引用 grep 对账零命中。

### 价值

- 直接收益：每个会话省下约 5.8K token 的固定开销，有效指令浓度回升；
- 更深的收益是方法论：**减法和新功能一样，需要判据、需要计划、需要两轮审核、需要验收测试**。"感觉没用了就删"和"感觉有用就加"是同一种草率；
- 顺带销了一笔旧账：复审遗留清单里"两个文件的陈旧散文"一项——文件整删，全销。

## 验收减法：双臂 dogfood（2026-10-06）

**完成时间：2026-10-06（本记录期最后一次验收）**

减了 24.5% 的文档，行为真的没变吗？这是减法批欠下的验收债。理论上"语义等价"已经在评审里论证过了，但**论证不等于证据**——尤其判据收编那种"三处分歧调和为一处"的操作，谁也不敢打包票行为完全一致。

### 实验设计

做一个力所能及的**双臂对照**：拿 fx991 的日常迭代嵌入 A/B——

- **臂 A**：减重前的技能快照（旧文档）；
- **臂 B**：减重后的技能快照（新文档）；
- **任务**（三条腿，都是真实需求）：腿 1 = 历史记录功能（新交互维度，正好考验判据）；腿 1b = 单组件精度字段（小改动）；腿 2 = evaluate 模块重构 + bug 修复（重构场景）；
- **观测点**：每条腿两臂的 CONDITIONAL 阶段决策集合是否一致；判据溯源引用的是新权威清单还是旧副本；六个会话（F1-F6）的探针是否零失效；token 消耗差异。

这里要诚实说明设计的局限（写进验收报告第一节的）：这是**日常使用嵌入形态，不是受控消融**——会话长度、制品规模、交互次数都无法完全控制，所以它给不出"减重导致了 X% 改进"这种强结论，只能回答"行为有没有变"（等价性）和"方向对不对"（收益符号）。

### 结果：方向性通过

**行为等价（核心验收项，过了）**：

- 每条腿两臂的**条件阶段决策集合完全一致**——该跳的阶段两边都跳、该做的都做，一个格子都没差；
- 臂 B 的决策溯源全部引用新权威清单措辞、**零旧判据残留**——模型确实在用新通路做判断，不是碰巧蒙对；
- 六个会话探针零失效。

**token（方向对，但要看清口径）**：

- 静态口径：恒载 -24.5% 维持，约合每会话省 5.8K token——这是可辩护的数字；
- 会话级实测：三腿差异 -23.0K / +4.9K / -17.7K——方向 2/3 有利臂 B，但**噪声远大于信号**。这恰好印证了一个预判：**会话上下文由制品主导**（需求文档、代码本身），规则文档只占小头。给规则文档瘦身的收益天花板就在那里；给制品瘦身（rollup、知识树）才是下一阶段的真战场。

### 诚实定级（验收报告原样摘录，这部分我最想让读者看到）

- 腿 2 两侧快照来源存疑（一侧疑似形态误判、一侧疑似混入主项目胖快照），**降级为日常累积，不构成减重验证证据**；
- 臂副本的 .git 被重新初始化，血统证明断裂，lineage 退化为"特征判定"——协议据此排了改进项：**快照必须注记源 commit + 时间戳**（本轮三次缺失是实证教训）；
- 一个引擎冲突样本（引擎按计划行残留发射了用户故事阶段 vs frontmatter 声明 SKIP → frontmatter 胜、裁定跳过）原本想算减重的功劳，复核后**重定性**为 Phase 2 scope 权威机制的验证——不是自己的功劳就不领。

### 顺带的新发现（排队未立项）

- **Windows 自由文本参数被拆**：`park --note` 带空格/分号，被 cmd 拆参——三个会话复发。建议加 `--note-file` / `--reason-file` 文件通道（对齐"多词文本写临时文件再传"的老经验）；
- **引擎派发未按 scope 预剪枝**：计划行含跳过阶段时引擎照常发射、多耗一轮交互（模型现行规则能正确消化，属效率问题非正确性问题）；
- **consumes 的 required × scope 剪枝组合语义**待契约澄清（上游被 scope 跳过时，"必需"消费怎么办——契约里其实有答案[moot]，但边界场景需要写清楚）；
- **部署卫生**：主项目里的技能副本还是减重前的胖快照——工具链改进了，使用侧也要跟上，否则收益到不了用户。

## 尾声：一条主线，全部决策，几点诚实

### 一条主线

四周，十几个批次，回头看是一条主线上的连续施工——还是那句宪法纲领的逐步落地：

- **Phase 1** 把"阶段"从散文变成数据（唯一事实源）；
- **Phase 2** 用同一份数据推导出任务裁剪（第一个消费者）；
- **Phase 3** 把同一份数据编译成引擎的路由表（第二个消费者）——"精确归工具"至此成立；
- **Phase 3.1-3.3** 补上记忆的连续性（泊车、恢复简报、传感器），吸收外部借鉴，把真实反馈变成机制；
- **D15** 让"迭代"成为一等公民——做完再加功能，不再推倒重来；
- **D16-D18** 给权限装上生命周期，再把它简化到一问开启；
- **D-清系列**证明减法也是工程——判据、计划、审核、验收，一样不能少；
- **双臂验收**示范了如何诚实地验收——包括承认哪条腿不算数。

而"决定归人类"从第一天到最后一天没变过：每个审批门都是你说了算，AI 从未获得替你批准的权力（report 的关卡 [2] 把这一点焊死在类型系统里）。

### 方法论清单（四周里反复验证的那些话）

1. **先考证，后修复**——看起来像 bug 的行为可能是故意的，改之前先查出生证明（两次防住误修）；
2. **把正确行为变成最省力的路径**——流程步骤和一条命令，优于规则条文（Phase 3.3 批次原则）；
3. **中性提示词审核**——给审核方的提示词不预埋结论，疑似问题单独列为待验证主张（Phase 3.2 方法学转折）；
4. **判断/精确的分界线**：事实问题（什么时候过期、走到哪一步）下沉工具，语义问题（怎么暂停、要不要跳过）留在规则文本；
5. **fail-open 的传感器，宁漏报不误报**——误报训练用户无视告警；
6. **删除要办退休手续**——编号退役不重排、被删语义有尸检报告、死代码随功能一起删；
7. **无法归类不删、拿不准不删**——减法的果断是贬义词；
8. **全树清扫**——改协议必须 grep 全部消费方，改一处漏一处就是给模型制造精神分裂；
9. **规则描述能力，不描述产品**——"凡能在同一次交互里呈现带选项问题的工具"，而不是"question 工具"；
10. **验收要说实话**——哪条腿不构成证据、哪个功劳不是自己的，写在报告里。

### 几点诚实

写博客不讲漂亮话，这套设计有几条**诚实的边界**，全部记录在案：

1. **检测不等于阻止**。没有 harness 钩子的环境，工具层防不住一个铁了心要伪造批准的模型。对策是提示词纪律 + 完整审计留痕，威胁模型明确定义为"疏忽"而非"对抗"。
2. **消融实验做不了**。"没有引擎会怎样"的对照组在当前架构下无法构造（引擎必选），改进效果只能靠历史对比和双臂嵌入间接观察。
3. **传感器宁可漏报不误报**。缺产物检测设计得非常保守，误报会训练用户无视告警——那是比漏报更糟的失败模式。
4. **泊车防不了强杀**。park 是模型的主动自律动作，强关 harness 时它没有机会执行（负债清单明文记录，兜底是半成品传感器）。
5. **自主模式的过期翻转，其触发互斥是纪律约定而非机制保证**。该状态区不在完整性摘要里、没有锁，多会话并发下的彻底语义留给 Phase 4。
6. **减重的会话级 token 收益噪声太大**。可辩护的只有静态口径与行为等价；会话上下文由制品主导，给制品瘦身才是下一步的真战场。
7. **双臂验收自己承认了一条腿不构成证据**。在验收报告里写明哪些数据可信、哪些不可信，比一个漂亮的总结论值钱。
8. **还有没做完的事**。备份遗产清理批立项未实施；RCA 八例沉淀为零的账挂着；主项目的技能副本还是胖快照。登记在案，不装看不见。

### 下一步

- **Phase 4 团队构建**：多个 AI 会话（或人机混合）像真正的开发团队一样并行工作——任务认领与释放锁、按单元编排波次、单阶段独立重跑。地基（结构化单元清单、封闭的动词集、状态唯一写入者）在前面的批次已经全部埋好。
- **待实施的备份遗产清理批**：规格已审，等着动手。
- **Phase 5A 知识树与学习闭环**：让工作流"越用越懂你的项目"——把记过的账变成资产的路径。

从一堆会互相打架的 Markdown，到一套**状态有唯一权威源、恢复有分级协议、变更有合法通道、迭代有正门、权限有生命周期、每次转移都留痕、还能自己做减法**的可移植工作流——四周，十几个批次，一条主线。

这就是 Phase 1 到今天的故事。
