## 1. 立项背景

B15/B16 建全了迭代**边界上**的机制（roadmap 边界重排 / 完成仪式 / shipped 不可改写）。2026-10-09 五问推演暴露迭代**运行中**的缺口：

1. 就地讨论 vs 跳回 brainstorm 的"升级桥"缺失（二分结局假设单交互收敛）
2. 中途发现 bugfix / 安全任务的路径——**又急又大的插队无路走**（单线性状态机没有"暂停→插队→恢复"）
3. 就地改 vs 加迭代的判断轴分散（基本覆盖）
4. 顺延不裁剪未成文（dogfood #2 实证好用但只活在对话裁决里）；迭代行号 vs FR/US 编号的不对称未点破
5. 跳回 brainstorm 后被中断迭代的去向（已覆盖且刻意：机制强制从 RA 重走、语义增量续作——缺"先判要不要走重路"的内部提醒）

用户三轮修正定型方向：

- **傻瓜化**：路由判断成本由模型承担，用户永不见机制词汇——非技术用户不知道 jump 是什么，"要不要 jump、jump 到哪、现在的工作怎么办"解释成本极高。给建议而非给选择树。
- **本质化**：核心问题是"**外线变更如何合流**"，hotfix 只是三触发之一（自助线 / 协作线 / 交付线）。有 git 走 git 原生路径（stash / worktree），**不迁就状态机去改产品计划**——"提前收尾"从主方案降级为非 git 兜底。串行版今天就能成文（零引擎改动），并行版（claim/release）才是 Phase 4。
- **排队 vs 吸收 = 产品决策**：带推荐呈给用户（"加进这期，捋一遍晚点交付"vs"排下期，照常交付"），是产品选择不是内部路由。

## 2. 设计原则（三条，统领全批）

1. **P1 机制隐身（适用范围 = 本批新增 A/B 流）**：路由决策（跳不跳 / 跳哪 / 轻路重路）是模型内部决策，经引擎执行；台前只见处置 + 推荐 + 代价的产品语言。例外三条：①技术用户主动问机制——如实讲（机制隐身 ≠ 机制保密）；②决策改变交付物本身——仍用结果语言（"捋一遍、晚一到两天"）；③引擎错误按 engine-contract 逐字呈现优先。**既有 Type 1~10 用户话术与恢复菜单本批不动**（"全量去术语化"登记开放项）。先例：RA Step 2.5 de-emphasize 条款。
2. **本质化**：成文一条通用五步流，三触发复用，不写三本说明书。
3. **AM 中立**：不写任何新 AM 条款（AM 退役事宜另行裁决，未登记）；插队协议不复述 AM 规则只求不冲突——撤 AM 时清理面零牵连。

## 4. 台前话术规范（两例已获用户认可，2026-10-09）

**例一·复合许愿**（迭代 3 写码中途，用户："手机上棋子太小；能不能跟电脑下；棋谱打开空白"）——台前回复三段式：

1. bug："这是我的问题，这轮顺手修掉，交付时一起验证"（吸收，不问）
2. 可吸收可排队（够格候选 → A2 问句）："只是放大可以并进这期，晚一天左右；整体重排版我建议排到下一期专门做——孩子用手机是长期场景"
3. 方向性（→ A4 时机问句）："跟电脑下是新方向，值得认真聊。我建议这期先交付，用出来的感受会让讨论更实在；现在聊也可以"
