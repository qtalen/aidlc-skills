engine.py 图解

架构 · 流程 · 作用 —— 一个 1786 行的纯标准库命令行工具，如何替 AI 记住"我们走到哪一步了"
Python 3.8+ 标准库，零第三方依赖 8 个动词 15 个阶段 253 个单元测试 harness 无关
宪法纲领：判断归 LLM，精确归工具，决定归人类。 engine.py 就是那句"精确归工具"的化身——该动脑的交给 AI，该一丝不苟记账的交给它，该拍板的永远留给人。

01它解决什么问题

在引擎出现之前，"现在走到哪个阶段了"完全靠 AI 的记性和自觉：状态文件由模型手写维护，20 多处散文指令教它"做完阶段去把第 X 行勾上"。长对话会遗忘、中断后恢复每次不一样、状态改坏了无人察觉。引擎把这类不需要动脑但需要绝对精确的事全部收编。

判断 · 归 LLM

AI 模型继续做脑力活

条件阶段适不适用、scope 推荐、需求澄清、写一切文档与代码、审批门的呈现方式——引擎一个都不碰。

精确 · 归工具

引擎独占记账与路由

下一步是哪个阶段、状态转移、审计流水、完整性校验、原子写盘——封闭规则，一个字符都不许错。

决定 · 归人类

审批门永远留给用户

带门的阶段必须用 approved / rejected 上报——AI 想用 completed 蒙混过门？引擎在类型层面直接拒绝。

一句话类比：引擎是地铁闸机——刷一下（一条命令），过去几步（一个 JSON 回执）；乘客在两台闸机之间怎么走（写文档、做判断），闸机不管，也管不着。

02全景架构：谁编译、谁判断、谁执行

引擎有"两种人生"：作者期（维护技能的人改规则时）只吃编译产物；运行期（AI 带着用户干活时）被模型通过 shell 一条条调用。两期之间隔着一道刻意的防火墙。

04八个动词：权限最小化

模型操作引擎的全部词汇表就这 8 个子命令，按"能改什么"分层（D13 纪律）。想改进度只能走 report / jump 两扇门；只想留便签？park 物理上摸不到进度数据。一个动作能改什么，由动词决定，不由调用者小心不小心决定。

setup 建立
init开户：创建 state + audit，审计第一条 STATE_CREATED；已存在则报错（那是恢复路径）
transition 转移
封闭集合
report唯一常规转移写入口，5 种结果，四道关卡（下一节）
jump改道：回跳重置目标及其后；完成态下放行为同产品再入（D15）；--fresh 归档重来
annotation 注记
park --note临时停车留条：Last Parked + handoff.md，不碰 marks / current、不写审计
read 读
status恢复简报：resume_note + 便签年龄 + 最近 5 条转移 + 传感器警报 + autonomous 键
next路由：发出"执行某阶段"指令 JSON，附全量契约信息（产物/依赖/门/规则路径/conditional）
stamp权威 UTC 时间戳，零副作用——审计条目要可信时间时的专用时钟
repair 修复
rebase保修通道：以审计流水为准重放，重建进度区 + 新指纹（第 06 节）
连命令行用法错误都输出 JSON（为此重写了 argparse 错误类）：所有错误统一 {kind, code, message, hint} + 退出码 1，所有成功输出注入 timestamp。消费方是 AI——统一形状意味着"出错"本身成为可编程处理的事件，而不是一次崩溃。

05report 流水线：四道关卡 + 盖章记账

report --stage <slug> --result <R> [--reason] 是整个系统唯一的常规进度写入口。每道关卡都在堵一类作弊或失误。

▼report 进入 _validate_transition()
1
查票 · slug 在图里存在吗

防止幻觉——模型编造一个不存在的阶段名来"完成任务"。

2
票种匹配 · 门与结果必须配套

带审批门的阶段必须用 approved / rejected / revised，不许用 completed 蒙混；无门阶段正好相反。"决定归人类"不靠自觉，靠类型系统。

3
跳过资格审查

skipped 只给三类：CONDITIONAL 阶段 / 当前 scope 裁剪 / 计划显式跳过——且必须给 --reason。必做阶段想偷懒？改走 jump（人类决定的改道）。

4
本人办理 · 只能 report 当前阶段

不能跳着报、不能补报很久以前的。

▼四关全过 → 盖章记账
5
盖章 + 作废便签

completed/approved→[x]，rejected→[R]，revised→[?]，skipped→[S]；parked=None（重新上路，便签失效）。

6
原子写入 + 审计追加

_splice_region() 重写引擎区（marks / current / digest）→ 临时文件一步替换（断电不出半截文件）→ 审计 append-only 追加一条转移事件。

7
produces_missing 软探测（fail-open）

完成/获批时顺手查承诺产物是否全缺；检查本身出错也静默放行——传感器可以坏，大门不能锁死。

8
JSON 回执

"记上了，现在轮到 <下一个待办阶段>"——下一阶段 = 计划顺序里第一个 [ ]。

unknown-stage
关卡 1 拒绝：编造的阶段名
gate-result-mismatch
关卡 2 拒绝：票种不对（含"想绕过用户审批"）
skip-not-allowed / reason-required
关卡 3 拒绝：无资格跳过 / 没给理由
not-current-stage
关卡 4 拒绝：跳报、补报
{kind, code, message, hint}
每个错误三件套：机器可读 code + 人类可读 message + 补救提示 hint

06完整性三角：digest + 审计对账 + rebase

状态文件人人能打开、能改。怎么防"手改进度表作弊"？两道互相独立的证据链，每次状态操作前交叉核验——两道链条抓的是不同的贼。

证据链 1 · 抓"改了内容"

内容指纹 digest

对引擎区内容（指纹行除外）算 sha256 存档。下次操作前重算——改过哪怕一个空格，哈希立刻对不上，当场识破。

＋
证据链 2 · 抓"绕过引擎伪造"

审计交叉核验

把 audit.md 里的转移事件解析出来，与进度表印章逐一对账：进度表说 requirements-analysis [x]，审计里就必须有对应流水。多一枚、少一枚、对不上，都算账目不符——哪怕连指纹一起重算，没有流水照样露馅。

▼check_integrity()
两道全过 → integrity: ok

正常放行，操作继续。

对不上 → tampered

进入修复通道：rebase 以审计流水为准重放转移历史，重建整个进度区 + 新指纹。审计是 append-only、引擎独写的，比状态文件更可信——"存折丢了，拿银行流水重新补一本"。修复后交叉核验豁免（重放的章天然没有新流水，修复机制不能被校验机制卡死）。

诚实边界：这是检测，不是阻止——无钩子环境拦不住模型真的去改文件，但"改了必被发现"是确定的。威胁模型是"疏忽/手滑"，不是"蓄意对抗"（铁了心伪造批准的模型，工具层防不住；对策 = 提示词纪律 + 完整审计留痕）。

08转移语义矩阵与设计边界

result勾选指针适用
completed[x]推进无门阶段完成
approved[x]推进门阶段用户批准后
rejected[R]停本阶段门拒绝
revised[?]停本阶段修订后再提交
skipped[S]推进仅条件/计划跳过，须理由

运行期事实清单

引擎对图集只读 stage-graph.json，永不解析 frontmatter / 散文
审计文件append-only，引擎只追加转移条目；用户原始输入仍由模型记录
handoff.md引擎独写，模型不得手改
per-unit 阶段引擎只发一次指令，单元内循环归模型——粒度到阶段为止
jump不绕过计划过滤：跳到计划外阶段照样执行，但附带 note 提示
分发随技能目录分发，用户侧前提仅两条：harness 能加载技能 + 机器能跑 python；无引擎 = HARD STOP 提示安装
