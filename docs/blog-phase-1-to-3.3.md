# 从一堆 Markdown 到一套会自己管状态的 AI 工作流：Phase 1 → 3.3 演进全记录

> 这篇文章记录了我过去两周（2026-09-11 ~ 2026-09-24）在一个开源项目分叉上做的六轮迭代。
> 读者不需要任何背景：只要你知道"AI 能帮我写代码"，剩下的概念我都会从头讲起。
> 每个版本我都会按同一个套路讲：**遇到了什么问题 → 打算怎么解决 → 实际做了什么 → 结果如何 → 带来了什么价值**。

---

## 第 0 章：背景速成班（已熟悉的读者可跳过）

在讲 Phase 1 之前，先把几个关键词讲透。这些词后面会反复出现。

### 什么是 harness？

**harness（脚手架/工具箱）** 就是承载 AI 编程助手的那层软件，比如 Claude Code、OpenCode、Cursor 这类工具。它们负责：

- 让你和 AI 对话；
- 让 AI 能读你的文件、改你的代码、执行命令。

不同的 harness 能力大同小异，但**彼此并不兼容**——就像不同的浏览器都装着不同的插件系统。这一点很重要，因为它决定了我的一个核心设计约束，后面会反复提到：**我做的这套东西不能绑定任何一家 harness**。

### 什么是"技能（Skill）"？

技能就是**一包预先写好的规则文档**，塞进 harness 里，让 AI 在做某类任务时"照章办事"。你可以把它理解成：给 AI 的一本《操作手册》。AI 每次接到任务，先翻手册，再动手。

我这个项目的技能叫 **aidlc-workflows**，最初是纯 Markdown 文档——没错，就是一堆 `.md` 文本文件，零代码。

### 什么是 AI-DLC？

DLC = Development Life Cycle（开发生命周期）。**AI-DLC** 就是"由 AI 驱动的开发生命周期"：把一次软件开发拆成一个个**阶段（Stage）**，比如：

```
需求分析 → 用户故事 → 工作流规划 → 应用设计 → 单元拆分
       → 功能设计 → 代码生成 → 构建与测试 → ……
```

每个阶段 AI 产出一份**制品（artifact）**——需求文档、设计文档、代码、测试报告……每个阶段结束时有一个**审批门（Gate）**：AI 停下来，把成果摆给你看，你来决定"继续"还是"打回"。

我这个项目里的完整流程是 **3 个相位（Phase）、14 个阶段**：

| 相位 | 含义 | 阶段 |
|---|---|---|
| Inception（孕育期） | 搞清楚要做什么 | 工作区探测、逆向工程、需求分析、用户故事、工作流规划、应用设计、单元生成（7 个） |
| Construction（施工期） | 把它做出来 | 功能设计、NFR 需求、NFR 设计、基础设施设计、代码生成、构建与测试（6 个） |
| Operations（运营期） | 跑起来之后 | 占位（1 个） |

> NFR = Non-Functional Requirements，非功能需求，就是性能、安全、可用性这类"不是功能但很重要"的要求。

### 两个版本和一个分叉

这个故事有三个主角：

- **v1.0**：一个纯 Markdown 技能。优点是轻、哪儿都能跑；缺点是原作者停止维护了，而且有一些结构性痛点（后面细讲）。
- **v2.0**：同一个理念的进化版，做成了特定 harness（opencode）的插件，包含 **50 多个 TypeScript 工具、17 个钩子、33 个阶段、11 种任务类型、14 个角色人设**。功能很强，但重，而且绑死了 opencode。
- **我的分叉**：拿 v1.0 当底座，**原地进化**——分阶段把 v2.0 的先进理念搬进来，但始终保持"harness 无关"：任何能加载技能、能执行 shell 的 AI 编程工具都能用。

v2.0 有一句纲领性的话，是我这整个项目的精神主线：

> **"判断归 LLM，精确归工具，决定归人类。"**

翻译成大白话：

- **该动脑的（判断）交给 AI**：需求该怎么理解、方案怎么权衡、问题该问什么；
- **该精确的（算数/记录/路由）交给程序**：现在走到第几步、下一步是什么、状态有没有被人改坏——这些不能靠 AI"记性"，必须交给确定性代码；
- **该拍板的（决定）留给人**：AI 永远不能替你批准一个方案。

前三个 Phase 做的事，本质上就是让这句话一步步落地。

有了这些背景，我们正式开始。

## Phase 1（与 Phase 0 同批交付）：让文档学会"一处定义，处处生成"

**完成时间：2026-09-11**

### 遇到的问题：阶段清单抄了 8 遍

v1.0 最头疼的结构性问题是：**同一份"阶段清单"在仓库里被手工复制了 8 处左右**。

SKILL.md（技能主入口）里有阶段列表；process-overview.md（流程总览）里有阶段分类和流程图；welcome-message.md（欢迎词）里有 ASCII 版阶段示意；terminology.md（术语表）里有按相位分组的阶段名；session-continuity.md（会话恢复规则）里有"恢复时该加载哪些产物"的清单；workflow-planning.md（工作流规划规则）里有执行计划模板……每个文件都从自己的角度"抄写"了一遍这份清单。

这带来两个恶果：

1. **改不动**。想新增一个阶段？你得记得改 8 个地方。漏改一处，文档之间就开始互相打架，而 AI 读到互相矛盾的规则时行为是不可预测的。
2. **必然漏改**。人（和 AI）的记性就是靠不住的。这不是态度问题，是结构问题——**重复本身就是错的**。

写过程序的人一眼就能看出解法：这就是典型的"没有单一事实源（SSOT, Single Source of Truth）"问题。

### 解题思路：给每个阶段建"户口"，让脚本抄清单

我借鉴了 v2.0 的一个关键设计：**阶段契约（Stage Contract）**。

思路分三步：

1. **让每个阶段文件自己声明自己的属性**——在每个阶段 Markdown 文件的顶部加一段 **frontmatter**（前置元数据块）。frontmatter 就是文件开头用 `---` 包起来的一段结构化数据，写博客的人应该很熟悉。比如需求分析阶段的文件顶部从此变成这样：

   ```yaml
   ---
   slug: requirements-analysis        # 阶段唯一标识（必须等于文件名）
   phase: inception                    # 属于哪个相位
   execution: ALWAYS                   # 总是执行 / 有条件执行
   gate: approve-continue              # 审批门类型
   produces:                           # 本阶段产出哪些制品
     - inception/requirements/requirements.md
   consumes: []                        # 依赖哪些上游制品
   requires_stage: []                  # 前置阶段（DAG 的边）
   scopes: ...                         # 任务类型适用性（Phase 2 才填）
   ---
   （下面才是原来的规则正文，一字不动）
   ```

   这就像给每个阶段上了户口：身份、归属、产出、依赖，全在一张表里，**机器可读**。

2. **写一个生成器脚本** `scripts/generate.py`：扫描全部 14 个阶段文件的 frontmatter，做校验（比如 slug 必须等于文件名、依赖不能成环、consumes 引用的产物必须真的有人生产），然后**自动重新生成**那 8 处清单。

3. **在被生成的位置画上"标记区"**：用 HTML 注释对 `<!-- BEGIN GENERATED: xxx -->` / `<!-- END GENERATED -->` 圈出"这块内容是机器生成的，人不要手改"。标记区外的内容，脚本一个字都不碰。

这里有个容易混淆的点，值得讲透——**这个脚本是"作者期"工具，不是"运行期"组件**。什么意思？它是给**维护技能的人**（我）用的，不是给使用技能的 AI 用的。用户拿走技能时，这个脚本静静躺在目录里不参与任何运行时逻辑。所以它不破坏"harness 无关、零依赖"的承诺——只要维护者机器上有 Python 就行。

### 实际方案

落地的交付物：

- `references/common/stage-contract.md`：契约规范文档，定义了每个字段的含义和校验规则；
- **14 个阶段文件**全部加上 frontmatter，规则正文零改动；
- `scripts/generate.py`：纯 Python 标准库（零第三方依赖），带校验和 `--check` 漂移检测；
- 7 个消费方文件里圈定了 13 个生成区（后来随 Phase 2 增加到 17 个）；
- 一个 GitHub Actions 工作流，每次 push/PR 自动跑 `--check`——万一有人改了 frontmatter 忘了跑脚本，CI 直接红给你看；
- 20 个单元测试，锁定解析器的各种边界行为。

`--check`（漂移检测）值得多讲一句：它重新生成一遍内容，和磁盘上的文件对比，**只要有一个字节不一样就以非零退出码报错**。这就把"忘了跑脚本"从"靠自觉"变成了"机器把关"。

### 结果

冒烟测试通过：**新增一个阶段，现在只需要"新建一个带 frontmatter 的阶段文件 + 跑一次脚本"，全仓库 12+ 处清单自动同步**。生成器二次运行幂等（再跑一遍不会有任何变化），标记区外的内容零改动。

审查环节还抓出并修掉了一批潜伏问题，比如解析器遇到引号里的 `#` 会静默截断、某个产物名在两个文档里不一致等。这里有个让我很满意的纪律：审查发现的每个问题都"先考证、后修复"——先翻历史决策文档确认这个行为是不是当初故意设计的，再决定改不改。事实证明有几次"看起来像 bug"的行为其实是记录在案的已知取舍。

### 价值

- **扩展痛点根除**：从"改 8 处"变成"改 1 处 + 跑一次命令"。
- **埋下了最重要的地基**：这一步让"阶段"从散文描述变成了**结构化数据**。当时看只是消除了文档重复，回头看，这是后面一切（scope 矩阵、运行时引擎）的前提——就像先有了户口数据，才谈得上户籍系统数字化。
- **确立了一个架构原则："地基按未来要盖两栋楼设计"**。frontmatter 这份事实源，Phase 2 从这里转置出矩阵，Phase 3 把它编译成引擎吃的 JSON——**三个阶段都是给同一份事实源新增消费者，事实源本身一次都没返工**。

## Phase 2：给工作流装上"任务类型"这档变速器

**完成时间：2026-09-12**

### 遇到的问题：修个 bug 也要走全套仪式？

Phase 1 之后，文档不再打架了，但工作流本身有个体验问题：**v1.0 对所有任务一视同仁**。

你想啊：开发一个全新产品，走 14 个阶段是合理的；可如果我只是要**修一个 bug**、**改一段重构**、**打一个安全补丁**呢？让我先做需求分析、写用户故事、拆单元……这就像去楼下便利店买东西也要先做市场调研。

v1.0 的做法是靠模型在"工作流规划"阶段**逐个阶段临时判断**该不该跳过。这有两个毛病：

1. **十四次判断 = 十四次出错机会**，判断质量看运气；
2. **每次都从头想一遍**，同样的"修 bug"场景，这次跳三个阶段、下次跳五个，没有沉淀。

v2.0 对此有个漂亮的解法：**scope（任务类型）预设**。它定义了 11 种任务类型，每种类型预先裁剪好一套"哪些阶段执行、哪些跳过"的执行矩阵。我决定把这个理念搬过来——但砍到一个务实的子集。

### 解题思路：一个字段，转置出一张矩阵

方案非常顺滑，因为 Phase 1 的地基已经打好了：

1. 在 `references/common/scopes/` 目录下定义 scope：每个 scope 一个文件，说明这种任务类型的定位、默认深度（后面讲）、关键词（用于自动识别）；
2. 给 14 个阶段 frontmatter 里的 `scopes:` 字段填值——**每个阶段对每个 scope 声明 EXECUTE 或 SKIP**；
3. 让 generate.py 把这份"阶段 × scope"的映射**转置**成一张"scope × 阶段"的矩阵表，自动注入到工作流规划的规则文件里；
4. 运行时流程升级为"**先选 scope，再微调**"：模型在需求分析阶段根据任务特征推荐一个 scope（后来进一步升级：明显的场景**自动选定、不设审批门**，比如用户说"修个 bug"就直接给 bugfix，事后一句话告知），然后在工作流规划时以该 scope 的矩阵为基线，允许逐阶段微调。

这里解释一下 **depth（深度）** 这个配套概念：每个 scope 除了裁剪阶段，还带默认深度档位——**minimal（最小）/ standard（标准）/ comprehensive（全面）**。同样是"需求分析"，express（速通）档下就写一页纸，comprehensive 档下就可能要写透。"哪些阶段做"由 scope 定，"每个阶段做多细"由 depth 定，两个旋钮配合，就把"流程重量"调到了连续可调。

### 实际方案

- 定义了 **6 个 scope**：`classic`（默认全家桶）、`bugfix`（修 bug）、`refactor`（重构）、`security-patch`（安全补丁）、`infra`（基础设施）、`express`（速通）。
- 为什么是 6 个而不是 v2.0 的 11 个？这是个有记录的取舍：`poc`/`mvp`/`workshop` 这几种要等运营期阶段补齐后才有区分度，`enterprise` 可以用深度档表达——**先不引入**，等将来运营期补齐，各 scope 只需"加一行"，定义本身不用改。
- 矩阵列序 = 默认优先 + 字母序，全矩阵 84 格（14 阶段 × 6 scope）逐格核对零误差。
- 审查环节抓出一个很隐蔽的坑并补了护栏：某些 scope（比如 bugfix）会跳过"单元生成"阶段，那后续那些本该"逐单元执行"的阶段怎么办？约定为**退化为对整个任务执行一次**，并且生成器加了条防回归规则，谁以后改坏了会报错。

### 结果

从那以后，"修个 bug"这个请求会自动落到 bugfix scope：需求分析保留（还是要理解问题），用户故事、应用设计、单元拆分全部 SKIP，直接进功能设计 → 代码生成 → 构建测试。**模型从"现场判断十四次"变成"确认一次基线、偶尔微调"**。

还有一个意外之喜：scope 的引入让**扩展延迟加载**成为现实——不被选中的 scope 文件根本不进上下文，实测显著节省了 AI 的 token 消耗（AI 的上下文窗口是有限资源，这个后面 Phase 3 还会再讲）。

### 价值

- **轻任务终于轻得起来**：流程重量和任务重量匹配，这是工作流可日常使用的关键一步。
- **经验第一次被"固化"**：什么样的问题该跳哪些阶段，从模型每次的临场发挥，变成了可审查、可版本管理的**数据**。
- **再次验证 SSOT 架构**：整个 Phase 只往 frontmatter 里填了一个字段的值，矩阵、目录表、规则注入全部由生成器自动完成。改一个阶段对某 scope 的适用性？改一格、跑脚本，全仓库同步。

## Phase 3：把方向盘交给模型，把仪表盘交给程序

**完成时间：2026-09-14；后续两天各有一轮增量修复**

这是整个项目最重要的一次跃迁。前两个 Phase 还是"整理文档"，Phase 3 开始**写真正的运行时代码**。

### 遇到的问题：谁还记得我们走到哪一步了？

Phase 2 之后，流程轻重的问题解决了，但一个更根本的问题浮出水面：**"现在走到哪个阶段了"这件事，一直靠 AI 的记性和自觉**。

具体来说，v1.0 的运行时是这样的：

- 有一个状态文件（aidlc-state.md），记录每个阶段完成没有、当前在哪个阶段——但这个文件**由模型手写维护**；
- "下一步该做什么"由模型读文档、读状态、自己推导；
- 全仓库有 **20 多处散文指令**在教模型"完成阶段后去把状态文件的第 X 行勾上"——这些指令散落在各个阶段规则文件里；
- 还有一个审计文件（audit.md）记录每次阶段转移，也是模型手写追加。

这套机制的隐患，用一次真实的项目使用（dogfood，"自己吃自己的狗粮"，即用这套工作流开发真实项目来验证它）暴露得淋漓尽致：

- 长对话里模型会**遗忘**开头读过的规则，状态更新走样；
- 会话中断后重开，"恢复现场"全靠模型重新读文档推导，**每次恢复都可能不一样**；
- 状态被改坏了（无论故意还是手滑）**没有任何检测手段**；
- 路由逻辑（下一步是什么）在文档里写着，但文档不是代码，**不保证被遵守**。

这正是开篇那句纲领的反面："精确"的事（状态、路由、审计）落在了 LLM 手里。LLM 擅长判断，但不擅长一丝不苟的记账。

### 解题思路：一个"轻量编排引擎"

v2.0 用 50 多个 TS 工具 + 17 个钩子解决这个问题，但那套东西绑死了 opencode。我要的是：**同等理念，更轻的可移植性**。

最终方案：写一个**单文件 Python 引擎** `scripts/engine.py`，作为**必选运行时组件**随技能分发。用户侧的全部前提只有两条：harness 能加载技能 + 机器上有 Python 3.8+（只用标准库，不用装任何第三方包）。

这里有个重要的决策转向值得如实记录：最初我打算让引擎是"可选增强层"——没 Python 也能退回纯 Markdown 模式。后来放弃了，因为**双模镜像会掐死演进**：引擎每加一个功能，就得手写一份等效的 Markdown 约定给"无引擎模式"，两份还得永远保持一致——这恰恰是 Phase 1 刚刚消灭掉的那种重复。于是立场修订为：**无引擎 = 硬停（HARD STOP），提示安装 Python**。

引擎的分工哲学完全对应"三归"：

| 归属 | 内容 |
|---|---|
| **精确归工具（引擎管）** | 跨阶段路由（下一步是什么）、状态机（走到哪了）、审计日志（发生过什么）、状态完整性校验（状态有没有坏） |
| **判断归 LLM（模型管）** | 阶段内的实际工作：理解需求、写文档、写代码；有条件阶段的"适用不适用"判断；scope 推荐、深度自适应 |
| **决定归人类（你管）** | 每个审批门依然是双选项（Approve & Continue / Request Changes），AI 永远不能替你选 |

有个精彩的细节：每个阶段 frontmatter 里有一个 `condition` 字段，是给人读的散文（"仅当项目是棕地时执行"）。引擎**永远不解析它**——CONDITIONAL 阶段照常派发，模型判断不适用就用 `report --result skipped` 报告跳过并说明理由。判断权老老实实留在 LLM，工具只负责记账。这就是"判断归 LLM"在接口设计上的体现。

### 实际方案

**1. 编译而非解析（compile-to-JSON）。**
generate.py 新增一个"编译渲染器"：把全部 frontmatter 编译成一份机器友好的 `scripts/data/stage-graph.json`。引擎运行时**只读这份 JSON，永不解析 frontmatter**。好处是：解析 Markdown 的所有风险和复杂性都被关在"作者期"（改技能的人才跑生成器），运行时的引擎面对的永远是一份干净、已校验的数据。JSON 的漂移同样被 `--check` 和 CI 盯着。

**2. 一套动词（子命令）。**
引擎的对外接口就是几个命令行子命令，AI 在对话里通过 shell 调用它们：

- `status`（只读）：现在什么状态？在哪个阶段？——会话启动探测和恢复都靠它；
- `next`（只读）：下一步干什么？——引擎按"线性扫描 + scope 过滤 + 状态覆盖 + 跳过标记"算出下一步，返回一条**指令 JSON（directive）**：要么是"执行某阶段"（附上该阶段的全部契约信息：产物、依赖、门类型、规则文件路径），要么是"全部完成"，要么是"出错了"（错误对象带机器可读的错误码、人类可读的信息、补救提示）；
- `report`（**唯一的转移写入口**）：阶段做完，报告结果。引擎据此原子写状态 + 追加审计条目。结果有五种，各对应严格定义的转移语义：`completed`（完成，勾选并推进）/ `approved`（门批准，推进）/ `rejected`（门拒绝，停在原地）/ `revised`（修订后重交，停在原地）/ `skipped`（跳过，须附理由）；
- `jump`（写操作）：改主意专用。回跳会重置指针之后的所有阶段，前跳会标注跳过的阶段，全部留审计；
- `jump --fresh`：整体归档、从零开始；
- `rebase`：状态重定基线（下面讲）；
- `init`：创建初始状态文件。

**3. 状态文件分区所有权。**
状态文件还是 Markdown（人能直接读），但内部划了"辖区"：`<!-- BEGIN/END ENGINE-STATE -->` 标记区内（阶段勾选表、当前状态、State Digest）**只有引擎能写**；区外（项目信息、扩展配置、执行计划摘要等）模型按模板维护。这里有个巧妙的"模型写-引擎读"通道：工作流规划批准后，模型把 Scope/Depth/要执行和跳过的阶段按固定格式写进"执行计划摘要"区，引擎读它来做路由过滤——**Phase 0/1 时"无人消费的计划文档"这个遗留问题就此收口**。

**4. 完整性校验（防手改）。**
引擎每次写状态时附带一段 **State Digest**（对引擎辖区内容算的 SHA-256 摘要）。每次读状态先校验摘要，再和审计日志交叉核对（勾选记录和转移事件对不对得上）。发现漂移 → 引擎返回错误、工作流挂起、**必须人类确认后才能 rebase 重定基线**。要诚实说明它的边界：这是**检测，不是阻止**——没有钩子的环境拦不住模型真的去改文件，但"改了必被发现"这件事是确定的。它的威胁模型是"模型疏忽/手滑"，不是"模型蓄意对抗"。

**5. 全文档收口。**
这是实施中最大的一块暗活：grep 全部规则文件，把 20 多处"教模型手改状态"的散文指令**逐一改写或删除**——否则模型会同时收到"引擎独占写状态"和"完成后去把第 X 行勾上"两组矛盾指令，实际使用必撞车。错误恢复协议也整体重定向：过去教模型手改状态自救的一堆路径，统一改成"完整性挂起 → 人工确认 → 引擎重定基线"。

### 结果

- 引擎初版约 1000 行（含后续迭代，如今 1677 行），纯标准库；
- 77 个单元测试全绿（生成器 30 + 引擎 47）；二次运行幂等；`--check` 零漂移；
- **裸项目验收**（硬标准：只复制技能目录到一个全新项目，不带任何其他文件）跑通：全新项目全流程走到完成、棕地项目 bugfix 裁剪、手改状态触发挂起→重定基线、会话中断恢复、向后跳、归档重来。

上线后两天内又做了两轮快速迭代，值得记录的几件：

1. **真实项目二次 dogfood**：确认"引擎下限收益已兑现"——长对话跑偏之后，恢复现场零歧义（状态是引擎写的，指哪读哪）；同时暴露了一个逗号解析 bug，被引擎的严格校验当场拦下——这恰好证明"精确归工具"的价值：散文时代的这类错误会静默滑过去。
2. **token 账本**：实测整个技能加载约 18 个文件、171KB（≈4.3 万 token），引擎带来约 +15% 增量，其中大头是引擎契约文档被放进了"每次必读"清单。考证后发现没有任何决策要求它必读——纯属改写时的分组惯性。把它改成按需加载后，引擎净增量压到约 +3~4%。
3. **一轮全面审查**修掉三个实质缺陷：工作流变更规程和引擎路由语义冲突（文档教的步骤会被引擎拒绝）、截断状态被误判为旧格式（现在能精确识别"损坏"并给出修复路径）、CI 只查漂移不跑测试（引擎回归对 CI 不可见——现在测试套件也进 CI）。

### 价值

- **状态从此有了唯一权威源**。走到哪一步、发生过什么，一查便知，不再依赖任何模型的记性。会话中断、换人、换机器，恢复动作都是同一个：跑一下 `status`。
- **每次转移都留痕**。审计日志由引擎原子追加，"这个需求为什么被打回过"这类问题有了可靠答案。
- **"改主意"有了正门**。完整性校验堵死歪路（不许手改状态），`jump` 敞开正门（正规改道通道）——二者是阴阳配套：缺了 jump，每次正常的需求变更都会以"完整性告警"的形态呈现，体验就裂了。
- **Phase 4 的死结解开了**。未来的多会话团队协作需要"锁"（防止两个会话同时认领一个任务），而锁的前提恰恰是"引擎必选、状态唯一写入者"。Phase 3 的这个决策等于提前给 Phase 4 铺了路。

## Phase 3.1：让 AI 记得住"上次做到哪"

**完成时间：2026-09-22**

### 遇到的问题：换个会话就"断片"

引擎解决了"状态在哪"的问题，但真实用户反馈很快指出下一个软肋（这条反馈价值千金，它直接催生了 3.1 和 3.3 两个版本）：

> 长会话跑到一半，新开一个会话说"从上次结束的地方继续"，结果**加载旧制品不完整，工作流跑偏了**。

有意思的是诊断结论：**路由没漂**（引擎管着呢，下一步算得清清楚楚），漂的是**执行层**。代码级考证找到三个断点：

1. **状态机的粒度是"阶段"，而中断发生在阶段内部**。引擎知道"当前在功能设计阶段"，但不知道这个阶段做到一半时停在了哪一步。而且没有"收尾"动作——中断不留任何痕迹。
2. **恢复协议是一份"必须全量加载"的散文清单**。旧规则写着"MANDATORY: 加载上一阶段全部制品"——平铺几十条、无优先级、无验证。这在物理上就执行不了，于是模型开始**抽样加载**，抽样就漏，漏了就偏。
3. **半成品无探测**。当前阶段的产物文件如果已经存在（上次写到一半），引擎一声不吭——模型不知道该接着写还是从头写。

### 解题思路：泊车留条 + 分级阅读 + 第一代传感器

方案三件套，外加两条影响深远的新决策（D13/D14）：

**第一件：`park`（泊车）动词。**
`engine.py park --note "功能设计写到第 3 节，还差错误处理部分"`。效果：

- 状态文件的当前状态区写一行 "Last Parked: 功能设计 —— ……（你的便签）"；
- 追加一份交接文件 `aidlc-docs/handoff.md`（引擎独写、只增不删）。

两个关键设计：**泊车不是转移**——它不动阶段指针、不勾任何勾选框，纯粹留注记（新会话恢复时引擎会把这个便签原样递给你）；**审计分家**——泊车不写进审计日志。审计是"转移账本"，只记阶段变化，天然有界；如果把每次泊车也记进去，日志会无限膨胀，校验成本随之上涨。泊车记到专门的交接文件里，各走各的账。

**第二件：`status` 升级成"恢复简报"。**
新会话开局跑一次 `status`，引擎返回的不只是"当前阶段"，还有：

- `resume_note`：上次泊车的便签（有就给，没有就空）；
- `recent_events`：最近 5 次阶段转移（从审计日志尾部提取——这个数据源一直躺在那，过去没人用）；
- `artifact_alerts`：**传感器读数**（下面细讲）。

配套地，恢复协议从"全量加载"改写成**分级阅读**：第一级读引擎输出（状态+便签+近期事件+告警），第二级读下一步指令里声明的必需上游产物，第三级按需查一个"产物地图"。三级递进，每一级都明确"读到什么就够了"。

**第三件：第一代传感器（artifact_alerts）。**
引擎在 `status`（恢复时）和 `report`（收单时）两个时机做检查：

- **missing-produces（缺产物）**：已完成的阶段，声明的产物文件在不在？在——这里有个精妙的**不对称语义**：只有当某阶段有 2 个以上"具体产物"且**全部**缺失时才告警。为什么这么保守？因为考证发现很多产物是**条件性**的（比如"有问题文件才生成问题文件"），单个产物缺席分不清是"条件不满足"还是"真忘了"。宁可漏报，不可误报——误报会训练用户无视告警。
- **resumed-artifacts（半成品残留）**：当前阶段的产物文件如果**已经存在**，提醒"可能有半成品，先读再写、能追加别重写"。存在信号误报代价低（"先读后写"本来就是正确动作），所以语义反过来：任一存在就提示。

传感器的整体纪律是 **fail-open（失效放行）**：探测过程出任何异常，返回一个"传感器不可用"标记加空数组，**绝不阻断正常流程**。告警本身也不带强制力——每条告警带一个"处置纪律"字段，明确写着"报告用户，不要自作主张去补制品"。这是防**古德哈特定律**（当告警变成任务，模型就会为了消除告警而编造产物）。

**两条新决策（写进了项目的决策记录）：**

- **D13 动词三层纪律**：引擎动词分三层——读（status/next，无副作用）、**转移（report/jump，封闭集合——今后永远不再新增第二个改变阶段指针的动词）**、生命周期（init/park/rebase）。泊车这类"注记"动词必须保证指针和勾选零变化。以后每加一个新动词，入场券是"和全部既有写动词的两两交互测试"——交互矩阵从此成为 CI 的法定成本。这条纪律是为了防止动词集随版本膨胀最终失控。
- **D14 传感器接口**：传感器的触发点永远锚定在引擎动词上（status/report），这与"不绑定 harness"一脉相承（v2.0 靠写入钩子触发，我们没有钩子）；告警对象固定五个字段（类型/严重度/主体/消息/处置纪律），字段集只增不删、形状永不破坏——这成了 Phase 5 传感器体系的正式接口，今天的第一代实现将来升级时必须通过"输出逐字节一致"的等价测试。

### 结果

测试 102 → 141 → 144 全绿（两轮审查又抓出并修掉 3 处应修项，比如某个旧文档残留"全量加载"指令，和新协议打架）。泊车的几十个边界行为（去重、便签截断、崩溃窗口、写序、和转移动词的交互）全部有测试锁定。

### 价值

- **"换会话继续"从碰运气变成确定性操作**。泊车一秒留痕，恢复三级阅读，半成品有预警。
- **审计账本天然有界**——分家设计让它永远保持小而快。
- **传感器体系有了第一块基石和正式接口**。Phase 5 要做的"制品自检清单"将直接复用这套接口，第一代实现已经是它的形状了。

### 诚实边界：park 防不了"强杀"

写到这里必须主动交代 park 的边界，因为它经常被问：**如果模型正在思考时强行关闭 harness，再新开会话继续——park 能生效吗？**

答案是**不能**，而且不是实现疏忽，是记录在案的取舍（负债清单第⑥条原文："未 park 且当前阶段零制品的中断不可探测——**park 是自律层，非传感器**"）。

原因很根本：park 是模型的**主动自律动作**。泊车仪式定义的三个触发时机——用户说停、话题要切换、预感中断——全部要求模型还有一轮行动的机会。强杀 harness 是唯一不给任何窗口的场景：`park` 命令永远不会被发出。而"进程被杀"这个事件本身，在 harness 无关的世界里**没有任何手段能捕获**——传感器的触发点只能锚定在引擎动词上（D14），因为只有模型调用引擎时才有代码执行的机会。v2.0 靠 opencode 的钩子能多做一点，我们刻意不换——这又是"可移植性 vs 自动化程度"的交换。

但强杀之后并不是全丢。新会话跑 `status`，恢复精度分层：

| 信息层 | 强杀后 | 靠什么 |
|---|---|---|
| 阶段级位置（在哪个阶段） | ✅ 完好 | `current_stage` 来自最后一次 report/jump，引擎原子写 + digest 校验 |
| 时间线（最近发生了什么） | ✅ 完好 | `recent_events` 从审计尾部取最近 5 次转移 |
| 精确断点（阶段内做到第几步） | ❌ 丢失 | 本来靠 park note 提供 |
| 半成品探测 | ⚠️ 视情况 | `resumed-artifacts`：中断前已写出一部分制品文件就告警"先读后写"——它就是为这个场景设计的兜底 |

真正的盲区收窄到一种情况：**中断发生在当前阶段还没写出任何制品时**——没有便签、没有半成品、传感器无信号，恢复精度退化为"知道在这个阶段，不知道做到哪"，模型只能重读规则从头执行这个阶段。改善路径已经排期：Phase 4 的单元级检查点会在更细粒度上留痕，届时这个缝隙会自然收窄。

我一直觉得，"一个机制防不了什么"比"它能做什么"更能说明系统的成色——这条边界和它的兜底方案、改善排期，在项目文档里是同一页纸上的三行字。

## Phase 3.2：隔壁框架的好东西，搬机制不搬代码

**完成时间：2026-09-22（同日立项、同日完成）**

### 遇到的问题（或者说：遇到的机遇）

3.1 立项同一天，我顺手做了一次外部调研：考察了另一个 AI 工作流框架 **Trellis**。它和我们是同一个哲学（也是"判断归 LLM、精确归工具、决定归人类"），但押注的方向不同——我们押"阶段路由的确定性"，它押"状态保活与知识复利"。正因如此，它山之石特别多。

调研产出了四档借鉴清单（立即借鉴 / 排期借鉴 / 到某阶段再借鉴 / 仅记录）。3.2 这个"立即批"承载其中 5+2 项，**原则是搬机制、零代码复制**——学的是思路，落的是自己的实现。

### 实际方案：七个工作包

**WP-1 Evidence-First 提问纪律（证据优先）。**
过去规则里到处写着"拿不准就问用户"，结果 AI 拿着**代码库里明明有答案的问题**去烦用户（"这个项目用什么数据库？"——配置文件里写着呢！）。新的纪律：**凡是可以靠探索代码库/制品回答的问题，必须靠探索解决并引用出处，不进问题清单**。配套改造：所有选项题在"存在推荐项"时必须给推荐理由 + "如果你另选会怎样"的代价说明；9 个文件做了系统性收口（每处"积极提问"指令旁边都加上了"先过证据门"的限定）。一句话：**把用户的注意力当成稀缺资源来花**。

**WP-2 dogfood 协议。**
过去"自我试用"没有章法，试用完只能说"感觉不错"。新的协议文档定义了六条度量（重复解释次数、需求文档清晰度、重复评审次数、换工具稳定性、新人首任务独立完成度、问题沉淀率），数据源全部取自引擎已有的客观记录（审计条目数、转移趋势）。还有一条诚实声明我很喜欢：**消融对照（"没有引擎会怎样"的对照组）在当前架构下无法构造**——因为引擎已是必选组件，拆掉它工作流根本不启动。所以对照只能用"历史版本对比"和"引擎内开关对比"替代。承认实验设计的局限，和做实验本身一样重要。

**WP-3 长制品导航索引。**
规则：超过 300 行的内容制品，顶部必须维护一张"任务→章节"导航表。动机很朴素：AI 的上下文有限，人也懒得滚动——一张表让读者按需跳转。注意它是 **advisory（建议级）**而非阻塞级：违反了只列出来、不拦门。理由是"缺失无危害，但阻塞级告警会训练用户无视告警"——和传感器的保守哲学一脉相承。

**WP-4 构建与测试阶段的提交协议（Commit Protocol）。**
AI 帮你写完代码，最后一步提交（git commit）怎么管？时序定死：**门批准 → 引擎记账 → 完成消息里呈现提交计划 → 你说"继续"即批准执行提交**。提交计划的内容纪律：只提交本次会话工具实际写过的文件（判定依据是工具调用记录，绝不静默夹带）；一次性展示完整计划；禁止 amend、禁止 push（除非你明说）；不是 git 仓库就标注跳过。自主模式下更进一步：**绝不自动提交**，只列出待提交清单等你发话。

**WP-5 逆向工程阶段的可选产物。**
棕地项目（在已有代码库上工作）做逆向工程时，可以产出一份"工作约定"文档——关键是**每条约定必须带来源引用**（从哪个文件的什么情况总结出来的），拒绝空话。它同时被定位为未来"知识树"（Phase 5A）的种子：项目越用越懂你的起点。

**WP-6 契约硬规则单测清零。**
Phase 1 的阶段契约定义了 16 条校验规则，其中不少一直没有专门的单元测试。本批补齐 25 个测试，规则全覆盖，还用"保留字段夹具"锁定了"预留但不启用的字段"（reviewer/sensors）不会被误伤——给未来留的门，用测试守住。

### 结果

七包全部同日完成（并行分发了三个执行者子任务，强耦合的主包我自己做）。测试 144 → 169 全绿。全树扫描确认没有互相矛盾的指令残留。

### 价值

- **提问质量**是这个批次最直观的收益：问题清单变短了，每个问题都带着"我已经查过什么"的诚意。
- **自我验证有了章法**：后续每个版本的"好不好用"都有了数字可看，而不是体感。
- **提交安全**：AI 再也不会背着你在 git 里夹带私货。
- 方法论上还验证了一件事：**跨框架借鉴的正确姿势是"机制移植"**——理解对方为什么这么做，用自己项目的语言和架构重新实现，而不是复制粘贴。零代码复制，全部原生。

## Phase 3.3：真实项目验收之后，把教训变成机制

**完成时间：2026-09-24（同日立项、同日完成）**

### 遇到的问题：验收一个真项目，暴露的真问题

3.2 落地的 dogfood 协议，服务的第一个完整周期是一个真实项目：一个计算器应用（代号 fx991，跑了两个迭代）。验收通过了，但验收的价值全在细节里：

- 一项悬而未决的旧决策有了答案：3.1 做的"缺产物软警告"要不要升级成"硬阻断"？两个迭代里它**一次都没触发**——因为这个传感器的定位就是"灾难检测"（大面积产物缺失才报警），正常流程天然碰不到。而实际观测到的制品类问题（检查点遗漏、审计误替换、计数不准）都在它的管辖之外。**加严现有警告对已观测问题零解**——于是裁决：不升级，关闭。（同时诚实声明：这是"无证据支持升级"的保守裁决，新证据出现可重开。）
- 验收中发现的三处"记录表定性偏差"，共同点是**模型对规则文本的引述失真**——规则就在那里，模型复述的时候走样了。由此沉淀出本批的批次原则，我认为它值得单独抄下来：

> **修法优先选择"把正确行为变成最省力的路径"（一个流程步骤、一条命令），而非追加规则条文。**

规则越写越多，模型引述失真的面就越来越大。与其教它背更多，不如让正确做法顺手得不像故意。

### 实际方案：六个工作包

**WP-1 引擎扩展（四件小而锋利的工具）：**

- **`stamp`（盖章）动词**：零副作用的权威时间戳——跑一下，返回引擎级 UTC 时间。为什么需要它？过去审计条目的时间戳由模型报，模型时钟不可靠，条目可能出现**时序倒挂**（后面的事记录成更早）。现在"要权威时间就找引擎盖章"，审计规则同步改为优先取引擎输出时间。按 D13 分类它属于纯读层——零写入、零副作用。
- **`status` 新增 `autonomous` 键**：把状态文件里模型手写的"自主模式"配置区读出来（宽容解析，读不懂就返回空，绝不连累 status 本身）。又一条"模型写、引擎读"的通道。
- **泊车便签附年龄**：恢复简报里报告当前便签"多大岁数了"（距离泊车过了多少秒）——只报客观数字，判不判断"过时"留给模型。一条旧便签可能已经不再反映现实，年龄是最便宜的风险提示。
- **checkpoint-missing 告警**：检测"该有阶段检查点的地方没有检查点"（仅在用户启用了检查点扩展时才查，fail-open 不变）。

**WP-2 强制扩展发现步骤。**
dogfood 暴露的一个流程漏洞：有类"强制扩展"规则在文档里声明了，但加载流程的编号步骤里没覆盖到它——规则在，流程不通。修法正是批次原则的示范：给加载流程补一个**机械可执行的第 4 步**（"列出全部规则文件，减去有 opt-in 伴随文件的，剩下的立即加载"），而不是加一条"别忘了某某"的叮嘱。

**WP-3 范围收缩规程（工作流变更新增 Type 10）。**
真实项目里发生了"砍需求"：做到一半，一批功能要撤掉。当时的操作（在关卡如实报 rejected → 跳回最上游受影响阶段 → 就地修订 12 处文档 → 重走全链）被实践验证有效，本批把它固化成正式规程，包含几个考究的细节：**问答/决策历史文本受保护不得改写**（历史就是历史，只能追加修订说明）；**Deferred（推迟）的编号永不回收**（FR-30 被推迟了，将来新需求就从 FR-35 开始编，追溯链永不断裂）。

**WP-4 文档判例与自证治理。**
给"redo 时哪些文本受保护"补了正反判例；清扫类声明（"我检查过全仓库没有 X"）从今往后**必须附上所用的搜索模式和扫描范围**——否则就是自说自话。

**WP-5 追溯矩阵脚本。**
`scripts/trace-matrix.py`（纯标准库，作者期工具）：读需求文档的功能需求编号和用户故事的追溯映射，输出一张"FR 覆盖矩阵"+ 计数核对 + Deferred/Reserved 保留核对。用真实数据冒烟：功能需求 29 条（24 条生效 + 5 条推迟），和项目文档自述完全一致；4 条推迟的故事和修订记录吻合。它不进 CI——按需运行的手工核对工具。

**WP-6 提问工具能力抽象。**
dogfood 之外顺手修了一个 harness 无关性违规：规则里写死了 OpenCode 的 `question` 工具名——换个工具（Claude Code 的等价物叫 AskUserQuestion，有的工具压根没有）就对不上了。改法不是枚举工具名，而是**按能力特征定义**："凡能在同一次交互里呈现一组带选项的问题并收回答案的工具，无论何名。"具体参数在调用时适配。8 处文档同步。

### 结果

单日完成全部六包（主包自做，三路并行分发执行者，逐个 diff 复核——其中执行者复核揪出两处清单外残留和一个继承语义 bug，都当场裁决修复）。**205 个测试全绿**（169 + 引擎 14 + 追溯矩阵 22）；`--check` 零漂移；真实数据冒烟通过。随后一轮独立全面审查：0 个阻断级、1 个应修级、6 个建议级，**全部当天修复**——包括一个连真实项目都没暴露的分支缺口（"最上游受影响阶段恰好是当前阶段"时跳转必被引擎拒绝，规程补了"跳过跳转、就地修订"的分支）。

### 价值

- **时间戳从此权威**，审计的时序可信。
- **砍需求有了合法通道**，且历史不可篡改、编号永不复用——这两条对"项目记忆"的价值会随时间复利。
- **多会话前的最后加固**：这批修的每一个问题（恢复、审计、时间戳、砍需求），到了 Phase 4 的多会话团队场景都会被放大（更多恢复、更多审计、更多交叉）。先在单会话里把它们钉死，是给未来上保险。

## 尾声：一条主线，几个数字，几点诚实

### 一条主线

回头看这六轮迭代，有一条贯穿始终的主线，就是那句纲领的逐步落地：

- **Phase 1** 把"阶段"从散文变成数据（事实源）；
- **Phase 2** 用同一份数据推导出任务裁剪（第一个消费者）；
- **Phase 3** 把同一份数据编译成引擎的路由表（第二个消费者）——"精确归工具"至此成立；
- **Phase 3.1** 给引擎补上"记忆的连续性"（泊车、恢复简报、传感器）；
- **Phase 3.2/3.3** 用外部借鉴和真实反馈，把"判断归 LLM"和"决定归人类"的边界打磨得更干净（证据优先的提问、时序定死的提交协议、砍需求的合法通道）。

而"决定归人类"从第一天到最后一天没变过：每个审批门都是你说了算。

### 几个数字

| 指标 | 数值 |
|---|---|
| 阶段 | 3 相位 14 阶段，每个带机器可读契约 |
| 任务类型 | 6 种 scope × 14 阶段的裁剪矩阵，自动生成 |
| 引擎 | 单文件 1677 行 Python，纯标准库，8 个子命令 |
| 生成器 | 单文件 1321 行 Python，17 个生成区，`--check` 漂移检测 + CI |
| 测试 | 20 → 77 → 102 → 144 → 169 → **205**，全绿 |
| 交付节奏 | 3.2 和 3.3 都是"当天立项、当天完成、当天审查" |
| 运行时依赖 | 仅 Python 3.8+，不装任何包 |

### 几点诚实

写博客不讲漂亮话，这套设计有几条**诚实的边界**，我一直记录在案：

1. **检测不等于阻止**。没有 harness 钩子的环境，工具层防不住一个铁了心要伪造批准的模型。我们的对策是提示词纪律 + 完整审计留痕（每一步都查得到），以及威胁模型明确定义为"疏忽"而非"对抗"。
2. **消融实验做不了**。"没有引擎会怎样"的对照组在当前架构下无法构造（引擎必选），改进效果只能靠历史对比和客观度量间接观察。
3. **传感器宁可漏报不误报**。缺产物检测设计得非常保守（多个产物全缺才报），因为误报会训练用户无视告警——那是比漏报更糟的失败模式。
4. **泊车防不了强杀**。park 是模型的主动自律动作，强关 harness 时它没有机会执行，而"进程被杀"在 harness 无关的世界里无法捕获（负债清单明文记录）。兜底是半成品传感器，盲区是"未泊车且零制品"的中断，留待 Phase 4 的单元级检查点收窄（详见 Phase 3.1 一节）。

### 下一步

Phase 4 是团队构建：多个 AI 会话（或人机混合）像真正的开发团队一样并行工作——任务认领与释放锁、按单元编排波次、单阶段独立重跑。地基（结构化单元清单、封闭的动词集、状态唯一写入者）在前面各阶段已经埋好。

再往后是 Phase 5：让工作流"越用越懂你的项目"（知识树与学习闭环）和更智能的评审体系。

从一堆会互相打架的 Markdown，到一套状态有唯一权威源、恢复有分级协议、变更有合法通道、每次转移都有审计的可移植工作流——**两周，六个版本，一条主线**。

这就是 Phase 1 到 3.3 的故事。
